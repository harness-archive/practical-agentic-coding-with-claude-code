# 클로드코드와 MoAI-ADK
- AI 코딩의 구조적 문제를 해결하기 위해 설계된 MoAI-ADK를 소개 

## 8-1. 하네스 엔지니어링과 MoAI-ADK
- 바이브 코딩은 작은 규모의 프로토 타입에서는 인상적인 속도를 보여주지만 프로젝트가 복잡해지는 순간 다음과 같은 구조적 문제가 드러난다.
    - 1) 맥락 유실 : AI는 세션 기반으로만 기억하므로 새 세션을 열면 기존 대화를 기억하지 못한다.
    - 2) 품질의 비결정성 : 같은 요청을 두번하면 AI는 다른 코드를 생성한다. 
    - 3) 기존 코드의 파괴 : AI에 부분 수정을 요청했을 때 AI는 수정 요청한 부분만이 아니라 관련 코드까지 변경하는 일이 잦다.
    - 4) 유지보수의 불가능 : AI가 기존 코드를 재사용 가능한 모듈로 통합하기 보다 새로운 코드를 생성하여 유지 보수 비용을 증가시킴

### 1) 에이전트 하네스, MoAI-ADK
- 바이브 코딩의 구조적 문제를 해결하려면 AI코딩의 편의성을 유지하면서도 품질, 보안, 유지보수성을 확보하는 체계적인 방법론이 필요하다.
- MoAI-ADK는 클로드 코드 내에서 에이전트가 상호작용을 통해 에이전트 코딩을 수행하는 ADK로 세가지 핵심 원칙으로 바이브 코딩의 문제를 해결하는 에이전트 하네스이다. 
  - 1) SSD(Spec-Driven-Development) 명세 기반 개발 : 코드를 작성하기 전 SPEC 문서를 먼저 완성하고 문서에 정의된 범위 내에서만 개발을 진행하는 방법론
  - 2) TDD와 DDD 이진 방법론 : 신규 프로젝트에는 TDD를 기존에 만들어진 프로젝트에는 DDD를 적용한다. 바이브 코딩의 기존 코드 파괴 문제와 유지 불가능성 문제를 해결
  - 3) TRUST-5 품질 프레임워크 : TRUST-5는 Tested(테스트형), Readable(읽기 쉬움), Unified(통일됨), Secured(안전함), Trackable(추적 가능함)의 다섯가지 품질 기준으로 구성

### 2) 하네스 엔지니어링
- MoAI-ADK는 AI 에이전트가 직접 코드를 작성하는 대신, 에이전트가 작동할 환경을 설계하는 하네스 엔지니어링을 구현한다. 
- MoAI-ADK는 에이전트의 능력을 소프트웨어 공학원칙 안에서 발휘하도록 유도하는 장구 역할을 한다.
- 하네스 엔지니어링의 핵심 원칙은 실수의 재발을 구조적으로 차단하는데 있다. 에이전트가 동일한 실수를 두 번 다시 할 수 없도록 환경 자체를 개선
  - 1) 암묵적 프롬프팅의 정교화 : CLAUDE.md, /rules 디렉토리에 잘못된 명력어나 API를 선택하지 않도록 사전에 차단
  - 2) 검증 도구 직접 제작 : 에이전트가 스스로 결과를 검증할 수 있는 도구를 개발자가 직접 만들어 에이전트에 제공

### 3) MoAI-ADK가 해결하는 문제
- 앞서 설명한 원칙을 자동화된 파이프라인으로 구현하며 개발자가 원칙을 일일이 기억하고 수동으로 적용할 필요가 없다. 
- MoAI-ADK의 핵심 워크플로는 명세에서 구현 그리고 문서화로 이어지는 plan-run-sync 파이프라인이다.
  - 1) plan : /moai plan 명령어를 실행하면 manage-spec 에이전트가 개발자의 자연어 요청을 SPEC 문서로 변환
  - 2) run : /moai run SPEC-XXX 명령어로 manager-tdd 또는 manager-ddd 에이전트가 SPEC에 정의된 요구사항을 TDD/DDD 방법론에 따라 구현한다.
  - 3) sync : /moai sync SPEC-XXX 명령어로 manager-docs 에이전트가 API 문서를 생성하고, CHANGELOG를 업데이트하며, PR을 작성한다. 
- MoAI는 중심 오케스트레이터 역할을 수행하며, 개발자의 요청을 분석해서 가장 적합한 전문 에이전트에 작업을 위임한다. 
- MoAI-ADK에는 Manager 에이전트, Expert에이전트, Builder에이전트가 있어 개발자가 에이전트를 선택할 필요 없이 MoAI가 요청의 복잡도와 도메인을 분석하여 최적의 에이전트를 자동으로 선택한다. 

### 4) MoAI-ADK 실행 엔진
- MoAI-ADK 원칙과 4계층 아키텍처는 모두 moai라는 Go언어로 작성된 CLI 바이너리를 통해 실행
- Go언어로 작성된 이유는 단일 바이너리 배포의 편의성 떄문이다.
- 파이썬이나 Node.js처럼 런타임 의존성이 필요하지 않으며 다운로드 후 바로 실행할수 있기 때문

## 8-3. 아키텍처
- MoAI-ADK는 스킬, 에이전트, 언어별 규칙이 하나의 통합된 체계안에서 작동하는 프레임워크이다. 
 
### 1) 4계층 구조
- MoAI-ADK는 4계층 아키텍처로 설계되어있다. 관심사의 분리 장점을 갖는다. 
- Foundation 계층
  - Core(SPEC 시스템, TRUST-5), Claude(클로드 코드 오케스트레이션 패턴), Context(프로젝트 분석, 컨텍스트 관리), Quality(품질 게이트, LSP 통합), Philosopher(인지 편향 방지 의사 결정 프레임워크)
  - 5개의 스킬로 구성되며 프로그래밍 언어와 관계없이 항상 적용
- Workflow 계층
  - 개발 워크플로를 정의
  - Spec, DDD, TDD, Loop, Templates, Worktree, Testing 7개의 스킬이 속하며 plan-run-sync 3단계 파이프라인의 구체적인 실행 절차가 속함
- Domain 계층
  - 기술 도메인별 전문 지식을 제공
  - Backend, Frontend, Database, 프로그래밍 언어 등이 스킬이 포함된다. 
- Application 계층
  - 개발자가 직접 사용하는 인터페이스
  - /moai plan, /moai run 등의 슬래시 명령어, 에이전트 정의 등 카테고리별 스킬이 배치 

## 8-4. 개발 방법론, TDD와 DDD

### 1) SPEC과 EARS 형식
- 세션이 끊겨도 SPEC만 있으면 언제든 이어서 작업할 수 있다. 
- /moai plan "기능 설명" 명령어 실행시 manage-spec 에이전트가 사용자의 자연어 요청을 분석하여 SPEC 문서를 자동 생성
- 해당 문서의 요구 사항은 EARS 형식으로 작성
- EARS는 자연어의 모호함을 제거하고 테스트로 검증 할 수 있는 형태로 요구 사항을 변환하는 표준화된 구문이다.

### 2) DDD
- DDD는 기존 코드를 안전하게 개선하는 방법론
- 즉, 현재 코드가 속한 영역의 구조와 동작을 깊이 이해한 뒤에 변경을 시도
- ANALYZE 단계 : 어디가 문제인지 분석하는 단계
- PRESERVE 단계 : 현재의 상태를 기록한다.
- IMPROVE 단계 : 작은 단위로 변경한 뒤 매번 테스트를 실행하여 기존 동작이 보존되었는지 검증하는 단계
- 요구 사항을 모두 만족할때 까지 이 세 단계를 반복한다.

### 3) 이진 방법론
- MoAI-ADK는 v2.5.0부터 이진 방법론을 적용한다. 
- 신규 프로젝트에는 TDD를 기존 프로젝트에는 DDD를 적용
- .moai/config/sections/quality.yaml의 development_mode값을 직접 편집하거나 환경 변수 MOAI_DEVELOPMENT_MODE로 방법론을 수동 설정할 수 있다.

## 8-5 TRUST-5 품질 프레임워크
- MoAI-ADK는 모든 코드가 반드시 통과해야하는 다섯가지 품질 관문을 정의

### 1) 다섯가지 원칙
- /moai run 단계에서 구현이 완료되면 다음 다섯가지 원칙을 순차적으로 검증하며 모든 항목을 통과해야 비로소 배포가 가능
  - 1) Tested : 테스트로 검증되었는가
    - 전체 코드의 85% 이상이 테스트로 커버되어야 한다는 기준을 설정
    - 방금 다룬 이진 방법론과 직접 연결되는 내용
  - 2) Readable : 다른 개발자가 이해할 수 있는가 (가독성 검증)
    - 명명규칙을 검증하며 변수, 함수, 클래스 이름이 그 역할을 명확히 드러내야 한다.
    - 린트 오류 0개를 기준으로 린터가 보고하는 모든 규칙 위반을 해결해야 한다. 
  - 3) Unified : 프로젝트 전체에서 일관적인가 (일관성 검증)
    - 자동 포맷터 적용을 전제로 한다 
  - 4) Secured : 보안 취약점은 없는가
    - OWASP Top 10을 준수하는 것이 기본 요건
    - 흔한 보안 취약점을 방지 
  - 5) Trackable : 변경 이력이 추적 가능한가
    - 어떤 변경이 왜 이루어졌는지, 누가 승인했는지, 어떤 이슈와 연관되는지를 명확하게 기록해야한다. 

### 2) LSP 품질 게이트
- LSP 진단 결과를 plan-run-sync 단계별로 다른 임곗값을 적용하여 품질을 관리한다.
- plan 단계 
  - 현재 코드베이스의 LSP 상태를 베이스라인으로 캡처한다.
  - 기존프로젝트에 이미 존재하는 경고나 오류를 인식하고 새로 발생하는 문제만 정확하게 감지하기 위해서
- run 단계
  - LSP 오류0개, 타입 오류 0개, 린트 오류 0개를 요구
- sync 단계
  - 문서화와 PR 생성을 위해 LSP가 꺠끗한 상태여야 한다 
  - 오류는 0개 경고는 최대 10개까지 허용

### 3) Loop Engine: 자유 품질 루프
- TRUST-5 기준에 미달하는 코드가 있을 경우 Loop Engine을 통해 진단, 수정, 검증을 반복하여 코드의 모든 문제를 해결할 수 있다. 
- /moai loop 명령어로 사용
- Loop Engine은 총 다섯 단계로 구성
  - 1단계 : LSP 진단과 AST-grep 진단, 테스트 실행, 커버리지 측정이 병렬로 수행
  - 2단계 : 발견된 이슈가 하나의 목록으로 수집
  - 3단계 : 의존성 순서를 고려한 수정 작업 목록이 자동 생성
  - 4단계 : 수정이 하나씩 순차적으로 적용
  - 5단계 : 수정 결과를 다시 진단하여 문제 해결 여부를 검증

### 4) 품질 리포트 생성
- TRUST-5 검증 결과는 품질 리포트로 생성된다. 
- quality.yaml의 report_generation 섹션이 관리
- user_choice 설정은 리포트의 상세 수준을 결정
  - Minimal(Default)은 통과 여부와 핵심 수치만 포함하는 간결한 리포트 생성
  - Standard는 각 TRUST 원칙별 세부 결과와 LSP 진단 요약 포함
  - Full은 모든 진단 항목의 개별 결과, 회귀 분석, 커버리지 파일별 상세, 수정 이력까지 포함하는 종합 리포트를 생성한다. 

## 8-6 에이전트 생태계
- MoAI가 최상위 오케스트레이터, Manger, Expert, Builder라는 세 가지 범주의 에이전트가 계층적으로 배치 

### 1) Manger 에이전트 그룹
 워크플로의 각 단계를 책임지는 조율자들
 해당 에이전트들은 프로세스를 관리

  | 에이전트             | 역할              | 연결 명령어        | 주요 스킬                   |
  |------------------|-----------------|---------------|-------------------------|
  | manager-spec     | SPEC 문서 생성      | /moai plan    | moai-workflow-spec      |
  | manager-ddd      | DDD구현           | /moai run     | moai-workflow-ddd       |
  | manager-tdd      | TDD구현           | /moai run     | moai-workflow-tdd       |
  | manager-docs     | 문서 생성 및 동기화     | /moai sync    | moai-docs-generation    |
  | manager-quality  | TRUST-5 품질 검증   | 자동실행          | moai-foundation-quality | 
  | manager-project  | 프로젝트 구성 및 초기화   | /moai project | moai-workflow-project   |
  | manager-strategy | 시스템 설계, 아키텍처 결정 | 자동 위임         | moai-foundation-core    |
  | manager-git      | 깃 브랜칭, PR, 머지전략 | 자동 위임         | moai-foundation-core    |

### 2) Expert 에이전트 그룹
- 특정 도메인에서 실제 구현 작업을 수행하는 실행자
- Manager 에이전트가 프로세스를 설계한 내용을 MoAI가 다시 Expert 에이전트들에게 설계에 따라 코드를 작성하라고 위임

  | 에이전트               | 전문 도메인            | 주요 스킬                 | 활용 예시                |
    |--------------------|-------------------|-----------------------|----------------------|
  | expert-backend     | API, 서버로직, DB 통합  | moai-domain-backend   | REST API 엔드포인트를 만들어줘 |
  | expert-frontend    | UI 컴포넌트, 클라이언트 로직 | moai-domain-forntend  | 로그인 페이지를 구현해줘        |
  | expert-security    | OWASP, 보안분석       | moai-foundation-core  | 보안 취약점을 점검해줘         |
  | expert-devops      | CI/CD, 인프라, 배포    | 플랫폼별 스킬               | Github Actions를 설정해줘 |
  | expert-perfomance  | 성능 최적화, 프로파일링     | 도메인별 스킬               | 이 쿼리를 최적화해줘          | 
  | expert-debug       | 디버깅, 오류분석         | 언어별 스킬                | 이 에러의 원인을 찾아줘        |
  | expert-testing     | 테스트 전략, 커버리지      | moai-workflow-testing | 테스트 커버리지를 개선해줘       |
  | expert-refactoring | 코드 구조 개선, 리팩터링    | moai-workflow-ddd     | 이 모듈을 리팩터링해줘         |

### 3) Builder 에이전트 그룹
- MoAI-ADK 생태계 자체를 확장하는 메타 에이전트
- Manger와 Expert가 만들어야 하는 소프트웨어를 만드는 도구를 만든다
  
- | 에이전트           | 생성 대상      | 출력 경로                               | 활용 시나리오               |
  |----------------|------------|-------------------------------------|-----------------------|
  | builder-agent  | 에이전트 정의 파일 | .claude/agents/*.md                 | 커스텀 전문가 에이전트 추가       |
  | builder-skill  | 스킬 정의 파일   | .claude/skills/my-skills/*/SKILL.md | 도메인 전문 지식 추가          |
  | builder-plugin | 플러그인 번들    | .claude-plugin/pligin.json          | 스킬 + 에이전트 + 명령어 통합 배포 |
