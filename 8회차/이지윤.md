# 8장. 클로드 코드와 MoAI-ADK — 쉽게 풀어 쓴 정리

## 8-1. 하네스 엔지니어링과 MoAI-ADK

### 바이브 코딩이 왜 위험한가

2025년 2월, 안드레이 카파시(전 테슬라 AI 총괄, OpenAI 창립 멤버)가 "바이브 코딩"이라는 말을 처음 썼습니다. AI에게 "이런 기능 만들어줘"라고 방향만 던져주고, 나온 코드를 자세히 읽지도 않은 채 "일단 실행해보고 되면 OK"로 넘어가는 개발 방식을 말합니다.

이건 **설계도 없이 집을 짓는 것과 같습니다(바이브 코딩, Vibe Coding)**. 방 한 칸짜리 작은 창고라면 그냥 뚝딱 지어도 별문제가 없습니다. 그런데 2층을 올리려는 순간 "어디가 기둥이고 어디가 배관인지 아무도 모른다"는 사실이 발목을 잡습니다. AI 코딩도 똑같습니다. 작은 프로토타입을 뚝딱 만들 때는 놀랍도록 빠르지만, 프로젝트가 커지는 순간 다음 네 가지 문제가 터져 나옵니다.

1. **맥락 유실** — AI는 대화창(세션) 단위로만 기억합니다. 새 대화를 열면 지난번에 뭘 정했는지 다 잊어버립니다. 마치 매번 다른 사람이 인수인계도 없이 프로젝트에 투입되는 것과 같습니다.
2. **품질의 비결정성** — 같은 요청을 두 번 해도 AI는 매번 다른 코드를 냅니다. 어떤 날은 깔끔하고, 어떤 날은 보안 구멍(SQL 인젝션 등)이 뚫린 코드가 나옵니다. 실제로 조지타운대 연구에 따르면 여러 AI 모델이 생성한 코드의 절반 가까이에서 보안 취약점이 발견됐다고 합니다.
3. **기존 코드의 파괴** — 한 부분만 고쳐달라고 했는데 관련 없는 다른 코드까지 건드립니다. **설계도 없이 리모델링하다가 기둥(내력벽)을 부수는 것과 같은** 상황입니다.
4. **유지보수 불가능** — AI가 기존 코드를 재사용하기보다 매번 새로 만들다 보니 중복 코드가 쌓입니다. GitClear 조사에 따르면 코드 중복 비율은 늘고, 리팩터링(코드 정리) 활동은 오히려 줄었다고 합니다.

흥미롭게도 바이브 코딩이라는 용어를 만든 카파시 본인조차 나중에 "AI 에이전트를 써봤지만 전혀 잘 작동하지 않았다"며, 자신의 최신 프로젝트는 "기본적으로 전부 손으로 작성"했다고 밝혔습니다. 바이브 코딩은 빠른 프로토타입에는 유용하지만, 실제 서비스용(프로덕션) 소프트웨어를 만드는 방법론은 아니라는 뜻입니다.

### 그래서 나온 게 MoAI-ADK

MoAI-ADK는 바이브 코딩의 편리함(빠른 속도)은 살리면서 품질·보안·유지보수성 문제를 구조적으로 잡기 위한 도구입니다. "클로드 코드 안에서 여러 AI 에이전트가 서로 협력해 코딩하는 도구 모음(Agentic Development Kit, ADK)"이며, 세 가지 원칙으로 문제를 해결합니다.

- **SDD**(Spec-Driven Development, 명세 기반 개발): 코드를 쓰기 전에 "무엇을 만들지" 문서(SPEC)부터 완성한다 → 맥락 유실 해결
- **TDD/DDD**(이진 방법론): 새 프로젝트엔 TDD를, 기존 프로젝트엔 DDD를 적용한다 → 기존 코드 파괴·유지보수 불가능 문제 해결
- **TRUST-5**(품질 프레임워크): 다섯 가지 품질 기준을 자동 검증한다 → 품질의 비결정성 해결

이 세 원칙을 구현하는 방식이 바로 **하네스 엔지니어링(Harness Engineering)**입니다. 기수가 말을 억지로 힘으로 제압하는 게 아니라, **고삐와 안장 같은 장구(하네스, Harness)를 채워서 말이 자연스럽게 옳은 방향으로만 달리게 만드는 것처럼**, AI에게 "이렇게 해"라고 매번 지시하는 대신 AI가 애초에 잘못된 방식으로는 작동할 수 없는 "환경"을 설계하는 것입니다.

하네스 엔지니어링의 핵심은 실수를 "그때그때 고치는 것"이 아니라 "같은 실수를 구조적으로 두 번 다시 못 하게 만드는 것"입니다. 이를 위해 두 가지 방식을 씁니다.

- **암묵적 프롬프팅의 정교화**: `CLAUDE.md`, `.claude/rules` 같은 지침 파일에 "이런 식으로 하지 마라"를 미리 못 박아 둔다.
- **검증 도구 직접 제작**: AI가 스스로 자기 결과물을 확인할 수 있는 도구(테스트 스크립트 등)를 개발자가 미리 만들어 준다.

## 8-2. 설치와 초기 설정

### 시스템 요구 사항

| 항목 | 내용 |
|---|---|
| 운영체제 | macOS, 리눅스, 윈도우(파워셸 7.x 이상, Git Bash, WSL) |
| 메모리 | 최소 4GB |
| 디스크 여유 공간 | 100MB 이상 |

MoAI-ADK는 클로드 코드 위에서 동작하며 Git 기능(브랜치, 커밋 관리)에 의존하므로, 클로드 코드와 Git이 먼저 설치돼 있어야 합니다. (윈도우 cmd.exe는 지원하지 않습니다.)

### 설치

macOS·리눅스·WSL·Git Bash 환경:
```bash
curl -fsSL https://raw.githubusercontent.com/modu-ai/moai-adk/main/install.sh | bash
moai version   # 설치 확인
```

윈도우 파워셸 환경:
```powershell
irm https://raw.githubusercontent.com/modu-ai/moai-adk/main/install.ps1 | iex
```

`moai`는 Go 언어로 만든 CLI(명령줄) 프로그램입니다. **Go로 만든 이유는 "실행 파일 하나만 다운로드하면 바로 쓸 수 있다"는 배포 편의성 때문**입니다. 파이썬이나 Node.js 프로그램처럼 별도 런타임을 설치할 필요가 없다는 뜻입니다(비유하자면, 파이썬/Node 프로그램은 "전용 오디오 플레이어가 있어야 재생되는 파일"이고, Go 실행 파일은 "그냥 더블클릭하면 재생되는 파일"에 가깝습니다).

설치 후 문제가 생기면 순서대로 확인합니다.

1. `command not found: moai` → 터미널 재시작 → `echo $PATH`로 설치 경로 포함 여부 확인 → `which moai`로 실제 위치 확인
2. macOS/리눅스에서 `Permission denied` → `chmod +x ~/.local/bin/moai`로 실행 권한 부여
3. 윈도우에서 한글 계정명(예: '홍길동') 사용 시 `EINVAL` 오류 발생 가능 → ASCII 문자로만 된 임시 경로를 `MOAI_TEMP_DIR` 환경 변수로 지정하거나, 짧은 파일명(8.3 형식) 기능을 활성화

### 프로젝트 초기화

```bash
moai init my-project     # 새 프로젝트 생성
moai init .               # 기존 프로젝트에 적용
```

`moai init`을 실행하면 대화형 마법사가 뜨고, 9단계 질문(대화 언어, 개발자 이름, 프로젝트 이름, Git 전략, GitHub 계정, 커밋 메시지 언어, 코드 주석 언어, 문서 생성 언어, 개발 방법론 선택)에 답하면 프로젝트 환경이 자동으로 구성됩니다.

### 생성되는 파일 구조 — "회사의 사규집 vs 개인 다이어리"에 비유하면

초기화가 끝나면 아래와 같은 구조가 생깁니다.

```
프로젝트 루트/
├── CLAUDE.md              # 핵심 지시 파일 (클로드가 세션 시작 시 가장 먼저 읽음)
├── .mcp.json              # MCP 서버 설정 (외부 도구 연결 정보)
├── .claude/
│   ├── commands/moai      # 슬래시 명령어
│   ├── agents/moai        # 에이전트 20개 이상
│   ├── skills/moai-*      # 스킬(전문 지식 모듈) 52개 이상
│   ├── output-style/moai  # 응답 출력 스타일
│   ├── hooks/moai         # 특정 시점에 자동 실행되는 스크립트
│   └── settings.json      # 권한 및 환경 변수
└── .moai/
    ├── config/sections/   # 세부 설정 YAML 파일 10개
    ├── specs/             # SPEC(명세) 문서
    ├── project/           # 프로젝트 문서
    └── logs/              # 실행 로그
```

`CLAUDE.md`는 **회사 전체가 공유하는 사규집**과 같습니다. 반면 `CLAUDE.local.md`(Git에는 올라가지 않는 개인용 파일)는 **개인의 업무 수첩(다이어리)**에 해당합니다. `moai update`로 프레임워크를 갱신해도 `CLAUDE.local.md`나 `.claude/settings.local.json`처럼 "local"이 붙은 개인 파일은 절대 덮어쓰지 않습니다.

### 환경 진단(moai doctor)

```bash
$ moai doctor
Running system diagnostics...
+----------------------------+--------+
| Check                      | Status |
+----------------------------+--------+
| Git installed               | OK     |
| 클로드 코드 CLI              | OK     |
| Project structure(.moai/)   | OK     |
| Config file(...)            | OK     |
| MCP servers                 | OK     |
+----------------------------+--------+
All checks passed
```

건강검진처럼 설치 상태를 점검해 주는 명령어입니다. 문제가 있으면 항목별로 해결 가이드까지 같이 보여줍니다. 팀에 새 개발자가 들어왔을 때 환경이 제대로 세팅됐는지 확인하는 용도로도 씁니다.

### settings.json의 네 단계 우선순위 — "회사 정책 vs 팀 규칙 vs 개인 취향"

설정은 Managed(회사 전체 강제, 오버라이드 불가) → Local(개인 프로젝트 설정) → Project(팀 공유 설정) → User(개인 전역 설정) 순서로 우선순위가 매겨집니다. **"회사 취업규칙이 팀 내규보다 우선하고, 팀 내규가 개인 메모보다 우선한다"는 조직의 위계**와 비슷합니다.

## 8-3. 아키텍처

### 4계층 구조 — "빌딩의 지하부터 옥상까지"

MoAI-ADK는 4개 층으로 쌓여 있고, **아래층이 위층을 떠받치는 빌딩 구조**와 비슷합니다. 아래층(Foundation)을 바꾸지 않고도 위층(Application)에 새 기능을 얼마든지 추가할 수 있습니다.

| 계층 | 역할 | 예시 |
|---|---|---|
| Application (맨 위) | 개발자가 직접 쓰는 창구 | `/moai plan`, `/moai run` 같은 슬래시 명령어, 27개 전문 에이전트 |
| Domain | 기술 도메인별 전문 지식 | 백엔드/프론트엔드 스킬, 18개 언어별 코딩 규칙 |
| Workflow | 개발 절차 정의 | SPEC 기반 개발, TDD/DDD 이진 방법론, plan-run-sync 3단계 |
| Foundation (맨 아래, 기반) | 품질·통합 원칙 | TRUST-5 품질 프레임워크, 클로드 코드 통합 패턴, 에이전트 위임 규칙 |

예를 들어 Domain 계층에 Rust 지원을 새로 추가해도 Foundation 계층의 품질 원칙은 전혀 손댈 필요가 없습니다. 이렇게 계층별 책임이 분리돼 있어서, 프로젝트 규모에 맞게 유연하게 확장할 수 있습니다.

### CLAUDE.md의 15개 섹션

`CLAUDE.md`는 클로드가 세션을 시작할 때 가장 먼저 읽는 "운영 매뉴얼"입니다. 핵심 정체성, 요청 처리 절차, 명령어 목록, 27개 에이전트 소개, SPEC 워크플로, 품질 게이트 규칙 등 총 15개 섹션으로 구성됩니다.

### Rules 시스템 — "사규집 부속 규정집"

`.claude/rules/moai/` 디렉터리에는 `CLAUDE.md`(핵심 사규)를 뒷받침하는 세부 규정 파일이 4개 카테고리(Core, Development, Workflow, Languages)로 나뉘어 있습니다. 예를 들어 `moai-constitution.md`는 TRUST-5 원칙 같은 "언제나 지켜야 할 헌법"을, `coding-standards.md`는 코딩 표준을 담습니다. 이 규칙들은 **`paths` 설정을 통해 필요할 때만 불러오는(조건부 로딩)** 방식이라, 매번 모든 규칙을 다 읽지 않아 효율적입니다.

### .mcp.json — 외부 도구 연결 설정

MCP(Model Context Protocol)는 AI가 외부 도구·문서를 불러다 쓸 수 있게 해주는 표준 규격입니다. 기본으로 4가지가 설정돼 있습니다.

- **Context7**: 최신 라이브러리 공식 문서를 실시간으로 조회. AI의 학습 데이터는 특정 시점까지만 담겨 있어서, React 19나 Next.js 16처럼 최신 버전 API를 정확히 알려면 외부 문서 조회가 필수적입니다.
- **Sequential Thinking**: 복잡한 문제를 단계별로 분석하고, 이전 결론을 재검토·수정하는 "구조적 사고" 기능. 아키텍처 결정처럼 여러 선택지를 저울질해야 하는 상황에서 씁니다.
- **Pencil**: UI/UX 디자인 파일(.pen) 편집
- **claude-in-chrome**: 크롬 브라우저 자동화

### 출력 스타일 3종

`.claude/output-styles/moai/`에 세 가지 전용 스타일이 있습니다. **MoAI 스타일**은 페어 프로그래밍 파트너처럼 행동하고, **Einstein 스타일**은 "왜"와 "어떻게"에 초점을 맞춘 기술 교육자처럼 설명합니다.

## 8-4. 개발 방법론, TDD와 DDD

### 모든 것은 SPEC에서 시작한다

SPEC은 "AI와 나눈 대화를 파일로 영구 보존"하는 문서입니다. **세션이 끊겨도 SPEC 파일만 있으면 언제든 이어서 작업할 수 있다**는 게 핵심 가치입니다. `/moai plan "기능 설명"`을 실행하면 자동으로 생성됩니다.

SPEC의 요구 사항은 **EARS**(Easy Approach to Requirements Syntax, 롤스로이스 연구진이 항공우주 산업용으로 개발한 요구사항 작성 표준) 형식으로 씁니다. 사람이 "비밀번호는 안전하게 해줘" 같은 모호한 말을 하면, AI가 이걸 다섯 가지 정해진 패턴 중 하나로 구체화합니다.

| 유형 | 의미 | 예시 |
|---|---|---|
| Ubiquitous(항상 참) | 조건 없이 항상 적용 | "시스템은 모든 입력을 검증해야 한다" |
| Event-driven(이벤트 기반) | 특정 이벤트 발생 시 반응 | "WHEN 로그인하면 THEN JWT를 발급해야 한다" |
| State-driven(상태 기반) | 특정 상태 유지 중 동작 | "WHILE 세션이 활성화되는 동안, 5분마다 갱신해야 한다" |
| Unwanted(금지 사항) | 절대 하면 안 되는 동작 | "비밀번호를 평문으로 저장하면 안 된다" |
| Optional(선택적) | 권장되지만 필수는 아님 | "가능하다면 소셜 로그인을 지원해야 한다" |

### 이진 방법론: 신규 프로젝트엔 TDD, 기존 프로젝트엔 DDD

MoAI-ADK는 v2.5.0부터 "TDD 또는 DDD 중 하나만 선택"하는 방식으로 운영됩니다(예전엔 둘을 섞어 쓰는 하이브리드 모드가 있었지만 혼란스러워서 없앴다고 합니다). 프로젝트 상태를 자동 분석해 신규 프로젝트엔 TDD를, 테스트 커버리지가 10% 이상인 기존 프로젝트엔 TDD를, 10% 미만이면 DDD로 특성화 테스트부터 쌓습니다.

여기서 주의할 점 하나: **이 책(그리고 MoAI-ADK)에서 말하는 DDD는 "Domain-Driven Development"의 약자로, 소프트웨어 공학에서 흔히 말하는 에릭 에반스의 "DDD(Domain-Driven Design, 도메인 주도 설계)"와는 다른 개념**입니다. 에반스의 DDD는 비즈니스 도메인의 전략적 설계에 초점을 맞추고, 여기서 다루는 MoAI-ADK의 DDD는 "기존 코드 영역(도메인)을 안전하게 개선하는 것"에 초점을 맞춥니다.

#### TDD: RED → GREEN → REFACTOR

새 코드를 밑바닥부터 만들 때 쓰는 사이클입니다. **테스트(요구사항 체크리스트)를 코드보다 먼저 쓰고, 그 체크리스트를 통과하는 코드만 작성하는 방식**입니다.

1. **RED**: 아직 존재하지 않는 기능에 대한 테스트를 먼저 쓴다 → 당연히 실패한다(빨간불)
2. **GREEN**: 그 테스트를 통과시키는 최소한의 코드만 쓴다 → 통과한다(초록불)
3. **REFACTOR**: 테스트가 계속 통과하는 상태를 유지하면서 코드를 정리한다

#### DDD: ANALYZE → PRESERVE → IMPROVE

이미 존재하는 코드를 개선할 때 쓰는 사이클입니다. 핵심 철학은 **"기존 동작을 부수지 않으면서 개선한다"**입니다. 이걸 **10년 된 집의 리모델링**에 비유할 수 있습니다.

1. **ANALYZE(분석)**: 집 전체를 점검해 벽에 금이 간 곳, 배관 상태, 전기 배선 상태를 확인한다 → 어디가 문제인지 모르면 고칠 수 없다.
2. **PRESERVE(보존)**: 인테리어 사이트의 "비포 & 애프터" 사진처럼, 지금 상태를 있는 그대로 기록한다. 코드에서는 이걸 **특성화 테스트(Characterization Test)**라 부릅니다. 옳고 그름을 판단하지 않고 "지금 이렇게 동작한다"는 사실만 기록합니다. 코드에 버그가 있어도 그 버그까지 그대로 기록하는 게 포인트입니다(버그를 고치는 건 다음 단계에서 의도적으로 할 일입니다).
3. **IMPROVE(개선)**: 한 번에 다 뜯어고치지 않고, 작은 단위로 하나씩 리모델링하면서 매번 테스트를 돌려 "구조가 안전한지, 기존 동작이 그대로 보존됐는지"를 확인한다.

이 세 단계를 요구 사항이 모두 충족될 때까지 반복하고, 테스트가 실패하면 마지막 변경 하나만 되돌리면 됩니다. 이것이 "작은 단계"의 힘입니다. 반대로 잘못된 접근은 "AI에게 전체 코드를 한 번에 다 바꿔 달라"고 하는 것이며, 이는 요청하지 않은 부분까지 건드리는 위험을 그대로 안고 가는 방식입니다.

### 직접 구현해서 확인해 보기 — TDD 실습

말로만 들으면 감이 잘 안 오니, 실제로 TypeScript + Jest로 RED → GREEN → REFACTOR를 그대로 재현해서 돌려봤습니다. (전체 코드는 `moai-adk-practice/src/discount.ts`, `discount.test.ts`)

**요구사항**: 원가와 할인율(%)을 받아 할인된 가격을 반환하는 함수. 할인율은 0~100 사이여야 한다.

**1) RED — 구현 없이 테스트부터 작성하고 실패를 확인**

```ts
// discount.ts (아직 구현 전)
export function calculateDiscountedPrice(originalPrice: number, discountRate: number): number {
  throw new Error("아직 구현되지 않았습니다.");
}
```

```ts
// discount.test.ts
test("정가 10000원에서 20% 할인하면 8000원이다", () => {
  expect(calculateDiscountedPrice(10000, 20)).toBe(8000);
});
// ...할인율 0%, 100%, 범위를 벗어난 값, 음수 원가 등 총 6개 테스트
```

실제로 `npx jest`를 돌려보니 예상대로 6개 중 3개가 실패했습니다(에러를 던져야 하는 테스트 3개는 이미 `throw`가 있어서 우연히 통과).

```
Test Suites: 1 failed, 1 total
Tests:       3 failed, 3 passed, 6 total
```

**2) GREEN — 테스트를 통과시키는 최소 구현**

```ts
export function calculateDiscountedPrice(originalPrice: number, discountRate: number): number {
  if (originalPrice < 0) throw new Error("원가는 0보다 작을 수 없습니다.");
  if (discountRate < 0 || discountRate > 100) throw new Error("할인율은 0~100 사이여야 합니다.");
  return Math.round(originalPrice * (1 - discountRate / 100));
}
```

다시 실행하니 6개 전부 통과했습니다.

```
Tests:       6 passed, 6 total
```

**3) REFACTOR — 검증 로직을 함수로 분리해 가독성 개선**

```ts
export function calculateDiscountedPrice(originalPrice: number, discountRate: number): number {
  assertNonNegative(originalPrice, "원가");
  assertPercentage(discountRate);
  return Math.round(originalPrice * (1 - discountRate / 100));
}
function assertNonNegative(value: number, label: string): void {
  if (value < 0) throw new Error(`${label}는(은) 0보다 작을 수 없습니다.`);
}
function assertPercentage(value: number): void {
  if (value < 0 || value > 100) throw new Error("할인율은 0~100 사이여야 합니다.");
}
```

리팩터링 후에도 6개 테스트가 그대로 통과하는 것을 확인했습니다. 이것이 REFACTOR 단계의 핵심입니다 — **동작은 그대로, 코드만 정리**.

### 직접 구현해서 확인해 보기 — DDD 실습

책의 "레거시 결제 API 리팩터링" 예시를 참고해서, **장바구니·주문서·영수증 세 곳에 중복 구현된 "합계 계산" 로직**을 DDD 사이클로 안전하게 정리해 봤습니다. (전체 코드는 `moai-adk-practice/src/legacy-pricing.ts`, `legacy-pricing.characterization.test.ts`)

**1) ANALYZE — 기존 코드 분석**

```ts
// legacy-pricing.ts (개선 전)
export function cartTotal(items) { /* ... */ return Math.floor(sum * 1.1); }
export function orderTotal(items) { /* ... */ return Math.round(sum * 1.1); }   // cartTotal과 반올림 방식이 다름!
export function receiptTotal(items) { /* ... */ return Math.floor(sum * 1.1); } // cartTotal과 로직 중복
```

세 함수 모두 "소계 계산 + 부가세 10%"를 각자 구현하고 있는데, `orderTotal`만 반올림 방식이 다릅니다. 언뜻 버그처럼 보이지만, **이미 운영 중인 실제 동작**이라 함부로 통일하면 안 됩니다.

**2) PRESERVE — 지금 동작을 있는 그대로 기록(특성화 테스트)**

```ts
test("cartTotal은 소수점을 버린다 (현재 동작)", () => {
  expect(cartTotal(items)).toBe(1105);   // 1105.5원 → 버림
});
test("orderTotal은 반올림한다 (현재 동작, cartTotal과 다름)", () => {
  expect(orderTotal(items)).toBe(1106);  // 1105.5원 → 반올림
});
```

실행 결과 4개 테스트 모두 통과 — 이게 "지금 코드가 실제로 하는 일"을 정확히 사진 찍은 것입니다.

```
Tests:       4 passed, 4 total
```

**3) IMPROVE — 중복 제거, 단 기존 동작은 그대로 보존**

```ts
function calculateSubtotalWithTax(items): number {
  const subtotal = items.reduce((acc, item) => acc + item.price * item.qty, 0);
  return subtotal * 1.1;
}
export function cartTotal(items) { return Math.floor(calculateSubtotalWithTax(items)); }
export function orderTotal(items) { return Math.round(calculateSubtotalWithTax(items)); }
export function receiptTotal(items) { return Math.floor(calculateSubtotalWithTax(items)); }
```

중복된 "소계+세금" 계산을 공통 함수로 뽑아내고, 반올림 정책(버림/반올림)의 차이만 각 함수에 남겨뒀습니다. 리팩터링 후 PRESERVE 단계의 특성화 테스트를 다시 돌려보니 **4개 모두 그대로 통과**했습니다.

```
Tests:       4 passed, 4 total
```

즉, 코드 중복은 사라졌지만 "겉으로 보이는 동작(반올림 차이 포함)"은 한 치도 변하지 않았다는 걸 테스트로 증명한 것입니다. 이게 바로 DDD가 말하는 "안전한 개선"입니다.

## 8-5. TRUST-5 품질 프레임워크

건물을 다 지으면 반드시 준공 검사(완공 검사)를 거칩니다. 하나라도 기준에 못 미치면 입주할 수 없습니다. **TRUST-5는 코드판 준공 검사**라고 보면 됩니다. AI가 짰든 사람이 직접 짰든 예외 없이 다섯 가지 기준을 통과해야 "구현 완료"로 인정됩니다. TRUST는 다음 다섯 단어의 앞글자를 딴 약어입니다.

1. **Tested(테스트됨)** — 전체 코드의 85% 이상이 테스트로 커버돼야 합니다. 100%를 요구하지 않는 이유는 그 이상부터는 비용 대비 효과가 급격히 떨어지기 때문입니다. 단위 테스트뿐 아니라 LSP(Language Server Protocol, IDE에서 빨간 밑줄로 오류를 표시해 주는 바로 그 시스템)가 보고하는 타입 오류·진단 오류도 0개여야 합니다.
2. **Readable(읽기 쉬움)** — 명명 규칙(변수·함수 이름이 역할을 명확히 드러내야 함, 예: `calc(d, r)` 대신 `calculateDiscountedPrice(originalPrice, discountRate)`)과 린트 오류 0건 기준을 검증합니다.
3. **Unified(통일됨)** — 하나의 프로젝트 안에서 코딩 스타일이 뒤섞여 있으면 가독성이 급격히 떨어집니다. `ruff`/`black`(파이썬), `prettier`(자바스크립트) 같은 자동 포맷터로 스타일을 기계적으로 통일합니다.
4. **Secured(안전함)** — OWASP(Open Web Application Security Project) Top 10 준수가 기본 요건입니다. SQL 인젝션, XSS(크로스사이트 스크립팅), CSRF(크로스사이트 요청 위조) 같은 흔한 보안 취약점을 방지해야 합니다. DB 쿼리는 반드시 파라미터화된 쿼리를 쓰고, 비밀번호는 bcrypt 같은 해시 알고리즘으로 처리하며, API 키를 소스 코드에 하드코딩하는 것은 절대 금지됩니다.
5. **Trackable(추적 가능함)** — 어떤 변경이 왜 이루어졌는지, 누가 승인했는지 명확히 기록해야 합니다. `feat:`, `fix:`, `refactor:`, `security:` 같은 커밋 컨벤션(Conventional Commits) 형식을 요구합니다.

### 직접 확인해 보기 — 테스트 커버리지 측정

위에서 만든 TDD·DDD 실습 코드에 실제로 커버리지 측정을 돌려봤습니다.

```
$ npx jest --coverage

-------------------|---------|----------|---------|---------|
All files          |     100 |      100 |     100 |     100 |

 legacy-pricing.ts  |     100 |      100 |     100 |     100 |
-------------------|---------|----------|---------|---------|

```

TRUST-5가 요구하는 "85% 이상" 기준을 넘어 100% 커버리지를 달성했습니다. 실무에서는 이렇게까지 100%를 고집할 필요는 없지만(책에서도 "100%는 비용 대비 효과가 떨어진다"고 언급), 작은 예제 코드 정도는 전체를 다 테스트하는 게 어렵지 않다는 걸 보여줍니다.

### Loop Engine — 자율 품질 루프

TRUST-5 기준에 미달하는 코드가 발견되면 사람이 일일이 고칠 필요 없이, **Loop Engine**이라는 내부 엔진이 진단 → 수정 → 검증을 자동으로 반복합니다(오픈소스 Ralph Loop에서 영감을 받아 개발). 무한 루프를 방지하기 위해 최대 반복 횟수(기본 100회)를 넘거나, 같은 오류가 5회 연속 반복되면 "교착 상태(Deadlock)"로 판단해 사람에게 개입을 요청합니다.

## 8-6. 에이전트 생태계

MoAI-ADK의 에이전트 구조는 **회사 조직도**와 매우 비슷합니다. MoAI가 최상위 오케스트레이터로서 **CEO** 역할을 하고, 그 아래에 세 부류의 에이전트(총 19개)가 계층적으로 배치됩니다.

### Manager 에이전트 그룹(8개) — "각 부서 팀장"

워크플로의 각 단계를 책임지는 조율자입니다.

| 에이전트 | 역할 | 연결 명령어 |
|---|---|---|
| manager-spec | SPEC 문서 생성(EARS 형식) | `/moai plan` |
| manager-ddd | DDD 구현 | `/moai run` |
| manager-tdd | TDD 구현 | `/moai run` |
| manager-docs | 문서 생성·동기화 | `/moai sync` |
| manager-quality | TRUST-5 품질 검증 | 자동 실행 |
| manager-project | 프로젝트 구성·초기화 | `/moai project` |
| manager-strategy | 시스템 설계, 아키텍처 결정 | 자동 위임 |
| manager-git | Git 브랜칭, PR·머지 전략 | 자동 위임 |

### Expert 에이전트 그룹(8개) — "실무 담당자"

특정 도메인에서 실제 구현 작업을 수행하는 실행자입니다. `expert-backend`(API·서버 로직), `expert-frontend`(UI 컴포넌트), `expert-security`(OWASP 기반 보안 분석), `expert-devops`(CI/CD·배포), `expert-performance`(성능 최적화), `expert-debug`(디버깅), `expert-testing`(테스트 전략), `expert-refactoring`(구조 개선)이 있습니다.

### Builder 에이전트 그룹(3개) — "도구를 만드는 도구"

Manager와 Expert가 소프트웨어를 만든다면, Builder는 **그 소프트웨어를 만드는 도구 자체를 만드는** 메타 에이전트입니다. 새로운 에이전트를 정의하는 `builder-agent`, 새로운 스킬(전문 지식 모듈)을 만드는 `builder-skill`, 여러 요소를 배포 단위로 묶는 `builder-plugin`이 있습니다. 이런 "자기 자신을 확장하는" 구조 덕분에 MoAI-ADK는 고정된 도구가 아니라 계속 성장하는 프레임워크가 됩니다.

### Team 모드 — 수평적 협업

Team 모드는 별도의 에이전트 범주가 아니라, 여러 에이전트가 병렬로 협업하는 **운영 방식**입니다. 평소엔 개발자와 MoAI(중간 관리자)만 대화하고 MoAI가 하위 에이전트에게 일을 위임하는 "하향식 위임" 구조지만, Team 모드에서는 에이전트끼리 직접 소통(SendMessage)하고 병렬로 협업하는 수평적 구조로 바뀝니다.

### 에이전트는 어떻게 자동으로 선택되는가

개발자가 "API를 만들어 줘"라고 하면 자동으로 `expert-backend`가, "이 코드를 리뷰해 줘"라고 하면 `manager-quality`가 호출됩니다. 요청에 담긴 기술 키워드와 작업 성격(읽기 전용 탐색인지, 외부 문서 조사가 필요한지, 특정 도메인 전문성이 필요한지, 여러 도메인에 걸친 복잡한 작업인지)을 분석해 최적의 에이전트를 자동 선택하는 의사결정 트리가 내부에 있습니다.

### 에이전트 정의 파일 구조

모든 에이전트는 `.claude/agents/` 아래에 마크다운 파일로 정의됩니다. 파일 앞부분(프론트매터)에 `name`, `description`(필수), `tools`, `model`, `permissionMode`, `skills` 등 11개 필드로 메타데이터와 권한을 지정하고, 본문은 시스템 프롬프트 역할을 하며 역할 정의, 담당 범위, 위임 규칙, 품질 기준을 담습니다.

## 부록: 실습 코드 실행 방법

`moai-adk-practice/` 폴더에 이 문서에서 다룬 TDD·DDD 실습 코드가 그대로 들어 있습니다. 직접 실행해 보려면:

```bash
cd moai-adk-practice
npm install
npm test              # 전체 테스트 실행
npx jest --coverage    # 커버리지 포함 실행
```

- `src/discount.ts`, `src/discount.test.ts` — TDD(RED-GREEN-REFACTOR) 실습
- `src/legacy-pricing.ts`, `src/legacy-pricing.characterization.test.ts` — DDD(ANALYZE-PRESERVE-IMPROVE) 실습

두 파일 모두 실제로 `npx jest`를 실행해 통과를 확인했으며, 커버리지는 100%입니다.
