# MoAI-ADK 워크플로 (9장) 쉽게 이해하기
---

## 0. 먼저 큰 그림부터: MoAI-ADK가 뭔가요?

**MoAI-ADK**는 Claude Code 위에서 동작하는 "AI 개발 자동화 프레임워크"입니다. 쉽게 비유하면, Claude Code가 "혼자 코딩하는 AI 비서"라면, MoAI-ADK는 여기에 **기획서 작성 → 여러 명의 전문가 배치 → 작업 검수 → 문서 자동화**까지 붙여서, 마치 작은 개발팀을 통째로 운영하는 것과 비슷한 경험을 만들어주는 도구입니다.

이 장(9장)은 그 MoAI-ADK를 실제로 어떻게 쓰는지, 즉 "워크플로(작업 흐름)"를 다룹니다. 핵심은 딱 하나의 사이클입니다.

```
계획(plan) → 구현(run) → 동기화(sync)
```

이 3단계가 계속 반복되면서 하나의 프로젝트가 완성됩니다. 마치 여러분이 React 프로젝트에서 "기능 기획 → 컴포넌트 개발 → 문서/커밋 정리"를 반복하는 것과 똑같은 흐름인데, 이걸 AI 에이전트들이 대신해주는 것이라고 생각하면 됩니다.

---

## 1. 프로젝트 시작 전 준비: `moai project`

무언가를 계획(plan)하기 전에, MoAI-ADK는 먼저 프로젝트를 "이해"해야 합니다. 이때 쓰는 명령어가 `moai project`입니다.

- **신규 프로젝트**라면 `moai init`으로 초기화합니다. 이 과정에서 깃허브/깃랩 계정 연동, 사용할 AI 모델(예: Claude, GLM 등) 선택 같은 마법사(위저드) 단계를 거칩니다.
- **기존 프로젝트**에 MoAI-ADK를 붙이는 경우도 지원합니다. 이때는 `Explore`라는 탐색용 에이전트가 자동으로 코드베이스를 스캔해서, 이 프로젝트가 MVC 구조인지 Clean Architecture인지 등 아키텍처 패턴을 감지하고, `product.md`(제품 설명), `structure.md`(폴더 구조), `tech.md`(기술 스택) 같은 문서를 자동으로 만들어줍니다.

> 💡 비유하자면, 새 팀원이 프로젝트에 합류했을 때 온보딩 문서를 스스로 읽고 요약해서 정리해주는 것과 비슷합니다.

## 2. 핵심 워크플로: `plan → run → sync`

이 장에서 가장 중요한 부분입니다. 세 단계를 하나씩 뜯어보겠습니다.

### 2-1. `/moai plan` — 기획 단계 (SPEC 문서 만들기)

코드를 짜기 전에 먼저 **SPEC(명세서)**를 만드는 단계입니다. "이 기능이 무엇을 해야 하는지"를 사람과 AI가 같이 합의하는 문서라고 보면 됩니다.

- `manager-spec`이라는 관리자 에이전트가 사용자와 대화하며 요구사항을 정리합니다.
- 요구사항은 **EARS 문법**이라는 정형화된 형식으로 작성됩니다. (예: "시스템은 ~할 때 ~해야 한다"처럼 애매하지 않게 쓰는 규칙입니다.)
- SPEC에는 ID(예: `SPEC-AUTH-001`), 요구사항, 수용 기준(acceptance criteria), Given-When-Then 형식의 시나리오 등이 담긴 `spec.md`, `plan.md`, `acceptance.md` 파일들이 생성됩니다.
- `--worktree`, `--branch` 같은 옵션을 붙이면, 이 SPEC 작업을 위한 독립적인 Git 작업 공간(worktree)이나 브랜치를 자동으로 만들어줍니다. (worktree는 뒤 7번 항목에서 자세히 설명합니다.)

> React 개발로 비유하면, 새 기능을 만들기 전에 Jira 티켓/기획 문서를 AI와 함께 미리 정리해두는 단계입니다.

### 2-2. `/moai run` — 구현 단계 (TDD/DDD로 코드 짜기)

SPEC 문서를 기반으로 실제 코드를 구현하는 단계입니다. 특징은 **TDD(테스트 주도 개발)**와 **DDD(도메인 주도 설계)** 방식을 함께 씁니다.

구현은 `ANALYZE → PRESERVE → IMPROVE` 라는 8단계 사이클로 진행됩니다. 풀어서 설명하면:

1. **ANALYZE(분석)**: 기존 코드와 요구사항을 분석
2. **PRESERVE(보존)**: 기존에 잘 동작하는 부분은 건드리지 않고 지키기
3. **IMPROVE(개선)**: 필요한 부분만 테스트를 먼저 작성하고, 그 테스트를 통과하도록 코드를 개선(TDD 사이클)

이 과정에서 `manager-strategy`, `manager-ddd` 같은 에이전트들이 투입되어 계획을 세우고 실제 구현 전략을 짭니다.

### 2-3. `/moai sync` — 동기화 단계 (코드·SPEC·문서 맞추기)

구현이 끝나면 코드, SPEC 문서, README/CHANGELOG 같은 프로젝트 문서 사이에 **불일치가 없는지** 확인하고 자동으로 맞춰주는 단계입니다.

- Conventional Commits 형식으로 커밋을 정리
- Git 브랜치를 동기화, 원격 저장소에 push
- README, CHANGELOG를 자동 갱신 (Keep a Changelog 형식)
- SPEC 상태를 `ACTIVE`(진행 중) → `COMPLETED`(완료)로 갱신
- PR(Pull Request)을 자동 생성

> 정리하면 "코드 다 짰는데 문서는 예전 그대로"인 상황을 막아주는 단계입니다.

### 2-4. 세 단계 사이의 "전환 조건"

각 단계에서 다음 단계로 넘어가려면 정해진 조건을 통과해야 합니다.

| 전환 | 조건 요약 |
|---|---|
| plan → run | SPEC 승인 완료 (`DRAFT` → `ACTIVE`), 필수 항목(요구사항, 수용 기준) 작성 완료 |
| run → sync | 테스트 커버리지 85% 이상, TRUST-5 품질 게이트 통과, Critical 이슈 없음 |
| sync → Complete | 문서·코드·SPEC 정합성 검증 통과, PR 생성 완료 |

이 조건들이 자동으로 체크되기 때문에, "테스트도 안 짰는데 다음 단계로 넘어가는" 실수를 방지해줍니다.

### 2-5. plan-run-sync 자동화 모드

매번 `/moai plan`, `/moai run`, `/moai sync`를 수동으로 입력하지 않아도, `/moai "기능 이름"` 형태로 한 번에 요청하면 3단계가 자동으로 이어서 실행되는 모드도 있습니다. 아래처럼 세부 옵션도 지원합니다.

- `--branch`: 단계마다 자동으로 Git 브랜치 생성
- `--solo`: 단일 에이전트로 순차 처리 (기본값에 가까움)
- `--team`: 에이전트 팀을 구성해 병렬로 처리 (아래 3장 참고)
- `--max N`: 최대 N개 SPEC까지 자동 반복 처리
- `--loop`: 문제가 있으면 자동으로 다시 시도

## 3. 서브에이전트와 에이전트 팀

### 3-1. Agent 도구 기본 사용법

MoAI-ADK는 Claude Code의 `Agent` 도구(서브에이전트를 부르는 기능)를 적극 활용합니다. 서브에이전트를 부를 때 지정하는 주요 값들:

- `subagent_type`: 어떤 종류의 에이전트인지 (예: `claude/agents/` 디렉터리에 정의된 에이전트)
- `prompt`: 에이전트에게 시킬 작업 지시문
- `model`: 사용할 모델 (`haiku`처럼 빠르고 저렴한 모델, `sonnet`/`opus`처럼 더 똑똑한 모델 등 작업 난이도에 맞게 선택)
- `run_in_background`: 백그라운드 실행 여부
- `max_turns`: 에이전트가 최대 몇 번 주고받을 수 있는지 제한
- `inherit`: 상위 에이전트의 컨텍스트(대화 맥락)를 물려받을지 여부

### 3-2. 왜 여러 에이전트를 쓰나요?

하나의 AI가 기획, 백엔드, 프론트엔드, 테스트를 전부 순서대로 처리하면 느리고, 전문성도 떨어질 수 있습니다. MoAI-ADK는 아래처럼 **역할을 나눠 병렬로** 일하게 합니다.

- `expert-backend`: API 설계·구현 (예: FastAPI 기반 JWT 인증 API)
- `expert-frontend`: UI 구현 (예: React + shadcn/ui 컴포넌트)
- `expert-testing`: 테스트 코드 작성 (단위 테스트, 통합 테스트 등)

이 에이전트들은 각자 다른 파일(백엔드 라우트/모델, 프론트 컴포넌트/페이지, 테스트 파일)을 동시에 건드리기 때문에 충돌 없이 병렬 작업이 가능합니다.

### 3-3. 에이전트 간 소통: `SendMessage`

에이전트들끼리는 `SendMessage`라는 도구로 메시지를 주고받습니다. 예를 들어 백엔드 에이전트가 "API 엔드포인트 구현 완료"라고 프론트엔드 에이전트에게 알려주면, 프론트엔드 에이전트가 그 시점부터 연동 작업을 시작하는 식입니다. 이런 소통 패턴을 책에서는 **Collect-Then-Delegate**(먼저 정보를 모으고, 그다음 위임한다) 패턴이라고 부릅니다.

### 3-4. "서브에이전트"와 "에이전트 팀"의 차이

| 구분 | 서브에이전트 | 에이전트 팀 |
|---|---|---|
| 규모 | 가볍고 빠른 위임 (1회성 작업) | 여러 역할이 장기간 협업 |
| 적합한 상황 | 간단한 조사, 단일 작업 | 복잡한 기능, 여러 파일 동시 작업 |
| 관리 도구 | `Agent` 도구 | `TeamCreate`, `TaskCreate` 등 |

### 3-5. 에이전트 팀 활성화하기

팀 모드는 기본으로 꺼져 있고, 아래처럼 켜야 합니다.

1. `.claude/settings.json`에 실험적 기능 플래그 추가: `"CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"`
2. `.moai/config/sections/workflow.yaml`에서 `team.enabled: true` 설정

실행 모드(Claude / GLM / 하이브리드)와 팀 모드를 조합할 수 있는데, 대표 조합은 다음과 같습니다.

| 명령어 | 리더 모델 | 워커 모델 | 특징 |
|---|---|---|---|
| `moai cc` | Claude | Claude | 표준 조합 |
| `moai glm` | GLM | GLM | 비용 절감형 |
| `moai cg` | Claude | GLM | 리더는 품질, 워커는 비용 절감 |

팀을 화면에 표시하는 방식도 두 가지가 있습니다: **in-process**(같은 프로세스 안에서 조용히 실행) vs **tmux**(터미널 창을 여러 개 분할해서 각 에이전트 작업을 실시간으로 보여주는 방식, `tmux`가 컴퓨터에 설치되어 있어야 함).

### 3-6. 역할 프로필(role_profiles)

팀의 각 역할(researcher, analyst, architect 등)마다 사용할 모델과 권한 수준을 미리 정의해둘 수 있습니다.

```yaml
team:
  role_profiles:
    researcher: { mode: plan, model: haiku, isolation: none }
    analyst:    { mode: plan, model: sonnet, isolation: none }
    architect:  { mode: plan, model: sonnet, isolation: none }
```

- `mode`: `plan`(계획만 세우고 편집은 못 함, 읽기 위주), `acceptEdits`(편집 자동 승인) 등
- `model`: 역할 난이도에 맞는 모델 선택 (단순 조사는 `haiku`처럼 가벼운 모델로 비용 절감)
- `isolation`: `worktree`(독립 작업 공간에서 작업, 충돌 방지) 또는 `none`

### 3-7. 팀이 만들어지는 3단계

1. **팀 생성**: `TeamCreate(team_name: "plan-auth-001")`
2. **역할 배정**: `role_profiles`를 참고해 각 역할에 맞는 Agent를 팀원으로 소환
3. **작업 분배**: `TeamCreate`, `TaskCreate`로 실제 작업(Task)을 팀원들에게 나눠줌

작업이 끝나면 `shutdown_request`로 팀을 정리(해산)합니다.

### 3-8. plan 단계 팀 구성 예시

- `moai-team-researcher`: 관련 자료·기존 패턴 조사 (모델: haiku, 저렴하고 빠르게)
- `moai-team-analyst`: 요구사항 정리, EARS 문법 적용
- `moai-team-architect`: 파일 구조·아키텍처 설계

이 세 역할이 동시에 다른 관점에서 조사하고, 최종적으로 하나의 SPEC 문서로 합쳐집니다.

### 3-9. run 단계 팀 구성 예시

- `moai-team-backend-dev`, `moai-team-frontend-dev`, `moai-team-tester`, `moai-team-designer` 등이 각자 담당 파일 영역(백엔드는 서버 코드, 프론트는 컴포넌트, 테스터는 테스트 파일)에서 동시에 작업합니다.
- 팀 전체 품질은 `TRUST-5` 기준으로 검증됩니다 (뒤에서 다시 언급되는 품질 게이트 개념).

### 3-10. 격리(isolation) 규칙

여러 에이전트가 같은 파일을 동시에 건드리면 충돌이 나므로, 역할에 따라 격리 규칙이 다릅니다.

| 에이전트 유형 | isolation 값 | 의미 |
|---|---|---|
| team-backend-dev, team-frontend-dev 등 편집 담당 | `worktree` (필수) | 반드시 독립된 작업 공간에서 작업 |
| team-researcher, team-analyst 등 읽기 전용 | `worktree` 사용 금지 (권장) | 굳이 격리할 필요 없음, 가볍게 실행 |

## 4. 스킬(Skill) 생태계

**스킬**은 MoAI-ADK가 특정 작업을 더 잘 수행하도록 도와주는 "지식/도구 묶음"입니다. 이름 규칙은 `moai-{category}-{name}` 형태이고, 9개 카테고리(예: foundation, framework, tool, library, platform, language, domain, workflow, design)에 걸쳐 총 48개의 대표 스킬이 소개됩니다.

각 스킬은 YAML 형식의 "설명서"(front matter)를 가지고 있습니다. 대표 항목:

- `name`, `description`: 스킬 이름과 설명
- `allowed-tools`: 이 스킬이 사용할 수 있는 도구 목록 (예: Read, Grep, Glob, Bash)
- `compatibility`: 호환되는 언어/프레임워크 버전 (예: Python 3.13+)
- `disclosure`: 정보를 얼마나 자세히 보여줄지 단계 (`progressive` 등)
- `triggers`: 이 스킬이 언제 자동으로 발동될지 조건 (키워드, 언어, 실행 단계 등)

예를 들어 `moai-lang-python` 스킬은 `"fastapi"`, `"django"`, `"pytest"` 같은 키워드가 등장하면 자동으로 트리거됩니다.

### 4-1. 트리거 시스템: 자동 호출 원리

스킬이 1단계에서 발동될 확률은 대략 100토큰당 1개 스킬 사용 정도로 설계되어 있고, 트리거 조건은 크게 두 가지 방식으로 판단됩니다.

- **keywords**: 사용자 요청 문장에 특정 단어가 있는지 (예: `"api"`, `"database"`, `"authentication"`)
- **languages/phases**: 어떤 프로그래밍 언어를 다루는지, 어떤 워크플로 단계(`plan`, `run` 등)인지

여러 조건이 동시에 맞으면(AND) 또는 하나만 맞아도(OR) 트리거되도록 설정할 수 있습니다.

### 4-2. 스킬과 에이전트의 관계

에이전트가 특정 스킬을 명시적으로 사용하도록 지정할 수도 있고(`skills` 필드), 스킬 자체가 여러 에이전트에서 공용으로 재사용되기도 합니다.

## 5. 빌더 에이전트 & 빌더 스킬: 나만의 도구 만들기

기본 제공되는 에이전트/스킬만으로 부족하다면, 직접 커스텀 에이전트나 스킬을 만들 수 있습니다.

### 5-1. `builder-agent`: 커스텀 에이전트 생성

대화를 통해 새 에이전트를 만들어주는 전용 에이전트입니다. "보안 감사만 전담하는 에이전트를 만들어줘" 같은 요청을 하면, `.claude/agents/` 디렉터리에 YAML 형식의 에이전트 정의 파일을 생성해줍니다.

필수 구성 요소:

```yaml
name: my-security-audit
description: >
  보안 취약점 감사 전문가. OWASP Top 10 기준으로 코드를 점검하고
  취약점 보고서를 생성한다. 보안 감사, 취약점 분석, 코드 리뷰 요청 시 사용.
tools: Read, Grep, Glob, Bash
model: sonnet
permissionMode: plan
skills:
  - moai-foundation-quality
  - moai-domain-backend
```

- `name`은 소문자-하이픈(kebab-case) 형식
- `description`은 "언제 이 에이전트가 사용되어야 하는지"를 명확히 서술해야 자동 호출 정확도가 올라감
- `tools`는 이 에이전트가 쓸 수 있는 도구 최소 권한만 부여 (예: 보안 감사 에이전트는 코드 수정 권한 없이 Read/Grep만 부여)

### 5-2. `builder-skill`: 커스텀 스킬 생성

마찬가지로 대화형으로 새 스킬을 만들어줍니다. 이름은 `agentskills.io` 표준을 따르고, `name`/`description`은 최대 글자 수 제한(예: name 64자, description 1024자)이 있습니다.

## 6. 훅(Hook)과 MCP 통합

### 6-1. 훅이란?

**훅**은 Claude Code가 특정 이벤트(예: 도구 실행 직전/직후, 세션 시작/종료)를 만났을 때 자동으로 실행되는 셸 스크립트입니다. 총 14가지 정도의 이벤트가 있으며, 대표적으로:

- `SessionStart`: 세션이 시작될 때 (예: 프로젝트 상태 표시, 환경 점검)
- `PreToolUse`: 도구를 실행하기 직전 (예: 위험한 명령어 차단)
- `PostToolUse`: 도구 실행 직후 (예: 코드 포맷팅 자동 적용, AST-grep으로 스타일 검사)
- `Stop` / `SessionEnd`: 작업 중단 시 임시 파일 정리, 세션 종료 시 상태 저장

훅 스크립트는 `.claude/hooks/moai/` 디렉터리에 위치합니다.

### 6-2. 훅으로 무엇을 자동화하나요?

예를 들어 `expert-backend` 에이전트가 파일을 수정(`Write`, `Edit`)하려고 할 때 `PreToolUse` 훅이 끼어들어 위험한 명령어(`rm -rf`, `git push --force` 등)를 사전에 차단하거나, SSH 키 같은 민감한 파일 수정을 막을 수 있습니다.

훅은 JSON으로 구조화된 입력(도구 이름, 입력값, 실행 결과 등)을 받고, `permissionDecision`(허용/거부/확인) 값을 반환해서 도구 실행을 제어할 수 있습니다.

### 6-3. MCP(Model Context Protocol) 통합

**MCP**는 Claude가 외부 도구/서비스와 연결되는 표준 프로토콜입니다. MoAI-ADK는 다음과 같은 MCP 서버들을 기본 활용합니다.

- **Context7**: 라이브러리의 최신 공식 문서를 실시간으로 조회 (예: "next.js"로 검색 → 최신 App Router 문서 반영). 오래된 학습 데이터에 의존하지 않고 최신 버전 정보를 반영할 수 있게 해줍니다.
- **Sequential Thinking**: 복잡한 문제를 단계적으로 분해해서 풀어나가는 사고 과정을 명시적으로 만들어주는 MCP
- **Pencil MCP**: UI/UX 디자인 관련 도구 (Figma, 아이콘 생성 등과 연동)
- **Claude in Chrome MCP**: 브라우저를 직접 조작해서 웹 페이지 스크린샷, 폼 입력, 네비게이션 등을 수행

## 7. 작업 트리(Worktree): 여러 SPEC 병렬 개발

**Git worktree**는 하나의 저장소(repository)에서 여러 개의 독립적인 작업 폴더를 동시에 유지할 수 있게 해주는 Git 기능입니다. MoAI-ADK는 이를 활용해 여러 SPEC(기능)을 동시에, 서로 충돌 없이 개발할 수 있게 합니다.

```
Main Worktree (main 브랜치)
 ├─ Worktree 1: feature/SPEC-AUTH-001
 ├─ Worktree 2: feature/SPEC-LOG-002
 └─ Worktree 3: feature/SPEC-API-003
```

각 worktree는 독립된 작업 폴더라서, 한쪽에서 `git stash`를 쓸 필요 없이 여러 기능을 병렬로 작업하다가 자유롭게 오갈 수 있습니다.

### 7-1. `moai wt` 명령어 모음

| 명령어 | 용도 |
|---|---|
| `moai wt new SPEC-AUTH-001` | 새 작업 트리 생성 |
| `moai wt list` | 전체 작업 트리 목록 표시 |
| `moai wt switch <branch>` | 작업 트리 간 전환 |
| `moai wt go <branch>` | 해당 작업 트리 폴더로 이동 (`cd`) |
| `moai wt sync` | main 브랜치 최신 내용을 현재 작업 트리에 반영 |
| `moai wt done <branch>` | 작업 완료 처리 (병합 준비) |
| `moai wt remove <branch>` | 작업 트리 제거 |
| `moai wt clean` | 완료된 작업 트리 일괄 정리 |
| `moai wt recover <branch>` | 손상된 작업 트리 복구 |
| `moai wt status` | 전체 작업 트리 상태 확인 |
| `moai wt config` | 작업 트리 설정 관리 |

### 7-2. 병렬 SPEC 개발 패턴

여러 개의 독립적인 SPEC(예: `SPEC-AUTH-001`, `SPEC-LOG-002`, `SPEC-API-003`)을 각각 다른 터미널 창에서 동시에 `plan → run` 시키고, 완료되면 `moai wt done`으로 병합하는 식으로 작업합니다. 각 SPEC이 소모하는 리소스(예: `node_modules`, 가상환경)가 겹치지 않는다면 문제없이 병렬 진행이 가능합니다.

## 8. 즉시 명령어와 CLI 유틸리티

plan-run-sync라는 큰 흐름 외에도, MoAI-ADK는 일상적으로 자주 쓰는 짧은 명령어들을 제공합니다.

- **`/moai fix`**: 일회성 즉시 수정. 예를 들어 `import` 문 하나가 빠졌거나 스타일이 깨졌을 때, 전체 워크플로를 돌리지 않고 빠르게 고치는 용도. Linter/AST-grep으로 문제를 스캔 → 문제 발견 시 자동 수정 → 재검증하는 4단계 루프로 동작
- **`/moai loop`**: 문제가 해결될 때까지 자동으로 반복 시도 (`--max N`, `--dry-run`, `--level 1~4`, `--security` 등 옵션으로 강도 조절)
- **`/moai feedback`**: AI가 제안한 수정에 대해 사용자가 승인/반려하는 흐름
- **`moai statusline`**: 클로드 코드 하단 상태 표시줄에 현재 활성 에이전트, 작업 진행 상태, SPEC ID, 품질 게이트 상태 등을 실시간으로 표시
- **`moai init`**: 새 프로젝트 초기화
- **`moai update`**: MoAI-ADK 프레임워크를 최신 버전으로 업데이트 (`--templates-only` 옵션으로 템플릿 파일만 동기화 가능)
- **`moai cc` / `moai glm` / `moai cg`**: 각각 Claude 단독, GLM 단독, Claude(리더)+GLM(워커) 하이브리드 모드로 실행
- **`moai rank`**: (품질/기여도 등에 대한) 순위 관련 유틸리티

## 9. 전체 흐름 한눈에 정리

```
1) moai init / moai project
   → 프로젝트 분석 및 문서(product.md, structure.md, tech.md) 생성

2) /moai plan "기능 이름"
   → SPEC 문서(spec.md, plan.md, acceptance.md) 생성 (EARS 문법)
   → 필요 시 --team 옵션으로 researcher/analyst/architect 팀 병렬 조사

3) /moai run
   → TDD/DDD 기반 8단계(ANALYZE-PRESERVE-IMPROVE) 구현
   → 필요 시 --team 옵션으로 backend/frontend/tester 등 병렬 구현
   → 테스트 커버리지 85%+, TRUST-5 통과해야 다음 단계 진행 가능

4) /moai sync
   → 코드/SPEC/문서 정합성 확인, 커밋/브랜치 동기화, PR 자동 생성

(이 모든 과정에서)
- 훅(Hook)이 위험한 작업을 자동 차단하거나 후처리를 자동화
- MCP(Context7, Sequential Thinking 등)로 최신 정보·복잡한 추론 보강
- 스킬(Skill)이 특정 언어/프레임워크/도메인 지식을 자동으로 주입
- worktree로 여러 SPEC을 동시에 병렬 개발
```

## 10. 헷갈리기 쉬운 용어 미니 사전

| 용어 | 쉬운 설명 |
|---|---|
| SPEC | "이 기능이 뭘 해야 하는지" 정리한 명세 문서 (기획서 같은 것) |
| EARS 문법 | 요구사항을 애매하지 않게 쓰는 표준 문장 형식 |
| TDD | 테스트를 먼저 쓰고, 그 테스트를 통과하도록 코드를 짜는 개발 방식 |
| DDD | 비즈니스 도메인(핵심 개념/규칙) 중심으로 설계하는 방식 |
| 서브에이전트 | 잠깐 불려서 한 가지 작업만 하고 사라지는 가벼운 AI 일꾼 |
| 에이전트 팀 | 여러 역할의 에이전트가 오래 협업하는 조직 단위 |
| worktree | 하나의 Git 저장소에서 여러 작업 폴더를 동시에 쓰는 기능 |
| 훅(Hook) | 특정 시점(도구 실행 전/후 등)에 자동 실행되는 스크립트 |
| MCP | Claude가 외부 도구/서비스와 연결되는 표준 규격 |
| 스킬(Skill) | 특정 분야 지식/노하우를 담아 AI에게 자동으로 제공하는 지식 패키지 |
| TRUST-5 | 코드 품질을 검증하는 5가지 기준 게이트 (책의 앞부분 챕터에서 자세히 다뤄질 가능성이 높습니다) |
