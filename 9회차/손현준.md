## 1. plan-run-sync 핵심 파이프라인과 자율 자동화

MoAI-ADK의 핵심은 단순 대화형 코딩의 한계인 맥락 유실과 기존 코드 파괴를 방지하기 위해 **계획(Plan) - 구현(Run) - 동기화(Sync)**의 3단계 전환 게이트를 강제하는 파이프라인입니다.

*   **준비 단계 (`/moai project`)**: AI가 프로젝트의 전반적인 기술 스택과 아키텍처 구조를 완벽하게 인지하도록 돕는 3대 문서(`product.md`, `structure.md`, `tech.md`)를 `.moai/project/` 경로에 동적으로 생성합니다.
*   **1단계: plan (`/moai plan "기능"`)**: 자연어로 구성된 사용자의 요구 사항을 **EARS(Easy Approach to Requirements Syntax) 표준 구문**으로 변환하여 체계적인 설계도인 `spec.md`, `plan.md`, `acceptance.md`를 구성합니다.
*   **2단계: run (`/moai run SPEC-XXX`)**: 이진 방법론(신규는 TDD, 기존 레거시는 DDD)을 통해 최소 단위의 테스트 케이스를 우선 충족시키는 점진적 개발을 수행하며 코드를 완성합니다.
*   **3단계: sync (`/moai sync SPEC-XXX`)**: 구현 완료 후 변경된 코드 구조를 분석하여 API 문서 및 README를 자동 갱신하고, SPEC 상태를 완료로 전환하며 깃 커밋(Conventional Commits)과 PR을 안전하게 생성합니다.
*   **자율 자동화 모드 (`/moai "구현 기능" --loop`)**: 이 3단계 과정을 하나의 프롬프트로 완전 자동 실행하며, 빌드 테스트 오류나 커버리지 부족 감지 시 100회까지 스스로 진단 및 수정을 수행합니다.

### 단계 전환 조건 (품질 게이트)
1.  **Plan ➔ Run**: 사용자의 서명 및 승인을 통해 SPEC의 상태가 `DRAFT`에서 `ACTIVE`로 격상되어야만 코딩이 시작됩니다.
2.  **Run ➔ Sync**: 모든 빌드가 성공하고 **테스트 커버리지가 85% 이상**을 상회하며 TRUST-5 품질 기준을 충족해야만 동기화 단계 진입이 허용됩니다.
3.  **Sync ➔ Complete**: 문서 일관성 검사 및 정적 분석(LSP)에 에러가 전혀 없어야 최종 릴리스 상태로 처리됩니다.

## 2. 에이전트 팀 기반 병렬 협업 아키텍처

서브에이전트가 단발성 일회용 호출 패턴이라면, 에이전트 팀(Agent Teams)은 여러 AI 에이전트가 하나의 공유 작업 목록을 관리하고 실시간으로 통신하는 **지속성(Persistent) 협업 모델**입니다.

*   **동적 역할 프로파일**: 하드코딩된 마크다운 대신 `.moai/config/sections/workflow.yaml`에 선언된 역할군을 기반으로 스펙 설계 단계에는 `plan_research` 패턴을, 실제 코딩 시에는 `implementation` 패턴을 유동적으로 조직하여 에이전트를 동적으로 스폰(Spawn)합니다.
*   **최소 권한의 원칙**: 분석 역할(analyst, reviewer 등)은 파일 수정이 아예 차단되는 `plan(읽기 전용)` 모드로 실행하고, 구현 역할(implementer, tester)에게만 `acceptEdits` 수정 권한을 부여해 코드의 안정성을 확보합니다.
*   **파일 소유권(File Ownership) 분리**: 다중 에이전트가 동일한 파일에 동시 접근하여 덮어쓰는 충돌을 원천적으로 제어하기 위해, `backend-dev`는 서버 파일을, `tester`는 테스트 폴더만을 단독 소유하여 수정 권한을 격리합니다.

```yaml
# workflow.yaml 파일 내의 역할 프로파일 예시
team:
  role_profiles:
    researcher: { mode: plan, model: haiku, isolation: none }
    analyst:    { mode: plan, model: sonnet, isolation: none }
    implementer:{ mode: acceptEdits, model: sonnet, isolation: worktree }
    tester:     { mode: acceptEdits, model: sonnet, isolation: worktree }
    reviewer:   { mode: plan, model: haiku, isolation: none }
```

## 3. 스킬 생태계와 점진적 공개(Progressive Disclosure) 시스템

MoAI-ADK는 총 48개 이상의 도메인 스킬을 핵심 철학(Foundation), 개발 흐름(Workflow), 프로그래밍 언어(Language), 도메인(Domain) 등 9대 카테고리로 체계화하여 활용합니다.

*   **3단계 점진적 공개(Progressive Disclosure) 구조**:
    1.  **1단계 (메타데이터, ~100토큰)**: 세션 시작 시 스킬의 설명과 이름만 노출해 탐색 오버헤드를 줄입니다.
    2.  **2단계 (본문 가이드, ~5,000토큰)**: 스킬이 활성화되면 실질적인 지침과 설계 원칙을 담은 `SKILL.md`를 셸(Bash)로 로드합니다.
    3.  **3단계 (번들 리소스, 가변적)**: 대규모 API 명세나 템플릿 코드 등 무거운 외부 참조는 에이전트가 탐색 중 명시적으로 요구할 때만 동적으로 추가 로드하여 메인 컨텍스트의 여유 공간을 90% 이상 세이브합니다.
*   **다중 트리거 시스템**: 스킬 프론트매터의 `triggers` 필드를 사용하여 사용자 메시지 속 키워드 감지(`keywords`), 특정 에이전트 호출(`agents`), 현재 파이프라인 단계(`phases`), 다루고 있는 파일의 확장자(`languages`)에 맞춰 해당 지식 모듈을 컨텍스트에 자동 주입합니다.

## 4. 빌더 도구(builder-agent / builder-skill)를 활용한 커스텀 설계

기본 탑재된 범용 지식 외에 프로젝트 고유 규칙을 반영한 AI 에이전트 조직 및 도메인 교과서를 직접 제작할 수 있는 메타 에이전트를 지원합니다.

*   **`builder-agent`**: 대화형 인터페이스를 통해 역할, 보안 경계(In-Scope / Out-of-Scope), 허용할 도구 목록을 설정하여 커스텀 서브에이전트 정의 마크다운 파일을 생성합니다.
*   **`builder-skill`**: 에이전트 스킬 오픈 표준(agentskills.io) 및 MoAI-ADK의 점진적 공개 스펙에 맞춰 규칙을 구조화한 도메인 스킬 패키지를 제작합니다.

다음은 빌더 에이전트를 통해 생성될 수 있는 **읽기 전용 보안 검사 커스텀 에이전트 정의 파일의 구조적 예시**입니다.

```markdown
# 파일 경로: .claude/agents/my-security-audit.md
---
name: my-security-audit
description: OWASP Top 10 기준의 정적 소스 코드 보안 검사 전담 에이전트
tools: Read, Grep, Glob, Bash
model: sonnet
permissionMode: plan
maxTurns: 30
skills:
  - moai-foundation-quality
  - moai-domain-backend
---

당신은 보안 취약점 검사 전문가입니다.

## 핵심 임무
코드베이스를 분석하여 SQL 인젝션, XSS, 민감 정보 하드코딩 노출 여부를 식별하고 보고합니다.

## 분석 경계
- IN SCOPE: 정적 코드 분석, 취약점 탐지, 권장 수정 패턴 제안
- OUT OF SCOPE: 직접적인 코드 수정 작업 (수정이 필요하면 expert-security를 위임 호출할 것)
```

## 5. 훅(Hooks) 시스템과 MCP 통합 시너지

MoAI-ADK는 결정론적인 이벤트 반응 도구인 훅(Hooks)과 실시간 외부 인프라 통신 도구인 MCP를 결합해 완전하고 신뢰성 높은 작업 처리를 보장합니다.

*   **생애 주기 훅 체계**:
    *   `SessionStart`: 세션 진입 시 Git 상태와 미결 태스크 보드를 실시간 대시보드로 갱신합니다.
    *   `PreToolUse`: 위험한 Bash 명령 및 민감한 설정 파일(`.env`, `.git/`) 수정을 사전에 감지하여 차단(Exit Code 1)하는 보안 방어선 역할을 합니다.
    *   `PostToolUse`: 파일이 생성되거나 수정되면 AI의 개입 판단과 무관하게 포맷터, 린터, AST-grep 보안 스캔, LSP 정밀 진단을 물리적으로 강제 구동합니다.
*   **MCP 확장 연동**:
    *   `Context7`: resolve-library-id와 get-library-docs 2단계 조회를 거쳐 학습 데이터 바깥에 있는 React 19, Next.js 최신 등의 공식 라이브러리 문서를 실시간 참조합니다.
    *   `Sequential Thinking`: `--deepthink` 활성화 시 아키텍처 트레이드오프나 데이터베이스 설계 변경 등 다차원적 고민이 수반되는 결론 도출을 단계별로 나누어 구조적으로 숙고합니다.

## 6. 깃 작업 트리(Git Worktree) 기반 병렬 SPEC 개발

단일 작업 디렉토리에서 브랜치를 널뛰기하며 작업할 때의 컨텍스트 스위칭 비용(Stash, Commit 전환)을 완전히 제거하기 위해 MoAI-ADK는 **Git Worktree**를 내장 관리 도구로 활용합니다.

*   **물리적 격리 개발**: 동일한 하나의 `.git` 저장소를 기반으로 두고, 다중 SPEC 마일스톤에 매핑된 독립적인 작업 경로를 외부에 동시에 펼쳐놓습니다.
*   **병렬 파이프라인 형성**: 터미널 1에서 `JWT 인증(SPEC-001)` 명세 분석을 마친 후 `--worktree` 플래그로 격리된 디렉토리를 생성하면, 해당 경로의 독립적인 node_modules나 컴파일 가상 환경에서 메인 브랜치 오염 없이 백엔드/프런트엔드 각각의 서브에이전트가 동시에 빌드 및 실시간 구현을 마칠 수 있습니다.
*   **에이전트 격리 원칙 (HARD Rule)**:
    *   **구현 에이전트** (`team-backend-dev`, `team-tester` 등): 동시 쓰기 충돌 및 Git 인덱스 파괴 방지를 위해 반드시 `isolation: worktree` 설정을 강제 준수해야 합니다.
    *   **읽기 전용 에이전트** (`team-researcher`, `team-quality` 등): 무분별한 격리 디렉토리 생성으로 인한 패키지 설치 오버헤드를 아끼기 위해 절대 작업 트리를 생성해서는 안 됩니다.

```bash
# 깃 작업 트리 핵심 유틸리티 명령어 패턴
\$ moai wt new SPEC-AUTH-001               # 새 작업 트리 디렉토리 및 브랜치 자동 초기화
\\( cd \\)(moai wt go feature/SPEC-AUTH-001)  # 해당 작업 격리 공간으로 즉시 디렉토리 이동
\$ moai wt sync                            # main 브랜치의 최신 빌드 변경 사항을 실시간 반영
\$ moai wt done feature/SPEC-AUTH-001 -d   # 병합 완료 후 작업 트리 삭제 및 로컬 브랜치 일괄 정리
```

## 7. 자동 검증 및 복구 명령어 (/moai fix & /moai loop)

TDD/DDD 사이클 진행 중 축적되는 자질구레한 타입 에러, 테스트 실패, 레거시 시스템 구조 변경 등으로 인한 사이클 중단을 자동화 루프로 자체 진단하고 수정하는 내부 핵심 유틸리티입니다.

### /moai fix (단발성 신속 보수)
스캔 과정에서 LSP, AST-grep, 린터를 병렬 실행하여 문제를 탐지한 후, 위험 수준에 따라 4단계로 체계화해 처리합니다.
*   `1레벨 (포매팅)`: 후행 공백, 임포트 순서 등 코드 동작에 무해한 규칙으로 즉각 자동 반영합니다.
*   `2레벨 (린트 경고)`: 미사용 변수 등을 수정하며 작업 로그를 축적합니다.
*   `3레벨 (로직 에러)`: 분기 처리 누락 등 로직 변경 위험이 있는 부분으로 사용자 동의 후 반영합니다.
*   `4레벨 (보안 취약점)`: 취약점 발견 시 수정안과 함께 안전을 위한 사용자 수동 검토를 강제 권장합니다.

### /moai loop (자율 루프 보증 엔진)
테스트 통과, LSP 에러 0개, 커버리지 85% 이상의 3대 완료 조건이 모두 달성될 때까지 진단 ➔ 수정 에이전트 자동 배정 ➔ 빌드 재검증 과정을 백그라운드 반복 수행합니다. 5회 연속 진행 성과가 없거나 100회 상한을 초과하면 무한 루프 탈출 안전장치가 동작하여 분석 데이터를 화면에 출력하고 사용자 개입을 요청합니다.
