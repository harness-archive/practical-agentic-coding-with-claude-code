# MoAI-ADK 워크플로

### /moai project: 프로젝트 문서 생성
- MoAI-ADK의 코드베이스를 분석하여, AI가 프로젝트를 이해하는 데 필요한 기초 문서를 자동으로 생성한다. 
- 새로운 대화 세션마다 클로드는 프로젝트 정보를 초기화한 상태에서 출발하기 때문에, 이 문서들이 없으면 /moai plan이나 /moai run 단계에서 AI가 기술 스택과 코드구조를 모른채 부정확한 판단을 내릴 수 있다.

## 9-1 plan-run-sync 핵심 워크플로
- MOAI-ADK의 워크플로는 세 단계로 구선된다. 
- plan단계에서 요구사항을 구조화된 명세서로 변환하고, run 단계에서 그 명세서를 기반으로 안전하게 코드를 구현하며, sync 단계에서 코드와 명세서, 프로젝트 문서간의 일관성을 검증하고 동기화 한다. 

### 1) /moai plan: 명세서 생성
- 자연어 요청을 EARS형식의 구조화된 SPEC 문서로 변환하는 과정으로 바이브 코딩의 문제점 중 맥락 유실을 해결한다. 
- 생성된 SPEC 문서는 .moai/specs/SPEC-XXXX/ 디렉터리에 spec.md, plan.md, acceptance.md로 저장된다. 

### 2) /moai run: TDD/DDD 구현
- plan단계에서 승인된 SPEC 문서를 바탕으로 실제 코드를 구현하는 과정이다. 
- 내부적으로는 먼저 manager-strategy 에이전트가 SPEC을 분석하고 실행 전략을 수립한 뒤 manager-ddd 에이전트가 ANALYZE-PRESERVE-IMPROVE 사이클을 통해 구현을 진행
- 구현이 완료되면 manager-quality 에이전트가 TRUST-5 품질 검증을 수행한다. 
- 품질게이트를 통과하지 못하면 IMPROVE 단계로 돌아가 수정하거나 사용자에게 품질 문제를 보고하고 선택을 요청한다. 

### 3) /moai sync: 코드, SPEC, 프로젝트 문서 동기화
- sync 단계 목적은 코드 변경 사항과 SPEC 문서, 프로젝트 문서 간의 일관성을 검증하고 동기화하는데 있다. 
- 코드가 SPEC에 명시된 요구 사항을 정확히 반영하는지, SPEC의 상태가 실제 구현 진행도와 일치하는지 등 종합적으로 확인한다. 
- 먼저 Phase 0.5 품질 검증이 수행된다. 프로젝트 언어를 자동 감지한 후 테스트 실행, 린터 검사, 타입 검사를 병렬로 실행한다. 
- 사전 검증을 통과하면 Phase1에서 manager-docs 에이전트가 동기화 전략을 수립한다. 
- Phase2는 동기화의 핵심이다. 먼저 안전 백업을 먼저 생성하고 manager-docs가 세가지 방향의 동기화를 수행한다.
- 첫 번째 방향은 코드에서 문서로의 동기화, 두번째 방향은 코드에서 SPEC으로의 동기화, 세번째 방향은 일관성 검증

### 4) /moai: 자율 자율화 모드
- /moai "구현하고 싶은 기능 설명" 한줄로 전체 파이프라인을 자율적으로 실행할 수 있다. 
- 자율모드는 실행 전 Phase 0 병렬 탐색을 추가한다. Explore 에이전트가 코드베이스를 분석하고 Research 에이전트가 외부 문서를 조사하면 Quality 에이전트가 품질 기준선을 확인한다. 
- 이 세 에이전트가 동시에 실행되어 순차 실행 대비 2~3배 빠른 속도를 달성한다. 

## 9-2 서브에이전트 심층 활용
### 1) Agent 도구의 기본 사용법
- 서브 에이전트를 호출하는 유일한 수단은 Agent 도구다. Agent 도구는 다섯가지 핵심 매개변수를 제공한다. 
  - subagent_type: .claude/agents/ 디렉터리에 정의된 에이전트 중 하나를 선택해 호출
  - prompt : 에이전트에 전달할 작업 지시를 담는다
  - model : haiku는 빠르고 저렴한 작업에, sonnet은 균형잡힌 일반 작업에, opus는 복잡한 추론이 필요한 작업에, inherit를 지정하면 부모 대화의 모델을 그대로 사용
  - max_turns: 에이전트가 수행할 수 있는 최대 턴 수를 제한
  - run_in_background: true로 설정하면 에이전트가 백그라운드에서 실행되어 메인 대화가 차단되지 않는다. 

### 2) 에이전트 호출 패턴
- 명시적 호출은 에이전트 이름을 직접 지정하고 자동 위임은 description 키워드 매칭으로 에이전트를 선택한다. 
- 서브에이전트는 다른 서브에이전트를 생성할 수 없다. 이는 무한 재귀를 방지하기 위한 설계 원칙이다. 

### 3) 에이전트 간 통신과 컨텍스트 격리
- MoAI-ADK에서 서브 에이전트가 50개의 파일을 읽고 분석하더라도 메인 대화에는 핵심 결과만 요약되어 전달되는 것이 이 격리의 실질적 효과다. 
- MoAI-ADK에서 에이전트 간 통신은 단방향이라서 서브에이전트끼리 직접 통신하는 것은 불가능 하며, 모든 정보 흐름은 반드시 MoAI를 경유한다. 

### 4) 에이전트 재개
- MoAI-ADK에서 재개의 핵심 이점은 컨텍스트 절약에 있다. 
- 에이전트의 컨텍스트가 약 95% 용량에 도달하면 자동 컴팩션이 수행된다. 컴팩션은 이전 대화 내용을 요약하여 새로운 컨텍스트 공간을 확보하는 과정이다. 
- 요약 과정에서 세부정보가 일부 손실될 수 있으므로, 핵심 결정 사항과 중간 결과물은 파일로 저장해 두는 것이 좋다. 

## 9-4 스킬 생태계와 점진적 공개
- MoAI-ADK에서 스킬은 특정 도메인의 전문 지식을 구조화한 지식 모듈이다. 
- 스킬은 9개의 카테고리로 분류되어 있으며 점진적 공개를 통해 필요한 시점에 적절한 수준의 정보만 로드된다. 

### 1) 스킬 분류 체계
- 집필 기준 MoAI-ADK의 스킬 수는 총 48개이다. 

### 2) 점진적 공개와 토큰
- 모든 스킬을 동시에 로드하면 대량의 토큰이 소모되기 때문에 이 문제를 해결하기 위한 3단계 토큰 최적화 전략이다. 
- 1단계(메타데이터)은 스킬당 약 100만 토큰을 사용
  - 스킬 이름, 설명, 트리거 키워드 등 최소한의 정보만 포함되며, 에이전트 프론트매터에 등록된 스킬은 항상 이레벨로 로드된다.
- 2단계(본문)은 트리거 조건이 매칭될 때 로드되며, 스킬당 약 5000토큰을 소모한다.
  - 전체 문서, 코드 예시, 구현 패턴 등 실질적인 작업 가이드가 이 레벨에 포함된다. 
- 3단계(번들)은 modules/ 디렉터리에 저장된 심층 참조 문서로 구성된다. 
  - 토큰 소모량은 가변적이며 클로드가 작업 맥락을 판단하여 필요한 모듈만 선택적으로 로드한다.

### 3) 스킬과 에이전트 연동
- 에이전트와 스킬의 관계에서 가장 중요한 점은 스킬이 단순히 '사용 가능한' 상태가 되는 것이 아니라 에이전트 컨텍스트에 완전히 주입된다는 것이다. 
- 에이전트 프론트매터의 skills필드에 스킬을 등록하면 해당 스킬의 전체 콘텐츠가 에이전트 시작시점에 컨텍스트로 주입된다. 

## 9-5 빌더 에이전트와 스킬만들기 
- 실무에서는 범용 에이전트와 스킬로 해결하기 어려운 요구사항이 등장하곤 한다. 이때 필요한 도구가 에이전트를 생성하는 builder-agent와 스킬을 생성하는 builder-skill이다.

### 1) builder-agent: 커스텀 에이전트 생성
- builder-agent는 대화형 프로세스를 통해 .claude/agents 디렉토리에 새로운 에이전트 정의 파일을 생성한다. 
- 사용자가 "~~ 만들어줘" 라고 요청하면 builder-agent는 이름, 역할, 도구 권한 등 순차적으로 질문한다. 
- 이 과정에서 수집된 정보를 YAML 프론트매터로 구조화하여 마크다운 파일을 자동 생성한다. 
- 잘 설계된 프론트매터는 에이전트가 적절한 시점에 자동으로 위임받고 허용된 범위 안에서만 작업을 수행하며 필요한 전문지식을 사전에 갖추도록 보장한다. 
- description 필드를 주의해야한다.
  - 클로드가 사용자의 요청을 분석할때 이 필드를 참조하여 해당 에이전트에 작업을 위임할지 결정하기 때문에
  - 구체적인 역할과 위임 트리거를 함께 기술해야한다. 

### 2) builder-skill; 커스텀 스킬생성
- YAML 스키마 기반으로 새로운 스킬을 생성한다. 
- 필수 필드는 name과 description이다. 

### 3) 도구 권한 설계 원칙
- 에이전트와 스킬 모두에서 도구 권한은 최소 권한원칙을 따른다. 
- 필요하지 않은 도구를 부여하면 의도하지 않은 파일 변경이나 시스템 명령 실행 위험이 증가한다. 

## 9-6 훅 시스템과 MCP 통합

### 1) MoAI-ADK의 훅 이벤트 체계
- SessionStart는 프로젝트 정보 표시와 환경 초기화, PreToolUse는 보안 검증과 위험 작업 차단, PostToolUse는 코드 포캐팅과 린트 검사, Stop은 루프 제어와 완료 조건 확인, SessionEnd는 정리 작업과 상태저장, Agent 이벤트는 에이이전트별 모니터링과 팀 간 조율에 활용

### 2) MCP 통합
- MoAI-ADK는 .mcp.json 파일에 MCP 서버를 등록하고, .claude/settings.json의 permissions.allow에서 해당 도구의 사용 권한을 부여하는 방식으로 MCP 통합을 구현한다.
- Context7: 실시간 라이브러리 문서 조회
  - MoAI-ADK에서 Context7은 스킬의 allowed-tools 필드를 통해 특정 에이전트에 선택적으로 연결한다. 
  - expert-backend 에이전트가 FastAPI나 Django의 최신 문서를 참조하고
  - expert-frontend 에이전트가 리액트나 Vue의 최신 패턴을 확인하는것이 대표적인 활용 사례다. 
  - 이를 통해 에이전트가 생성하는 코드가 항상 최신 공식 권장 사항을 따르도록 보장한다. 
- Sequential Thinking: 복잡한 의사결정 엔진
  - Sequential Thinking은 복잡한 문제를 단계쩍으로 분해하고 분석하는 MCP서버다.
  - MoAI-ADK는 -deepthink플래그를 통해 활성화 되며, 아키텍처 결정, 기술 선택의 트레이드 오프 분석, 호환성 파괴 영향도가 평가 등에 활용된다. 

## 9-7 깃 작업 트리 : 병렬 SPEC 개발
- 하나의 .git 디렉터리를 공유하면서 여러 개의 독립적인 작업 디렉토리를 생성하는것은 깃의 기본기능이다.
- 깃 작업트리는 서로 다른 브랜치를 체크아웃한 상태로 유지되며, 파일 시스템 수준에서 완전히 분리된다. 

## 9-8 슬래시 명령어와 CLI 유틸리티

### 1) 슬래시 명령어
- /moai fix, /moai loop, /moai feedback은 클로드 코드 안에서 슬래시 명령어로 실행된다.
- fix와 loop는 코드 품질을 자동으로 끌어올리는 역할을 맡고 feedback은 프레임워크 개선의견을 개발팀에 직접 전달한다.

### 2) /moai fix: 일회성 자동 수정
- AI 가 병렬 스캔을 통해 모든 문제를 탐지한 후 한번에 수정한다.
- 이 명령어의 핵심은 4단계 레벨 분류 체계다. 발견된 이슈를 위험도에 따라 네 등급으로 나누고, 등급별로 자동 수정 여부를 달리 적용한다. 
- 1레벨 : 포매팅 오류
  - import 정렬, 후행 공백 제거 등 코드의 동작에 영향을 주지 않는 형식적 문제이며 AI가 별도의 승인 없이 자동으로 수정
- 2레벨 : 린트 경고
  - 사용하지 않는 변수, 불필요한 else 구문, 네이밍 규칙 위반 등 코드 품질에 영향을 주는 경미한 문제를 다루며, 역시 자동 수정하되 로그를 남긴다.
- 3레벨 : 로직 오류
  - 누락된 에러 처리, 잘못된 조건문, 경곗값 미처리처럼 코드 동작을 변경할 수 있는 문제이므로 사용자의 승인을 받은 후 수정
- 4레벨 : 보안 취약점
  - SQL 인젝션, XSS 처럼 보안에 영향을 미치는 심각한 문제이며 반드시 사용자의 수동검토를 권장

### 3) /moai loop: 반복 수정 루프
- 집 전체가 깨끗해질때까지 반복하는 자동 청소 로봇
- LSP 오류가 0개여야 하고, 모든 테스트를 통과해야하며 커버리지가 85% 이상이어야 한다. 
- 이 세가지가 동시에 만족되어야 종료된다. 

### 4) /moai feedback: 피드백 제출
- MoAI-ADK 자체에 버그를 발견하거나 개선 아이디어가 떠올랐을 때 사용하는 명령어다.
- 클로드 코드 안에서 바로 피드백 제출 가능
