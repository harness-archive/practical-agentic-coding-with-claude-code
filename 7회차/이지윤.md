# Claude Code 7장 "자동화"
---

## 이 장이 다루는 것

지금까지(1~6장)는 클로드 코드를 **터미널에서 내가 직접 대화하며** 쓰는 법을 배웠습니다. 그런데 실무에서는 "매번 내가 옆에서 지켜보며 시키는" 게 아니라, **사람이 없어도 알아서 돌아가야 하는 상황**이 훨씬 많습니다.

7장은 바로 이런 **"사람 없이 자동으로 돌아가는 클로드"**를 만드는 법을 다룹니다. 네 파트로 이루어져 있습니다.

1. **7-1 비대화형 모드**: 클로드 코드를 대화창 없이, 스크립트나 파이프라인 안에서 "명령어 한 줄"처럼 호출하는 법
2. **7-2 훅(Hooks) 시스템**: 클로드가 특정 행동을 하는 바로 그 순간마다, AI의 판단과 상관없이 "무조건 실행되는" 내 명령을 끼워 넣는 법
3. **7-3 MCP 통합**: 깃허브·노션·데이터베이스 같은 외부 서비스를 클로드가 쓸 수 있는 "도구"로 연결하는 법
4. **7-4 플러그인 시스템**: 위 세 가지로 만든 설정들을 하나의 패키지로 묶어서 팀이나 커뮤니티에 나눠주는 법

7-1은 **"클로드에게 심부름을 시키는 법"**, 7-2는 **"특정 순간마다 저절로 울리는 알람/필터를 설치하는 법"**, 7-3은 **"외부 서비스에 만능 어댑터를 꽂는 법"**, 7-4는 **"그렇게 만든 설정 세트를 설치 파일 하나로 포장하는 법"**입니다.

이 네 가지는 서로 독립적인 게 아니라, 뒤로 갈수록 앞의 것을 활용합니다. 훅(7-2) 안에서 비대화형 모드(7-1)를 쓰기도 하고, MCP(7-3)를 훅과 연결해서 자동화하기도 하고, 이 모든 걸 플러그인(7-4)으로 포장해서 배포합니다.

## 7-1 비대화형 모드와 스크립트 자동화 (p.191~200)

### 비대화형 모드란?

평소 우리가 쓰는 클로드 코드는 터미널에 채팅창처럼 떠서 "질문 → 답변 → 확인"을 주고받는 **대화형(interactive)** 모드입니다. 사람이 계속 화면 앞에 앉아서 확인해줘야 합니다.

그런데 **자동화 파이프라인**에는 애초에 화면 앞에 앉아있을 사람이 없습니다. 이럴 때 쓰는 게 **비대화형 모드**입니다. `-p`(`--print`) 플래그 하나만 붙이면, 클로드가 프롬프트를 처리하고 결과만 딱 출력한 뒤 바로 종료됩니다.

```bash
$ claude -p "이 코드베이스의 구조를 설명해 줘."
```

**어디에 쓰일까? (그림 7-1)** cron(정해진 시간마다 자동 실행되는 스케줄러)이 정기 분석을 요청하거나, 깃 훅이 커밋 전 검사를 요청하거나, 슬랙 봇이 질문에 답하거나, 모니터링 시스템이 이상을 감지했을 때 — 이 모든 상황에서 호출 방법은 똑같이 `claude -p`입니다. 클로드는 분석 결과를 내놓고, 그 결과는 다시 알림·보고서 전송, 자동 코드 수정, 데이터 저장으로 이어집니다.

### 주요 플래그(옵션)들

자동화에서 가장 중요한 건 "클로드가 실수로 이상한 행동(예: 파일 삭제)을 하지 못하게 권한을 딱 필요한 만큼만 주는 것"입니다. 아래 플래그들이 그 역할을 합니다.

| 플래그 | 역할 | 쉬운 비유 |
|---|---|---|
| `--allowedTools "Bash,Read"` | 클로드가 쓸 수 있는 도구를 이 목록으로만 제한 | 알바생에게 "계산기랑 저울만 써도 돼" |
| `--disallowedTools "mcp__github"` | 특정 도구만 콕 집어 못 쓰게 막음 | "이 서랍은 절대 열지 마" |
| `--permission-mode` | 파일 편집 확인 방식 결정: `acceptEdits`(자동 승인) / `bypassPermissions`(전부 건너뜀, 가장 위험) / `dontAsk`(전부 자동 거부, 가장 안전) | 알바생에게 확인 절차를 얼마나 생략시킬지 정하기 |
| `--mcp-config <file>` | 복잡한 외부 서비스 연결 설정을 파일에서 불러오기 (7-3에서 배울 MCP) | 매번 말로 설명하지 말고 "매뉴얼 파일 보고 일해" |
| `--max-turns 3` | 클로드가 "도구 호출 → 결과 확인 → 다음 행동"을 반복하는 횟수(턴) 제한 | "질문 3번까지만 하고 결론 내" — 비용과 시간을 통제 |
| `--append-system-prompt "..."` | 기존 역할 지침에 내용을 덧붙임 (권장 방식) | "오늘은 보안 담당으로도 뛰어줘" 추가 지시 |
| `--system-prompt "..."` | 기본 지침을 통째로 교체 (기본 안전장치까지 사라져서 위험) | 알바생 매뉴얼을 아예 새로 갈아끼움 |
| `--verbose` | 실행 과정을 상세하게 로그로 남김 | 작업 일지를 꼼꼼히 기록 |

`--allowedTools`/`--disallowedTools`는 클로드 코드가 원래 갖고 있는 도구(Bash, Read, Write, Edit 등)뿐 아니라, `mcp__서버이름` 형식으로 7-3에서 배울 외부 연동 도구(MCP)도 지정할 수 있습니다.

### 입력과 출력, 어떻게 주고받을까

**출력 형식**은 상황에 따라 3가지 중 골라 씁니다.
- **텍스트(기본값)**: 사람이 그냥 읽기 편한 형태
- **JSON** (`--output-format json`): `is_error`(성공/실패 여부), `total_cost_usd`(비용), `session_id`(세션 식별자) 같은 부가 정보가 함께 담긴 구조화된 데이터. **다른 프로그램이 결과를 자동으로 읽어야 한다면 반드시 이 형식을 써야 합니다.**
- **스트리밍 JSON** (`stream-json`): 결과를 실시간으로 한 줄씩 흘려보냄. 오래 걸리는 작업의 진행 상황을 실시간으로 지켜볼 때 사용

> **쉽게 말하면**: 텍스트는 "사람이 읽는 보고서", JSON은 "엑셀 표처럼 정리된 데이터", 스트리밍 JSON은 "실시간 중계방송"입니다.

**입력 방법**은 명령어 뒤에 직접 쓰거나(`claude -p "..."`), `echo "..." | claude -p`처럼 파이프로 흘려보내거나, `cat error.log | claude -p "이 로그 분석해 줘"`처럼 파일 내용을 함께 넘길 수 있습니다.

### 대화가 끊기지 않게: 세션 이어가기

비대화형 모드라도 "저번에 나눴던 얘기, 기억하고 이어서 해줘"가 가능합니다. `--continue`(`-c`)는 가장 최근 세션을 자동으로 이어가고, `--resume`(`-r`)은 특정 세션 ID를 지정해서 그 세션으로 돌아갑니다.

```bash
# 세션 ID를 저장해뒀다가
session_id=$(claude -p "분석 시작" --output-format json | jq -r '.session_id')
# 나중에 그 세션을 이어서 작업
claude -r "$session_id" "추가 분석 수행" --no-interactive
```

### 실전에서는 이렇게 씁니다 — 예제 3가지

세 예제 모두 패턴은 똑같습니다: **"역할을 부여하고(누구처럼 행동해) + 도구 권한을 제한하고(뭘 쓸 수 있는지) + 결과를 JSON으로 받는다."** 이 세 가지 조합만 이해하면 어떤 자동화든 응용할 수 있습니다.

- **SRE 인시던트 대응 봇**: 장애 상황을 설명하면, 클로드가 "SRE(사이트 신뢰성 엔지니어) 전문가" 역할을 맡아 원인을 진단하고 조치를 제안. 모니터링 도구까지 도구로 붙여줌
- **자동화된 보안 리뷰**: `gh pr diff`로 PR(코드 변경 요청)의 변경 내용을 가져와서 "보안 엔지니어" 역할의 클로드에게 검토시킴. 읽기 전용 도구만 허용해서 실수로 코드를 고치지 못하게 안전장치를 걸어둠
- **다중 턴 법률 어시스턴트**: 세션을 유지하면서 "계약서 검토 → 규정 준수 확인 → 경영진 요약 생성"처럼 여러 단계를 순서대로 거쳐감

### CI/CD 파이프라인에 연결하기

**CI/CD**란 코드를 커밋할 때마다 자동으로 테스트·빌드·배포를 해주는 시스템(예: 깃허브 액션)을 말합니다. 여기에 클로드를 비대화형 모드로 끼워 넣으면 자동 코드 리뷰, 보안 감사, 문서 생성을 할 수 있습니다.

CI/CD에 연결할 때 신경 써야 할 5가지: **인증**(API 키는 코드에 직접 쓰지 말고 시크릿으로 안전하게 주입), **타임아웃**(`timeout` 명령으로 무한정 실행되지 않게 시간제한), **오류 처리**(`is_error` 필드로 실패를 감지하고 적절히 대응), **비용 관리**(`--max-turns`로 턴 수 제한, `total_cost_usd`로 비용 모니터링), **속도 제한**(여러 파일을 연속 처리할 땐 요청 사이에 `sleep`을 넣어서 API가 막히지 않게 함).

```yaml
- name: Claude Code Review
  uses: anthropics/claude-code-action@v1
  with:
    prompt: "이 PR을 리뷰하고 보안 취약점을 확인해 줘."
    output_format: json
    max_turns: 10
```

> **쉽게 말하면**: CI/CD 연동은 "회사 문 앞에 무인 경비 로봇을 세워두는 것"과 비슷합니다. 로봇이 멋대로 오래 일하지 않게(타임아웃), 문제 생기면 바로 알 수 있게(오류 처리), 전기세 폭탄 안 맞게(비용 관리), 너무 자주 왔다갔다 안 하게(속도 제한) 미리 규칙을 정해두는 것입니다.

### 조금 더 고급 기능들 (간단히)

- **다중 턴 세션 관리**: 첫 호출에서 세션 ID를 뽑아두고, 이후 호출마다 `--resume`으로 이어가며 "코드 작성 → 테스트 실행 → 실패하면 결과를 다시 클로드에게 전달해 수정 요청"처럼 단계별 검증 워크플로를 자동화할 수 있습니다.
- **에이전트 SDK**: `-p` 플래그와 파이썬/타입스크립트용 SDK를 아우르는 상위 개념입니다. `-p`가 "터미널에서 명령어 한 줄 치는 것"이라면, SDK는 "내 코드(자바스크립트/파이썬) 안에서 함수처럼 클로드를 호출하는 것"입니다. 복잡한 시스템을 만들 땐 SDK가 더 다루기 편합니다.
- **`--json-schema`**: 클로드의 응답을 내가 미리 정한 JSON 형식에 딱 맞춰서 강제로 받는 기능입니다. "아무렇게나 답하지 말고 이 양식에 맞춰서 답해줘"라고 강제하는 것이라, 뒤에 이어지는 프로그램이 데이터를 파싱하다가 에러 나는 걸 막아줍니다.

### 사용 전 체크리스트 & 비용 관리

프로그램이 결과를 자동으로 읽어야 한다면 반드시 JSON 출력을 쓰고, 종료 코드와 stderr로 실패를 항상 처리하고("클로드는 항상 성공한다"고 가정하면 안 됨), 맥락을 유지해야 하면 세션 기능을 쓰고, 장시간 작업엔 `timeout`으로 무한 대기를 막고, 여러 요청을 연달아 보낼 땐 `sleep`으로 속도 제한을 지킵니다.

**비용은 이렇게 관리합니다**: 프롬프트를 간결하게, 꼭 필요한 파일만 분석 대상으로 제한, `--max-turns`로 턴 수 제한, 같은 결과는 캐싱해서 중복 호출 방지.

## 7-2 훅(Hooks) 시스템 (p.201~226)

### 훅이란 무엇인가

앞서 배운 비대화형 모드는 "내가 명령을 내려야 클로드가 움직이는" 방식입니다. 그런데 이런 상황을 생각해봅시다: "클로드가 파일을 수정할 때마다, 매번 자동으로 코드 포맷터를 돌리고 싶다." 이걸 그냥 클로드에게 "수정할 때마다 포맷팅도 해줘"라고 프롬프트로 부탁하면 어떨까요? **AI는 깜빡 잊고 안 할 수도 있습니다.** 사람처럼 실수를 하는 것이죠.

이 문제를 해결하는 게 **훅(Hook)**입니다. 훅은 클로드 코드의 **생애 주기(라이프사이클) 중 정해진 시점**에 자동으로 실행되는 커스텀 셸 명령어, LLM 프롬프트, 또는 에이전트 작업입니다.

가장 중요한 포인트는 이것입니다: 훅은 **"AI의 판단"에 기대지 않고, 특정 작업이 반드시 실행되도록 보장**합니다.

> **쉽게 말하면**: "코드 작성 후 포맷팅해 줘"라고 클로드에게 부탁하는 것은 AI의 판단에 따라 실행될 수도, 생략될 수도 있는 "부탁"입니다. 반면 "파일을 수정할 때마다(정확히는 PostToolUse라는 시점에) 자동으로 포맷터를 실행하라"고 훅에 등록해두면, **AI의 기분과 상관없이 매번 무조건** 실행됩니다. 즉 훅은 "약속"이 아니라 "자동 반사 신경"입니다. 사람으로 치면 "무릎을 치면 다리가 반사적으로 움직이는 것"과 같아서, 생각할 필요 없이 몸(시스템)이 알아서 반응합니다.

훅으로 할 수 있는 일: 셸 명령어 자동 로깅, 코드 파일 자동 포맷팅, 규정 준수 추적, 민감한 파일(`.env` 등) 편집 자동 차단 등.

### 훅의 4가지 타입 — "무엇으로 반응할까"

훅이 실제로 실행할 때 "무엇을 실행할지"를 4가지 방식 중에서 고를 수 있습니다.

| 타입 | 하는 일 | 언제 적합한가 |
|---|---|---|
| `command` | bash 셸 명령을 직접 실행 | 포맷터, 린터, 유효성 검사처럼 규칙이 딱 정해진 결정론적 작업 |
| `prompt` | LLM(클로드)에게 프롬프트를 던져서 한 번만 빠르게 판단시킴 (`{"ok": true}` 또는 `{"ok": false, "reason": "..."}` 형태로 응답받음) | 단순 규칙만으로는 판단하기 애매한, 조금 복잡한 상황 |
| `agent` | Read·Grep·Glob 같은 도구를 쓸 수 있는 서브에이전트를 새로 만들어서, 여러 단계(최대 50턴)에 걸쳐 꼼꼼히 검증 | 실제 파일 내용이나 테스트 결과까지 직접 확인해야 하는 경우 |
| `http` | 지정한 URL로 이벤트 내용을 인터넷 너머로 전송(POST 요청) | 외부 감사 시스템, 로깅 서버, 알림 서비스 등과 연동할 때 |

> **쉽게 말하면**: `command`는 "정해진 매뉴얼대로 딱딱 움직이는 로봇팔", `prompt`는 "한 번 슥 보고 OK/NO만 빠르게 판단하는 검사관", `agent`는 "여러 서류를 직접 뒤져가며 꼼꼼히 조사하는 수사관", `http`는 "택배로 다른 회사(외부 서버)에 소식을 전하는 것"입니다. 뒤로 갈수록 더 똑똑하지만 그만큼 느리고 비쌉니다.

참고로 `command`/`http` 타입은 `"async": true` 옵션을 주면 **결과를 기다리지 않고 백그라운드에서 실행**시킬 수 있습니다. 배포처럼 오래 걸리는 작업에 적합하지만, 그 대신 "안 돼, 하지 마"라고 막는 차단 기능은 쓸 수 없습니다.

### 클로드가 움직이는 전체 흐름과, 훅을 끼울 수 있는 지점들 (그림 7-2)

클로드 코드가 세션을 시작해서 끝날 때까지의 흐름은 대략 이렇습니다.

```
세션 시작 → 사용자 프롬프트 → 도구 호출 준비 → (권한 필요?) → 도구 실행
  → (성공?) → 결과 처리/실패 처리 → (더 작업?) → 응답 완료 → 세션 종료
```

이 흐름의 **각 지점마다** "여기서 내 코드를 끼워 넣을 수 있다"는 개입 지점이 있고, 이걸 **이벤트**라고 부릅니다. 아래 표는 책에 나온 주요 이벤트를 순서대로 정리한 것입니다. 처음 보면 이름이 많아 보이지만, 사실 "언제(발생 시점)"만 잘 짝지어 이해하면 됩니다.

| 이벤트 | 발생 시점 | 쉬운 설명 |
|---|---|---|
| SessionStart | 세션이 시작되거나 재개될 때 | "출근 체크" — 환경 초기화 |
| UserPromptSubmit | 프롬프트를 제출한 직후, 클로드가 처리하기 전 | "질문 접수창구" — 프롬프트 검증 |
| PreToolUse | 클로드가 도구를 실행하기 직전 (**여기서 차단 가능**) | "출입 전 검문소" |
| PermissionRequest | 권한 승인 팝업이 뜰 때 | "허가서 도장 찍는 순간" |
| PostToolUse | 도구 호출이 성공적으로 끝난 직후 | "작업 완료 후 뒷정리" |
| PostToolUseFailure | 도구 호출이 실패했을 때 | "사고 접수" |
| Notification | 클로드가 알림을 보낼 때 | "안내 방송" (막을 수는 없음) |
| SubagentStart / SubagentStop | 서브에이전트 생성 시 / 종료 시 | "파견 직원 투입/복귀" |
| Stop | 메인 클로드가 응답을 다 끝냈을 때 (사용자가 중간에 끊으면 발생 안 함) | "작업자가 손 놓는 순간" |
| TeammateIdle / TaskCompleted | 팀원이 쉬려는 순간 / 작업이 완료 표시되려는 순간 | "품질 검사 없이는 못 쉬어!" 게이트 |
| PreCompact | 대화 내용을 압축하기 직전 | "책상 정리 직전" |
| SessionEnd | 세션이 끝날 때 | "퇴근" |

모든 이벤트는 **stdin(표준 입력)으로 JSON 데이터**를 훅에게 넘겨줍니다. 클로드가 훅에게 "지금 이런 상황이야"라고 쪽지를 건네주는 셈입니다. 공통으로 담기는 정보는 세션 ID, 대화 기록 경로, 현재 작업 폴더, 현재 권한 모드, 이벤트 이름입니다.

**매처(matcher)**는 "이 훅을 아무 때나 발동시키지 말고, 특정 조건에서만 발동시켜라"는 필터입니다. 예를 들어 `PreToolUse` 이벤트에서 매처를 `Bash`로 설정하면 "Bash 도구를 쓸 때만" 이 훅이 실행됩니다. `UserPromptSubmit`, `Stop`처럼 상황을 구분할 게 딱히 없는 이벤트는 애초에 매처를 지원하지 않고 항상 실행됩니다.

### 훅이 클로드에게 "안 돼!"라고 말하는 법 — 종료 코드와 결정 제어 (그림 7-3)

훅을 실행한 결과는 **종료 코드** 또는 **JSON 출력**, 둘 중 하나의 방식으로 클로드 코드에게 전달됩니다.

종료 코드는 신호등이라고 생각하면 쉽습니다.
- **0(초록불)** = 성공. 정상적으로 통과.
- **2(빨간불)** = "여기서 멈춰!" — 단, 이 빨간불이 실제로 브레이크 역할을 하는 이벤트는 정해져 있습니다. `PreToolUse`(도구 호출을 막음), `PermissionRequest`(권한을 거부함), `UserPromptSubmit`(프롬프트 처리를 막음), `Stop`/`SubagentStop`(종료를 막고 계속 진행시킴), `TeammateIdle`/`TaskCompleted`(전환·완료 표시를 막음)에서만 진짜로 "차단" 효과가 있습니다. 반면 `PostToolUse`처럼 "이미 끝난 일"에 대한 이벤트에서는 2를 반환해도 멈추지 않고, 대신 클로드에게 참고용 메시지로만 전달됩니다.
- **그 외 코드(1, 3 등)** = 차단은 안 되는 그냥 경고. "경고등만 깜빡"이고 작업은 계속 진행됩니다.

JSON으로 응답하면 더 세밀한 제어가 가능합니다. 공통 필드로 `continue`(false면 클로드를 완전히 중단), `stopReason`(중단 시 보여줄 메시지) 등이 있고, 이벤트에 따라 `decision: "block"` + `reason`, 또는 `permissionDecision: "allow"/"deny"/"ask"` 같은 필드로 세밀하게 결정을 내릴 수 있습니다.

### 훅은 어디에 적어둘까 — 설정 파일

훅 설정은 여러 레벨에 쓸 수 있습니다: `~/.claude/settings.json`(내 컴퓨터 전체 적용) → `.claude/settings.json`(이 프로젝트, 팀과 공유) → `.claude/settings.local.json`(이 프로젝트, 나만) → 기업 관리 정책 → 플러그인의 `hooks/hooks.json` → 스킬/에이전트 파일 안에 직접 적기.

작성 구조는 3단계입니다: **① 어떤 이벤트에 반응할지 고르고 → ② 매처로 조건을 좁히고 → ③ 실제로 실행할 내용을 정의**합니다.

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command", "command": ".claude/hooks/block-rm.sh" }]
    }]
  }
}
```
→ "Bash 도구를 실행하려고 할 때마다, `block-rm.sh` 스크립트를 실행해서 미리 검사한다"는 뜻입니다.

참고로 스킬이나 에이전트 파일 안에 직접 훅을 적어둘 수도 있는데(**프론트매터 훅**), 이건 그 컴포넌트가 켜져 있는 동안에만 동작하고 끝나면 자동으로 사라집니다. 전역 설정 파일의 훅과 동시에 정의되어 있으면 **둘 다 실행**됩니다(서로 배타적이지 않음).

### 실전 훅 예제 — "이렇게 씁니다"

- **위험한 명령 차단**: `PreToolUse`에서 명령어에 `rm -rf`가 포함되어 있으면 실행을 거부 → 클로드가 실수로 파일을 몽땅 지우는 사고를 원천 차단
- **자동 코드 포매팅**: `.ts`/`.tsx` 파일을 저장할 때마다(`PostToolUse`) 자동으로 `npx prettier --write` 실행 → 사람이 포맷팅 신경 안 써도 됨
- **민감 파일 보호**: `.env`, `.git/` 경로의 파일을 편집하려 하면 `PreToolUse`에서 차단 → 비밀 키나 깃 내부 파일을 실수로 건드리지 못하게 방지
- **세션 로깅**: 세션이 시작/종료될 때마다 로그 파일에 시간을 기록 → 언제 얼마나 썼는지 나중에 추적 가능
- **LLM 판단형 Stop 훅**: "대화가 정말 다 끝났는지" 클로드에게 한 번 더 물어보고 나서 종료를 허용 → 성급하게 끝내는 것을 방지

### 보안, 조심해야 합니다 (그림 7-4)

훅은 **내 컴퓨터 계정 권한으로 자동 실행**되기 때문에, 잘못 만들면 랜섬웨어처럼 위험할 수 있습니다. 공식 문서가 제시하는 5가지 안전 수칙: ① 입력값을 무조건 믿지 말고 검증할 것 ② 셸 변수는 항상 `"$VAR"`처럼 따옴표로 감쌀 것 ③ 경로에 `..`가 있는지 확인해서 상위 폴더로 못 나가게 막을 것(경로 순회 공격 방지) ④ 스크립트는 절대 경로나 `$CLAUDE_PROJECT_DIR` 변수로 정확히 지정할 것 ⑤ `.env`, `.git/`, 키 파일 같은 "금고"는 절대 건드리지 말 것.

문제가 생기면 `claude --debug`로 실행해서 어떤 훅이 언제 매칭됐는지, 종료 코드가 뭐였는지 로그로 확인할 수 있습니다.

### 놓치기 쉬운 부분 보완하기 — pre-bash/post-bash 훅

6장에서 배운 **체크포인팅**(작업을 실행 전 상태로 되돌리는 기능)은 Read·Write·Edit처럼 클로드가 직접 쓰는 파일 도구만 추적합니다. 그런데 클로드가 `Bash` 도구로 실행한 `rm`, `mv`, `cp` 같은 터미널 명령은 클로드 외부에서 실행되는 것이라 체크포인팅으로 되돌릴 수 없습니다.

해결책은 **`pre-bash` 훅에서 위험해 보이는 명령이면 미리 `git stash`로 스냅샷을 찍어두고**, **`post-bash` 훅에서 실제로 뭔가 바뀌었는지(`git diff --quiet`) 확인한 뒤, 바뀌었을 때만 커밋**하는 방식입니다. 이렇게 하면 실제 변경이 있을 때만 커밋해서 히스토리가 깔끔하고, 문제가 생기면 즉시 이전 상태로 되돌릴 수 있으며, 커밋 메시지에 실제 실행된 명령이 남아 나중에 추적하기도 쉽습니다.

## 7-3 MCP 통합 (p.226~233)

### MCP란 무엇인가

지금까지는 클로드가 "내 컴퓨터 안"에서만 일했습니다(파일 읽기/쓰기, 터미널 명령). 그런데 실무에서는 깃허브 이슈를 확인하거나, 노션 문서를 찾아보거나, 회사 데이터베이스를 조회해야 할 때가 많습니다. 문제는 이 서비스들이 **저마다 API 방식과 인증 절차가 다 다르다**는 점입니다. 매번 새로 배워야 한다면 너무 번거롭겠죠.

**MCP(Model Context Protocol)**는 이 문제를 해결하는, AI 에이전트가 **외부 시스템과 상호작용하기 위한 표준화된 프로토콜**(약속된 통신 규칙)입니다. MCP라는 하나의 표준만 이해하면, 어떤 서비스든 클로드 코드와 연결할 수 있습니다.

> **쉽게 말하면**: MCP는 "만능 어댑터"입니다. 노션·깃허브·슬랙·데이터베이스마다 콘센트 모양(연결 방식)이 다 다르면 매번 새로 어댑터를 사야 하지만, MCP라는 표준 규격 하나만 있으면 어떤 서비스든 클로드에 "USB처럼" 꽂아 쓸 수 있습니다. (그림 7-5: 클로드 코드는 내장 도구로 로컬 파일·터미널을 다루고, MCP 서버로 GitHub·Notion·Database·모니터링·디자인 도구 등 외부 세계를 다룸)

### 연결하는 방법 — 전송 방식

MCP 서버와 통신하는 방식은 3가지가 있는데, 선택 기준은 단순합니다: **로컬에서 도는 서버는 stdio, 인터넷 너머 원격 서버는 HTTP**를 씁니다.

- **stdio**: 내 컴퓨터에서 직접 실행되는 서버와 표준 입출력으로 통신. 네트워크를 거치지 않아 가장 빠르고 안정적. `claude mcp add --transport stdio <이름> -- <실행 명령>`
- **HTTP**: 클라우드에 호스팅된 원격 서버와 통신. REST API 방식. `claude mcp add --transport http <이름> <URL>`
- **SSE**: 오래된 방식이라 더 이상 권장되지 않음(레거시 서버가 아직 HTTP를 지원 안 할 때만 임시로 사용)

연결한 서버는 `claude mcp list`(목록 확인), `claude mcp get <이름>`(상세 정보), `claude mcp remove <이름>`(제거) 명령으로 관리하고, 세션 안에서는 `/mcp` 명령으로 상태 확인과 인증(아래 참고)을 처리합니다.

### 실제로 뭘 할 수 있나요? — 활용 사례

- **GitHub 연동**: 리포지토리 코드를 분석하고, PR을 자동으로 검토하고, 이슈를 보고 버그 수정 코드를 생성
- **데이터베이스 직접 쿼리**: "지난 7일간 가장 많이 구매한 사용자 10명 조회해줘"처럼 자연어로 DB에 물어보기
- **모니터링 도구 연동(Sentry 등)**: "지난 24시간 동안 가장 흔한 오류가 뭐야?" 같은 질문으로 운영 문제를 진단
- **디자인 도구 연동(피그마 등)**: "이 버튼 디자인을 React 컴포넌트로 만들어줘"처럼 디자인을 코드로 자동 변환

### 어디까지 공유할까 — 범위와 인증

MCP 서버 설정은 3단계 범위로 관리합니다.
- **로컬**(`--scope local`, `.claude/settings.local.json`): 나만, 민감한 개인 API 키 등에 적합
- **프로젝트**(`--scope project`, `.mcp.json`): 팀 전체와 공유, 버전 관리에 커밋해서 팀원 모두 같은 설정 사용
- **사용자**(`--scope user`, `~/.claude/mcp.json`): 내 컴퓨터의 모든 프로젝트에서 사용, 개인적으로 자주 쓰는 서비스에 적합

`.mcp.json`에 API 키를 그대로 적으면 위험하니, `${API_KEY}` 같은 문법으로 **환경 변수를 대신 참조**하게 만듭니다. 이렇게 하면 민감한 값은 각자의 컴퓨터 환경 변수에만 있고, 설정 파일 자체는 안전하게 버전 관리에 올릴 수 있습니다.

인증 방식은 두 가지입니다. **OAuth 2.0**(많은 클라우드 서비스가 쓰는 표준 로그인 방식 — `/mcp` 명령을 실행하면 브라우저가 뜨고, 로그인하면 토큰이 자동 저장됨)과 **헤더 기반 인증**(API 키나 Bearer 토큰을 `--header` 플래그로 직접 지정). 참고로 MCP 서버가 제공하는 자료는 `@github:issue://123`처럼 `@` 멘션으로 대화 중에 바로 참조할 수도 있습니다.

### 훅과 MCP를 함께 쓰면?

7-2에서 배운 훅과 MCP를 결합하면 더 강력한 자동화가 됩니다. 예를 들어 파일을 수정할 때마다(`PostToolUse`) "PR을 만들어드릴까요?"라고 MCP로 깃허브에 제안하게 하거나, 반대로 `PreToolUse` 훅으로 "허용된 리포지토리가 아니면 MCP 도구 사용을 차단"하는 것도 가능합니다.

**실전 예시**: 풀스택 개발 워크플로(그림 7-6)에서는 Jira → Figma → 데이터베이스 → GitHub Actions → Vercel → Sentry까지, 기획부터 배포·모니터링까지 전 과정을 클로드 코드 한 세션 안에서 순환시킬 수 있습니다. SaaS 운영에서는 Stripe로 결제 분석, SendGrid로 이메일 발송 확인, Zendesk로 고객 문의 자동 응답 제안 같은 것도 가능합니다.

> **쉽게 말하면**: MCP를 여러 개 연결하면 클로드 코드가 "기획 → 설계 → 개발 → 테스트 → 배포 → 모니터링"까지 이어지는 하나의 "만능 콘솔"이 됩니다. 여러 탭을 왔다갔다 하지 않아도 클로드 안에서 전체 사이클을 다룰 수 있는 것이죠.

**유의할 점**: 각 MCP 서버에는 꼭 필요한 최소 권한만 주고, API 키는 환경 변수로 분리하고, 안 쓰는 서버는 정리합니다. 대량 데이터를 다룰 땐 필터링 조건을 구체적으로 정하고, API 호출 비용도 모니터링해야 합니다. 그리고 MCP는 결국 외부 서비스에 의존하는 것이므로, 그 서비스가 다운되거나 네트워크 문제가 생길 경우의 대응책도 미리 생각해둬야 합니다.

## 7-4 플러그인 시스템 (p.234~253)

### 플러그인이란

지금까지 배운 비대화형 모드, 훅, MCP는 전부 "한 프로젝트 안에서 내가 직접 설정하는 기능"이었습니다. 그런데 이렇게 만든 유용한 설정을 **다른 프로젝트에서도 쓰고 싶거나, 팀 동료에게 그대로 전달하고 싶다면** 어떻게 할까요? 매번 설정 파일을 복사해서 붙여넣는 건 번거롭고 실수하기 쉽습니다.

**플러그인**은 클로드 코드의 핵심 기능을 건드리지 않고도 새 기능을 추가할 수 있게 하는 **모듈화된 확장 단위**입니다. 명령어·에이전트·스킬·훅·MCP 설정을 하나로 묶어서, 여러 프로젝트에 재사용하거나 팀 전체에 배포하거나 마켓플레이스(뒤에서 설명)를 통해 커뮤니티와 공유할 수 있습니다.

> **쉽게 말하면**: 플러그인은 지금까지 만든 여러 설정(커스텀 명령어, 훅, MCP 연결 등)을 **하나로 포장해서 다른 프로젝트나 동료에게 그대로 전달**할 수 있게 하는 "설치 패키지(앱)"입니다. 스마트폰에서 앱을 설치하듯, 클로드 코드에도 필요한 기능을 앱처럼 설치할 수 있는 것이죠.

### 플러그인은 어떻게 생겼나 — 구조와 plugin.json

모든 플러그인은 `.claude-plugin/plugin.json`이라는 **매니페스트 파일**(플러그인의 이름표이자 설명서)이 반드시 있어야 합니다. 이 파일에서 유일하게 꼭 채워야 하는 항목은 `name`(플러그인 이름) 하나뿐이고, `version`(버전), `description`(설명), `author`(작성자) 같은 나머지는 선택 사항이지만 채울수록 더 신뢰가 갑니다.

```
my-plugin/
├── .claude-plugin/plugin.json   # 필수: 이름표이자 설명서
├── commands/hello.md             # 선택: 슬래시 명령어
├── agents/helper.md              # 선택: 전담 에이전트
├── skills/my-skill/SKILL.md      # 선택: 배경지식(스킬)
├── hooks/hooks.json              # 선택: 자동 실행 규칙(훅)
└── .mcp.json                     # 선택: 외부 서비스 연결(MCP)
```

`commands/`, `agents/`, `skills/`, `hooks/` 같은 표준 폴더에 넣어두기만 하면 클로드 코드가 자동으로 인식합니다. 폴더 구조가 특이하면 `plugin.json` 안에 경로를 따로 지정할 수도 있습니다. 그리고 플러그인 내부 파일을 참조할 때는 절대 경로를 직접 쓰지 말고 `${CLAUDE_PLUGIN_ROOT}`라는 환경 변수를 씁니다. 이렇게 해야 플러그인이 어느 컴퓨터에 설치되든 경로가 자동으로 맞춰집니다.

### 플러그인 안에 담을 수 있는 5가지 재료

플러그인은 지금까지 이 문서에서 배운 개념들을 그대로 재료로 사용합니다. 즉, 완전히 새로운 걸 배우는 게 아니라 "포장하는 방법"만 배우는 것입니다.

| 컴포넌트 | 무엇인가 | 비유 |
|---|---|---|
| 명령어 | `commands/`에 마크다운 파일을 넣으면 `/plugin-name:명령어`로 호출 가능 (이름이 겹쳐도 플러그인 이름으로 구분되어 충돌 없음) | 내가 직접 부르는 단축키 |
| 에이전트 | `agents/`에 정의 파일을 넣으면 특정 작업 전담 서브에이전트 추가 | 특정 분야를 전담하는 부하 직원 |
| 스킬 | `skills/*/SKILL.md`로 클로드의 배경지식을 확장 (3장에서 배운 스킬 시스템) | 새로 장착하는 지식 확장팩 |
| 훅 | 7-2에서 배운 그 훅. `hooks/hooks.json`에 정의 | 자동 반사 신경 |
| MCP 서버 | 7-3에서 배운 그 MCP. `.mcp.json`에 정의 | 외부 서비스 어댑터 |

### 어디까지 설치될까 — 설치 범위 4가지

- **user**: 내 컴퓨터의 모든 프로젝트에 적용, 개인 유틸리티용 (기본값)
- **project**: 이 프로젝트에 커밋되어 팀 전체가 공유
- **local**: 이 프로젝트에서 나만, 버전 관리에서 제외
- **managed**: 회사 IT 관리자가 중앙에서 배포하는 읽기 전용 설정 (조직 보안 정책용)

### 플러그인은 어디서 받아올까 — 마켓플레이스

**마켓플레이스**는 스마트폰의 "앱 스토어"와 같은, 설치 가능한 플러그인의 목록(카탈로그)입니다. 클로드 코드에는 앤트로픽 공식 마켓플레이스(`claude-plugins-official`)가 기본으로 이미 등록되어 있어서, 별다른 설정 없이 바로 플러그인을 찾아볼 수 있습니다. 여기에는 코드 인텔리전스, 외부 서비스 연동, 개발 워크플로 자동화, 출력 스타일 같은 카테고리로 플러그인이 정리되어 있습니다.

회사 내부용 마켓플레이스나, 깃허브 저장소, 심지어 로컬 폴더도 마켓플레이스로 등록할 수 있습니다(`/plugin marketplace add owner/repo`). 마켓플레이스는 `.claude-plugin/marketplace.json` 파일에 이름·소유자·포함된 플러그인 목록을 정의해서 만듭니다.

### 실제로 설치/관리하는 법

```bash
> /plugin marketplace add owner/repo        # 마켓플레이스(앱스토어) 등록
> /plugin install plugin-name@marketplace   # 앱 설치하듯 플러그인 설치
> /plugin enable / disable plugin-name@mp   # 제거하지 않고 잠깐 켜고 끄기
> /plugin uninstall plugin-name@mp          # 완전히 삭제
```

`/plugin` 명령을 입력하면 앱스토어처럼 대화형 메뉴가 뜨는데, 여기서 마켓플레이스를 탐색하며 어떤 플러그인이 있는지 구경할 수도 있습니다.

팀 프로젝트에서는 `.claude/settings.json`에 마켓플레이스와 설치할 플러그인 목록을 미리 적어두면, 팀원이 저장소를 클론했을 때 클로드 코드가 "이 플러그인들을 설치할까요?"라고 물어보고, **사용자가 명시적으로 승인**하면 자동으로 설치됩니다(악의적인 플러그인이 몰래 설치되는 걸 막기 위해 항상 사람 확인을 거침). 이렇게 하면 새로 합류한 팀원도 별도 설정 없이 동일한 도구 세트를 자동으로 갖추게 됩니다.

**뭔가 안 될 때**: `claude --debug`로 실행하면 어떤 플러그인이 로드됐는지, 어디서 오류가 났는지 로그로 확인할 수 있습니다. 자주 겪는 문제는 `plugin.json`의 JSON 문법 오류, `commands/` 폴더 위치 오류, 훅 스크립트에 실행 권한이 없는 경우(`chmod +x`로 해결), `${CLAUDE_PLUGIN_ROOT}`를 안 써서 경로가 안 맞는 경우입니다.

### 실전 예제로 감 잡기 — "코드 품질 도구" 플러그인

팀에서 반복적으로 하는 작업(린트 검사, 테스트, 리팩터링, 컨벤션 확인)을 플러그인 하나로 묶은 예시입니다.

```
code-quality-plugin/
├── .claude-plugin/plugin.json
├── commands/quality-check.md          # "/quality-check" 명령어로 종합 품질 검사 실행
├── agents/refactor-specialist.md      # 복잡한 리팩터링을 전담하는 에이전트
├── skills/team-conventions/SKILL.md   # 팀 네이밍 규칙·파일 구조·코드 스타일
└── hooks/hooks.json                   # 파일 저장 시 자동 린트 실행 (PostToolUse)
```

이 하나의 플러그인 안에서 5대 컴포넌트가 어떻게 맞물리는지 보면: 코드를 짜기 전엔 스킬(팀 컨벤션)을 참고하고, 저장할 때마다 훅이 자동으로 린트를 돌리고, `/quality-check` 명령어로 언제든 종합 점검을 할 수 있고, 복잡한 리팩터링은 전문 에이전트에게 맡깁니다.

플러그인을 개발하는 동안에는 `dev-marketplace`라는 임시 로컬 마켓플레이스를 만들어서 빠르게 테스트합니다. 다만 플러그인은 설치할 때 원본이 아니라 **캐시(복사본)**로 저장되기 때문에, 코드를 수정해도 바로 반영되지 않고 재설치를 해야 반영됩니다(실행 중인 세션이 갑자기 바뀌는 걸 막기 위한 안전장치입니다).

### 배포 전 체크리스트와 설계 원칙

배포하기 전에 확인할 것: `plugin.json`의 이름·버전·설명·작성자 정보를 다 채웠는지, 모든 기능을 실제로 테스트했는지, README에 설치·사용법을 문서화했는지, 라이선스(MIT 등)를 명시했는지, 버전별 변경 사항(CHANGELOG)을 기록했는지.

좋은 플러그인을 만드는 원칙: **하나의 플러그인은 한 가지 일만** 하게 만들고(포매팅·테스트·보안검사는 각각 별도 플러그인으로), **플러그인끼리 서로 의존하지 않게** 하고(공통 기능은 스킬로 분리), **절대 경로 대신 상대 경로와 `${CLAUDE_PLUGIN_ROOT}`를 사용**하고, **훅 스크립트에는 실행 권한을 꼭 부여**하고, **에러가 나면 사용자에게 무엇이 잘못됐고 어떻게 고칠지 친절하게 알려주기**.
