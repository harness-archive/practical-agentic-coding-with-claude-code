# Claude Code 7장 "자동화" 

## 이 장이 다루는 것

6장까지는 클로드 코드 "혼자" 잘 쓰는 법(대화, 상태 관리)을 다뤘다면, 7장은 클로드 코드를 **외부 시스템과 연결하고, 사람이 매번 시키지 않아도 알아서 돌아가게 만드는 법**을 다룹니다.

크게 두 파트입니다.

1. **7-1 비대화형 모드**: 클로드 코드를 "대화창 없이" 스크립트/파이프라인에서 프로그램처럼 호출하는 법
2. **7-2 훅(Hooks) 시스템**: 클로드가 어떤 행동을 하는 특정 순간마다 "무조건 실행되는" 내 명령을 끼워 넣는 법

쉽게 비유하면, 7-1은 "클로드에게 심부름을 시키는 법"이고, 7-2는 "클로드가 특정 행동을 할 때마다 자동으로 울리는 알람/필터를 설치하는 법"입니다.

## 7-1 비대화형 모드와 스크립트 자동화 (p.191~200)

### 비대화형 모드란?

평소 우리가 쓰는 클로드 코드는 터미널에 채팅창처럼 떠서 "질문 → 답변 → 확인"을 주고받는 **대화형(interactive)** 모드입니다.

그런데 자동화 파이프라인(예: 매일 새벽에 자동으로 도는 스크립트)에는 "사람이 옆에서 확인해주는" 과정이 없습니다. 이때 쓰는 게 **비대화형 모드**입니다. 명령 하나로 "프롬프트 던지고 → 결과만 받기"를 할 수 있게 해줍니다.

> **쉽게 말하면**: 대화형 모드가 "챗봇과 카톡하기"라면, 비대화형 모드는 "자판기에 동전 넣고 버튼 누르면 물건만 나오는 것"입니다. 대화 없이 입력 → 결과만 딱 받습니다.

실행 방법은 `-p` (또는 `--print`) 플래그를 붙이는 것입니다.

```bash
$ claude -p "이 코드베이스의 구조를 설명해 줘."
```

이렇게 하면 클로드가 현재 폴더를 분석하고, 결과를 화면(표준 출력)에 뿌려주고 끝납니다. 대화창이 안 열리기 때문에 셸 스크립트에서 바로 호출할 수 있습니다.

**활용 예시 (그림 7-1 "비대화형 모드 통합 시나리오")**
- `cron` 작업(정해진 시간마다 자동 실행되는 스케줄러)이 **정기 분석**을 요청
- 깃 훅이 **커밋 전 검사**를 요청
- 슬랙 봇이 **질문 응답**을 요청
- 모니터링 시스템이 **이상 감지**를 요청

→ 이 네 가지가 전부 `claude -p`를 통해 클로드를 호출하고, 클로드는 **분석 결과**를 내놓고, 그 결과는 다시 알림/보고서, 자동 수정, 데이터 저장으로 이어집니다.

> **쉽게 말하면**: 클로드 코드가 "만능 일꾼"이고, cron·깃·슬랙·모니터링은 각자 다른 이유로 이 일꾼을 호출하는 "고객"들입니다. 고객이 누구든 호출 방법은 똑같이 `claude -p`입니다.

### 주요 플래그(옵션)들

비대화형 모드를 실전에서 쓸 때 자주 등장하는 옵션들입니다. 하나씩 "이게 왜 필요한지"로 이해하면 쉽습니다.

| 플래그 | 무엇을 하는가 | 쉬운 비유 |
|---|---|---|
| `--allowedTools "Bash,Read"` | 클로드가 쓸 수 있는 도구를 지정 | 알바생에게 "너는 계산기랑 저울만 써도 돼"라고 제한 |
| `--disallowedTools "mcp__github"` | 특정 도구만 못 쓰게 막음 | "이 서랍은 절대 열지 마" |
| `--permission-mode acceptEdits` | 파일 편집 시 사람 확인 없이 자동 승인 | 알바생에게 "물어보지 말고 바로 진행해" |
| `--mcp-config monitoring-tools.json` | 복잡한 MCP(외부 도구 연결) 설정을 파일에서 불러옴 | 매번 말로 설명하지 말고 "매뉴얼 파일 보고 일해" |
| `--max-turns 3` | 클로드가 "도구 호출 → 결과 확인 → 다음 행동"을 반복하는 횟수(턴) 제한 | "질문 3번까지만 하고 결론 내" |
| `--append-system-prompt "..."` | 기존 역할 지침에 내용을 덧붙임 | 알바생에게 "오늘은 특별히 보안 담당으로도 뛰어줘" 추가 지시 |
| `--system-prompt "..."` | 기본 지침을 통째로 교체 (위험할 수 있음, 안전장치도 같이 사라짐) | 알바생 매뉴얼을 아예 새로 갈아끼움 |
| `--verbose` | 상세 로그 출력 | 작업 일지를 꼼꼼히 기록 |

`--allowedTools`와 `--disallowedTools`는 클로드 코드 내장 도구(Bash, Read, Write, Edit, Glob, Grep, WebFetch, WebSearch)뿐 아니라, `mcp__서버이름` 형식으로 외부 연동 도구(MCP)도 지정할 수 있습니다.

```bash
# 읽기 전용 분석 (파일을 고치지 못하게, 보기만 하게)
$ claude -p "보안 취약점 분석" --allowedTools "Read,Grep,Glob"

# 특정 도구 제외
$ claude -p "코드 리뷰" --disallowedTools "mcp__github"
```

> **쉽게 말하면**: 자동화에서 제일 중요한 건 "클로드가 실수로 이상한 짓(예: 파일 삭제)을 못 하게 권한을 딱 필요한 만큼만 주는 것"입니다. `--allowedTools`가 바로 그 안전벨트입니다.

`--permission-mode`는 세 가지 값이 있습니다.
- `acceptEdits`: 파일 편집은 확인 없이 진행
- `bypassPermissions`: 모든 확인을 다 건너뜀 (가장 위험, 신뢰된 환경에서만)
- `dontAsk`: 모든 권한 요청을 자동으로 거부 (최소 권한으로만 동작)

### 입력/출력 형식

**출력 형식** 3가지:
1. **텍스트 출력(기본값)**: 사람이 읽기 편한 일반 텍스트
2. **JSON 출력** (`--output-format json`): `type`, `total_cost_usd`(비용), `is_error`(에러 여부), `duration_ms`(걸린 시간), `session_id`(세션 식별자) 같은 메타데이터가 포함된 구조화 데이터. **프로그램이 자동으로 파싱**해야 할 때 필수
3. **스트리밍 JSON 출력** (`--output-format stream-json`): 메시지 하나하나를 실시간으로 흘려보냄. 장시간 걸리는 작업의 진행 상황을 실시간 모니터링할 때 사용 (JSONL 형식)

> **쉽게 말하면**: 텍스트 출력은 "사람이 읽는 보고서", JSON 출력은 "엑셀 표처럼 정리된 데이터", 스트리밍 JSON은 "실시간 중계방송"입니다.

**입력 방법** 2가지:
```bash
# 직접 인수로
$ claude -p "이 코드를 설명해 줘."

# 표준입력(stdin)으로 흘려보내기
$ echo "이 코드를 설명해 줘." | claude -p

# 파일 내용과 함께
$ cat error.log | claude -p "이 에러 로그를 분석해 줘."
```

### 다중 턴 대화 (세션 이어가기)

비대화형 모드에서도 "이전에 나눴던 대화 내용"을 기억하게 만들 수 있습니다.

- `--continue` (`-c`): 세션 ID를 몰라도 **가장 최근 세션**을 자동으로 이어감
- `--resume` (`-r`): **특정 세션 ID**를 지정해서 그 세션을 재개

```bash
# 세션 ID를 저장해뒀다가
$ session_id=$(claude -p "프로젝트 분석 시작" --output-format json | jq -r '.session_id')

# 나중에 그 세션으로 이어서 작업
$ claude -r "$session_id" "추가 분석 수행" --no-interactive
```

> **쉽게 말하면**: 매번 "처음 뵙겠습니다"부터 시작하면 비효율적이니, "저번에 얘기한 그거 이어서 해줘"라고 할 수 있게 세션표(영수증)를 발급해주는 것과 같습니다.

### 자동화 실전 예제 3가지 (책에서 소개하는 패턴)

1. **SRE 인시던트 대응 봇**: 장애 설명과 심각도를 넣으면, 클로드가 "SRE 전문가" 역할을 맡아 원인 진단 + 즉각 조치를 제안. 모니터링 도구(Datadog 등)에도 접근 가능.
   ```bash
   investigate_incident() {
       local incident_description="$1"
       local severity="${2:-medium}"
       claude -p "인시던트: $incident_description(심각도: $severity)" \
         --append-system-prompt "당신은 SRE 전문가입니다. 문제를 진단하고 영향을 평가하고 즉각적인 조치 사항을 제공하세요." \
         --output-format json \
         --allowedTools "Bash,Read,WebSearch,mcp__datadog" \
         --mcp-config monitoring-tools.json
   }
   investigate_incident "결제 API에서 500 에러 반환 중" "high"
   ```

2. **자동화된 보안 리뷰**: PR(코드 변경 요청)의 변경 내용(diff)을 가져와서, "보안 엔지니어" 역할의 클로드에게 취약점을 검토시킴. 읽기 전용 도구만 허용해서 실수로 코드를 고치지 못하게 함.
   ```bash
   audit_pr() {
       local pr_number="$1"
       gh pr diff "$pr_number" | claude -p \
         --append-system-prompt "당신은 보안 엔지니어입니다. 이 PR에 대해 취약점, 안전하지 않은 패턴, 규정 준수 문제를 검토하세요." \
         --output-format json \
         --allowedTools "Read,Grep,WebSearch"
   }
   audit_pr 123 > security-report.json
   ```

3. **다중 턴 법률 어시스턴트**: 세션을 유지하면서 여러 단계를 거쳐 검토(계약서 검토 → 규정 준수 확인 → 경영진 요약 생성)를 수행.
   ```bash
   session_id=$(claude -p "법률 검토 세션 시작" --output-format json | jq -r '.session_id')
   claude -p --resume "$session_id" "계약서.pdf의 책임 조항을 검토해 주세요."
   claude -p --resume "$session_id" "GDPR 요구 사항 준수 여부를 확인해 주세요."
   claude -p --resume "$session_id" "위험 요소에 대한 경영진 요약을 생성해 주세요."
   ```

> **쉽게 말하면**: 세 예제 모두 패턴은 같습니다. **"역할 부여(누구처럼 행동해") + 권한 제한(뭘 쓸 수 있는지) + 결과를 JSON으로 받기"**. 이 세 가지 조합만 익히면 어떤 자동화든 응용할 수 있습니다.

### CI/CD 파이프라인 연동

깃허브 액션, 깃랩 CI, 젠킨스 같은 CI/CD 시스템에서 클로드 코드를 비대화형 모드로 호출해 **자동 코드 리뷰, 보안 감사, 문서 생성**을 할 수 있습니다.

CI/CD 통합 시 신경 써야 할 5가지:

1. **인증 관리**: API 키를 환경 변수로 주입하고, 로그에 노출되지 않도록 시크릿 관리 기능 사용
2. **타임아웃 설정**: `timeout` 명령으로 클로드 실행에도 시간제한을 걸어야 함
3. **오류 처리**: `--output-format json`으로 받아서 `is_error` 필드로 실패 감지, 실패 시 적절한 종료 코드 반환
4. **비용 관리**: `--max-turns`로 턴 수 제한, `total_cost_usd` 필드로 예산 모니터링
5. **속도 제한**: 여러 파일을 연속 처리할 때 요청 사이에 `sleep`(지연)을 넣어서 API 속도 제한에 안 걸리게 함

**깃허브 액션 예시**
```yaml
- name: Claude Code Review
  uses: anthropics/claude-code-action@v1
  with:
    prompt: "이 PR의 변경 사항을 리뷰하고 보안 취약점을 확인해 줘."
    output_format: json
    max_turns: 10
```

> **쉽게 말하면**: CI/CD 연동은 "회사 문 앞에 무인 경비 로봇을 세워두는 것"과 비슷합니다. 로봇이 멋대로 오래 일하지 않게(타임아웃), 문제 생기면 바로 알 수 있게(오류처리), 전기세 폭탄 안 맞게(비용관리), 너무 자주 왔다갔다 안 하게(속도제한) 미리 규칙을 정해두는 것입니다.

### 다중 턴 세션 관리 (고급 패턴)

첫 호출에서 세션을 시작하고 세션 ID를 뽑아낸 뒤, 이후 호출에서 `--resume`으로 같은 세션을 이어가며 **연속 작업**을 수행하는 패턴입니다. "코드 작성 → 테스트 실행 → 결과를 다시 클로드에게 전달해서 수정 요청"처럼 단계별 검증이 필요할 때 유용합니다.

```bash
# 1단계: API 엔드포인트 구현하고 세션 ID 저장
session_id=$(claude -p "API 엔드포인트 구현" --output-format json \
  --allowedTools "Read,Write,Edit,Bash" \
  --permission-mode acceptEdits | jq -r '.session_id')

# 2단계: 테스트 실행 후 결과를 같은 세션에 전달
test_result=$(npm test 2>&1)
claude -p --resume "$session_id" \
  "테스트 결과: $test_result. 실패한 테스트를 수정하라." \
  --output-format json
```

### 에이전트 SDK: 비대화형 모드의 확장

공식 문서에서는 비대화형 모드를 포함하는 상위 개념을 **에이전트 SDK**라고 부릅니다. CLI의 `-p` 플래그, 파이썬 SDK, 타입스크립트 SDK가 다 여기 속합니다. CLI 플래그는 동일하게 유지되지만, SDK는 각 프로그래밍 언어에 자연스럽게 통합되는 **구조화된 응답 객체**(스트리밍 콜백, 권한 승인 콜백 등)를 제공합니다.

> **쉽게 말하면**: `-p` 플래그가 "터미널에서 명령어 한 줄 치는 것"이라면, SDK는 "내 코드(파이썬/타입스크립트) 안에서 함수처럼 클로드를 호출하는 것"입니다. 복잡한 시스템을 만들 때는 SDK 쪽이 다루기 편합니다.

### 구조화 출력: `--json-schema`

클로드의 응답을 **내가 미리 정한 JSON 형식**에 딱 맞춰서 받고 싶을 때 씁니다.

```bash
$ claude -p "auth.py에서 함수 이름을 추출해 줘." \
  --output-format json \
  --json-schema '{"type":"object","properties":{"functions":{"type":"array","items":{"type":"string"}}}}'
```

→ 결과의 `structured_output` 필드에 `{"functions": ["login", "logout", "verify_token"]}` 같은 정해진 형태의 데이터가 들어옵니다.

> **쉽게 말하면**: 클로드에게 "아무렇게나 답하지 말고, 이 양식(엑셀 서식)에 맞춰서 답해줘"라고 강제하는 기능입니다. 뒤에 이어지는 프로그램이 데이터를 파싱하다가 에러 나는 걸 막아줍니다.

### 비대화형 모드 사용 시 주의할 점 (체크리스트)

- **JSON 출력 사용**: 프로그램이 결과를 파싱해야 하면 반드시 `--output-format json` 사용 (텍스트는 구조가 없어서 파싱이 불안정)
- **오류 처리**: 종료 코드와 stderr를 확인해서 실패를 우아하게 처리. "클로드는 항상 성공한다"고 가정하면 안 됨
- **세션 활용**: 맥락을 유지해야 하면 세션 기능 사용 (매번 새 세션 시작하면 이전 맥락이 사라져 비효율적)
- **타임아웃 적용**: 장시간 작업엔 `timeout` 명령으로 시간제한 (무한 대기 방지)
  ```bash
  $ timeout 300 claude -p "$prompt"   # 5분(300초) 후 강제 종료
  ```
- **속도 제한 존중**: 연속 요청 사이에 지연 추가
  ```bash
  for file in *.ts; do
      claude -p "Review $file" --output-format json >> reviews.jsonl
      sleep 2   # 2초 대기
  done
  ```

**비용 고려사항**: 프롬프트를 간결하게 유지, 필요한 파일만 분석 대상으로 제한, `--max-turns`로 턴 수 제한, 결과 캐싱으로 중복 호출 방지가 비용 관리 전략입니다.

## 7-2 훅(Hooks) 시스템 (p.201~214)

### 훅이란 무엇인가

훅은 클로드 코드의 **생애 주기(라이프사이클) 중 정해진 시점**에 자동으로 실행되는 커스텀 셸 명령어, LLM 프롬프트, 또는 에이전트 작업입니다.

가장 중요한 포인트: 훅은 **"AI의 판단"에 기대지 않고, 특정 작업이 반드시 실행되도록 보장**합니다.

> **쉽게 말하면**: "코드 작성 후 포맷팅해 줘"라고 클로드에게 부탁하는 것은 AI가 "까먹고 안 할 수도" 있습니다. 반면 "파일을 수정할 때마다(PostToolUse 시점) 자동으로 포맷터를 실행하라"고 훅에 등록해두면, **AI의 기분과 상관없이 매번 무조건** 실행됩니다. 즉 훅은 "약속"이 아니라 "자동 반사 신경"입니다.

훅으로 할 수 있는 것: 셸 명령어 자동 로깅, 코드 파일 자동 포맷팅, 규정 준수 추적, 민감한 파일 편집 차단 등.

### 훅의 3가지 타입

| 타입 | 하는 일 | 언제 적합한가 |
|---|---|---|
| `command` | bash 셸에서 명령을 직접 실행 | 포맷터, 린터, 유효성 검사 스크립트처럼 규칙이 딱 정해진 결정론적 작업 |
| `prompt` | LLM에 프롬프트를 전달해서 단일 턴 평가 수행 | 단순 규칙으로는 처리 못 하는 복잡한 판단이 필요할 때 |
| `agent` | 서브에이전트를 만들어서 Read, Grep, Glob 등 도구로 다중 턴 검증 수행 | 실제 파일 내용이나 테스트 출력을 검사해야 할 때 |

> **쉽게 말하면**: `command`는 "정해진 매뉴얼대로 딱딱 움직이는 로봇팔", `prompt`는 "한 번 슥 보고 판단하는 검사관", `agent`는 "여러 서류를 뒤져가며 꼼꼼히 조사하는 수사관" 정도로 생각하면 됩니다.

### 클로드 코드 생애 주기와 14개 훅 이벤트 (그림 7-2)

클로드 코드가 세션을 시작해서 끝날 때까지의 흐름은 대략 다음과 같습니다.

```
세션 시작 → 사용자 프롬프트 → 도구 호출 준비 → (권한 필요?) → 도구 실행
  → (성공?) → 결과 처리/실패 처리 → (더 작업?) → 응답 완료 → 세션 종료
```

이 흐름의 각 지점마다 "훅 실행"이라는 개입 지점이 있습니다. 총 14개 이벤트를 표로 정리하면 다음과 같습니다 (책에 나온 순서대로).

| 이벤트 | 발생 시점 | 쉬운 설명 |
|---|---|---|
| **SessionStart** | 세션이 시작되거나 재개될 때 | "출근 체크" — 환경 초기화, 필수 설정 확인 |
| **UserPromptSubmit** | 프롬프트를 제출했을 때, 처리 전 | "질문 접수창구" — 프롬프트 검증/로깅 |
| **PreToolUse** | 도구 호출 실행 전 (차단 가능) | "출입 전 검문소" — 위험한 행동을 사전 차단 |
| **PermissionRequest** | 권한 요청 다이얼로그가 나타날 때 | "허가서 도장 찍는 순간" |
| **PostToolUse** | 도구 호출이 성공적으로 완료된 후 | "작업 완료 후 뒷정리" — 자동 포맷팅, 린트 |
| **PostToolUseFailure** | 도구 호출이 실패한 후 | "사고 접수" — 실패 로깅, 알림 |
| **Notification** | 클로드 코드가 알림을 전송할 때 | "안내 방송" |
| **SubagentStart** | 서브에이전트가 생성될 때 | "파견 직원 투입" |
| **SubagentStop** | 서브에이전트가 종료될 때 | "파견 직원 복귀 보고" |
| **Stop** | 클로드가 응답 생성을 완료할 때 | "메인 작업자가 손 놓는 순간" |
| **TeammateIdle** | 에이전트 팀의 팀원이 유휴 상태로 전환되려 할 때 | "팀원이 쉬려고 할 때 품질 검사 강제" |
| **TaskCompleted** | 태스크가 완료로 표시될 때 | "할 일 체크박스 클릭 직전 검증" |
| **InstructionsLoaded** | CLAUDE.md나 규칙 파일이 로드될 때 | "사규집을 펼치는 순간" |
| **ConfigChange** | 세션 도중 설정 파일이 변경될 때 | "회사 규정이 바뀐 순간" |
| **WorktreeCreate / WorktreeRemove** | 작업 트리가 생성/제거될 때 | "임시 사무실을 열고/닫을 때" |
| **PreCompact** | 컨텍스트 압축이 실행되기 전 | "책상 정리하기 직전" |
| **SessionEnd** | 세션이 종료될 때 | "퇴근" |

(그림 7-2에는 14개 대표 이벤트가 표시되어 있고, 표 7-1과 이후 본문에서 InstructionsLoaded 등 추가 이벤트까지 상세히 설명합니다.)

모든 이벤트는 **stdin으로 JSON 데이터**를 훅에 넘겨줘서, 훅 스크립트가 "지금 무슨 상황인지" 정확히 알 수 있게 해줍니다. 공통 필드는 `session_id`(세션 식별자), `transcript_path`(대화 JSON 경로), `cwd`(작업 디렉터리), `permission_mode`(현재 권한 모드), `hook_event_name`(이벤트 이름)입니다.

### 주요 이벤트별 상세 설명 (쉬운 말로)

**SessionStart** — 새 세션이 시작되거나(`startup`), `--resume`/`--continue`로 재개되거나(`resume`), `/clear`로 초기화되거나(`clear`), 컴팩트가 수행될 때(`compact`) 발생. 대표 활용: `CLAUDE_ENV_FILE`이라는 환경 변수 파일에 `export` 문을 써두면, 세션 내내 그 환경 변수가 유지됩니다. (nvm, pyenv 같은 버전 관리 도구의 환경을 로딩할 때 유용)

```bash
#!/bin/bash
# SessionStart 훅: 환경 변수 영속화 예제
if [ -n "$CLAUDE_ENV_FILE" ]; then
  echo 'export NODE_ENV=production' >> "$CLAUDE_ENV_FILE"
  echo 'export DEBUG_LOG=true' >> "$CLAUDE_ENV_FILE"
fi
exit 0
```

**UserPromptSubmit** — 사용자가 프롬프트를 제출했을 때, 클로드가 처리하기 **전**에 실행. 프롬프트 검증, 컨텍스트 추가, 로깅에 활용.

**PreToolUse** — 클로드가 도구의 매개변수를 만든 뒤, 실제로 도구를 호출하기 **직전**에 발생. **도구 실행을 사전에 차단할 수 있는 핵심 지점**입니다.
```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "데이터베이스 쓰기가 허용되지 않음",
    "additionalContext": "현재 환경: 프로덕션. 주의하여 진행할 것"
  }
}
```
→ `permissionDecision`이 `allow`(우회 허용) / `deny`(거부) / `ask`(사용자 확인 요청) 세 가지로 갈립니다.

**PermissionRequest** — 권한 승인 대화상자가 실제로 뜨는 시점. `behavior`가 `allow`/`deny`로 승인 여부를 결정하고, `interrupt: true`로 클로드 작업을 강제 중단시킬 수도 있습니다.

**PostToolUse** — 도구가 **성공적으로 완료된 직후**. 파일 작성 후 자동 포맷팅, 코드 변경 후 린트 검사에 활용.

**PostToolUseFailure** — 도구 호출이 **실패했을 때**. 실패 로깅, 알림 전송에 활용.

**Notification** — 클로드가 알림을 보낼 때(권한 승인 필요, 유휴 상태, 인증 성공 등). 알림을 막을 수는 없지만, 추가 컨텍스트는 넣을 수 있습니다.

**SubagentStart / SubagentStop** — 서브에이전트(하위 작업자)가 생성되거나 응답을 완료했을 때. `SubagentStop`에서 `decision`을 `"block"`으로 하면 서브에이전트를 계속 작업시킬 수 있습니다.

**Stop** — **메인** 클로드 코드가 응답 생성을 완료했을 때 (사용자가 중간에 끊으면 발생 안 함). 세션 요약, 완료 보고서 작성에 활용. `decision`을 `"block"`으로 하면 종료를 막고 대화를 계속시킬 수 있는데, 이때 `reason`은 필수입니다.

**TeammateIdle** — (에이전트 팀 환경에서) 팀원 에이전트가 자기 턴을 마치고 쉬려고 할 때. **"작업을 끝내기 전에 품질 검사를 강제"**하는 용도로 쓰입니다. 종료 코드 2를 반환하면 유휴 전환을 막고 계속 작업시킬 수 있습니다.
```bash
#!/bin/bash
# TeammateIdle 훅: 빌드 아티팩트 검증
if [ ! -f "./dist/output.js" ]; then
  echo "빌드 아티팩트가 없습니다. 중단 전에 빌드를 실행하세요." >&2
  exit 2
fi
exit 0
```

**TaskCompleted** — 작업이 "완료"로 표시되려 할 때. 종료 코드 2를 반환하면 완료 표시를 막을 수 있습니다.
```bash
#!/bin/bash
# TaskCompleted 훅: 테스트 통과 검증
INPUT=$(cat)
TASK_SUBJECT=$(echo "$INPUT" | jq -r '.task_subject')
if ! npm test 2>&1; then
  echo "테스트 미통과. 작업 완료 전에 테스트를 수정하세요: $TASK_SUBJECT" >&2
  exit 2
fi
exit 0
```

**PreCompact** — 대화 컨텍스트를 압축해서 토큰 사용량을 줄이기 **직전**. `manual`(수동)/`auto`(자동) 트리거 구분.

**SessionEnd** — 세션 종료 시. 로그 저장, 임시 파일 정리, 사용량 통계 전송에 활용. 이 훅은 세션 종료 자체를 차단할 수 없습니다.

**ConfigChange** — 설정 파일이 변경될 때. 린트 규칙 재로드, 팀 설정 동기화 트리거에 활용.

**WorktreeCreate / WorktreeRemove** — 깃 작업 트리가 생성/제거될 때. 예: 작업 트리 생성 시 의존성 자동 설치.
```json
{
  "hooks": {
    "WorktreeCreate": [{
      "type": "command",
      "command": "cd $CLAUDE_WORKTREE_PATH && npm install"
    }]
  }
}
```

### 종료 코드와 결정 제어 체계 (그림 7-3)

훅의 실행 결과는 **종료 코드** 또는 **JSON 출력**, 둘 중 하나로 클로드 코드에 전달됩니다 (훅별로 한 가지만 선택).

- **종료 코드 0** = 성공. stdout에 JSON을 출력하면 그걸 파싱함
- **종료 코드 2** = 차단 오류. stdout/JSON은 무시하고, **stderr 텍스트를 클로드에게 오류 메시지로 전달**. 이벤트별로 차단 효과가 다릅니다.
  - `PreToolUse` → 도구 호출 차단
  - `PermissionRequest` → 권한 거부
  - `UserPromptSubmit` → 프롬프트 처리 차단(프롬프트 삭제)
  - `Stop` → 종료 방지, 대화 계속
  - `SubagentStop` → 서브에이전트 종료 방지
  - `TeammateIdle` → 팀원 유휴 전환 방지
  - `TaskCompleted` → 작업 완료 표시 방지
  - 반면 `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SessionStart`, `SessionEnd`, `PreCompact`에서는 종료 코드 2가 **차단 효과를 갖지 않음** (stderr가 사용자에게만 보이거나 클로드에게 피드백으로만 전달)
- **기타 종료 코드(1, 3 등)** = 차단되지 않는 오류. stderr가 상세 모드에서만 표시되고 실행은 계속됨

> **쉽게 말하면**: 종료 코드는 신호등입니다. 0(초록불)은 "정상 통과", 2(빨간불)는 "여기서 멈춰!"인데 그 빨간불이 실제로 브레이크 역할을 하는 이벤트가 정해져 있고, 나머지 코드(1, 3 등)는 그냥 "경고등 깜빡"일 뿐 차는 계속 갑니다.

JSON 출력으로 더 정교한 제어도 가능합니다. 모든 이벤트 공통 필드:
- `continue`: `false`면 클로드가 완전히 중단
- `stopReason`: `continue`가 `false`일 때 사용자에게 보여줄 메시지
- `suppressOutput`: `true`면 stdout을 상세 모드에서 숨김
- `systemMessage`: 사용자에게 표시되는 경고 메시지

이벤트별 결정 제어 패턴은 3가지로 분류됩니다.
1. `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure`, `Stop`, `SubagentStop` → 최상위 `decision`(`"block"`) + `reason` 필드 사용
2. `PreToolUse` → `hookSpecificOutput` 내부의 `permissionDecision`(`allow`/`deny`/`ask`) + `permissionDecisionReason`
3. `PermissionRequest` → `hookSpecificOutput` 내부의 `decision.behavior`(`allow`/`deny`)

`TeammateIdle`과 `TaskCompleted`는 JSON 결정 제어를 지원하지 않고 **종료 코드로만** 제어합니다.

### 훅 구성 파일과 우선순위

훅 설정 파일은 여러 레벨로 존재합니다.
- 사용자 설정: `~/.claude/settings.json`
- 프로젝트 설정: `.claude/settings.json`
- 로컬 프로젝트 설정: `.claude/settings.local.json`
- (기업 환경) 엔터프라이즈 관리 정책 설정
- 플러그인: `hooks/hooks.json`
- 스킬/에이전트: 프론트매터에 직접 정의

설정 구조는 3단계로 중첩됩니다.
1. **훅 이벤트 선택** (예: `PreToolUse`)
2. **매처(matcher) 그룹으로 실행 조건 필터링** (예: `Bash` 도구를 쓸 때만)
3. **하나 이상의 훅 핸들러 정의**

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  }
}
```

훅 핸들러 공통 필드: `type`(command/prompt/agent 중 하나), `timeout`(시간 초과 — command 기본 600초, prompt 기본 30초, agent 기본 60초), `statusMessage`(훅 실행 중 표시되는 스피너 메시지), `once`(true면 세션당 한 번만 실행, 스킬에서만 사용). `command` 타입은 추가로 `command`(셸 명령)와 `async` 필드를 가집니다.

> **쉽게 말하면**: 훅 설정은 "if 이벤트가 X이고, 대상이 Y라면 → Z를 실행하라"는 규칙을 JSON으로 적어두는 것입니다. 매처는 "이 규칙을 모든 경우가 아니라 특정 도구/조건에서만 발동시키는" 필터입니다.

### 훅 매처 패턴 이해하기 (p.215)

매처(matcher)는 훅이 어떤 조건에서 실행될지를 결정하는 정규식 문자열입니다. **이벤트마다 매칭 대상이 다릅니다.**

- `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest` → **도구 이름**에 매칭. `Write`는 Write 도구에만 정확히 일치, `Edit|Write`는 Edit 또는 Write에 일치, `Notebook.*`는 Notebook으로 시작하는 모든 도구에 일치. MCP 도구는 `mcp__<server>__<tool>` 패턴을 따름 (`mcp__memory__.*`는 memory 서버의 모든 도구, `mcp__.*__write.*`는 모든 서버의 Write 관련 도구)
- `SessionStart` → 세션 시작 방식에 매칭(`startup`, `resume`, `clear`, `compact`)
- `SessionEnd` → 세션 종료 사유에 매칭(`clear`, `logout`, `prompt_input_exit`, `bypass_permissions_disabled`, `other`)
- `Notification` → 알림 유형에 매칭(`permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`)
- `SubagentStart`/`SubagentStop` → 에이전트 타입에 매칭
- `PreCompact` → 실행 방식에 매칭(`manual`, `auto`)
- `UserPromptSubmit`, `Stop`, `TeammateIdle`, `TaskCompleted` → **매처를 지원하지 않음**, 모든 발생 시 실행됨 (matcher 필드를 넣어도 조용히 무시됨)
- 매처를 빈 문자열로 두거나 `*`를 쓰거나 생략하면 해당 이벤트의 모든 발생에 일치

> **쉽게 말하면**: 매처는 "이 훅을 아무 때나 발동시키지 말고, 특정 상황(특정 도구/특정 세션 시작 방식 등)에서만 발동시켜라"는 조건 필터입니다. 단, 일부 이벤트(UserPromptSubmit 등)는 애초에 "상황을 구분할 게 없어서" 필터를 걸 수 없습니다.

### 프롬프트 기반 훅과 에이전트 기반 훅 (p.216~217)

`command` 타입 외에 클로드 코드는 LLM을 활용하는 두 가지 고급 훅 타입을 지원합니다.

**프롬프트 기반 훅** (`type: "prompt"`)은 훅 입력과 개발자의 프롬프트를 클로드 모델(기본은 빠른 모델)에 전송해서 **단일 턴 평가**를 수행합니다. 모델은 `{"ok": true}` 또는 `{"ok": false, "reason": "설명"}` 형식의 JSON으로 응답하고, 클로드 코드가 이 결정을 자동 처리합니다. `$ARGUMENTS` 플레이스홀더로 훅의 JSON 입력 데이터를 프롬프트에 삽입할 수 있습니다.

지원 이벤트: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `TaskCompleted` (`TeammateIdle`은 미지원)

```json
{
  "hooks": {
    "Stop": [{
      "hooks": [{
        "type": "prompt",
        "prompt": "클로드가 중단해야 하는지 평가하라. 컨텍스트: $ARGUMENTS\n\n모든 요청 작업이 완료되었는지, 해결이 필요한 오류가 있는지, 후속 작업이 필요한지 분석하라.\n\nJSON으로 응답: {\"ok\": true} 중단 허용 또는 {\"ok\": false, \"reason\": \"설명\"} 계속 작업.",
        "timeout": 30
      }]
    }]
  }
}
```

**에이전트 기반 훅** (`type: "agent"`)은 프롬프트 기반 훅과 유사하지만, 단일 LLM 호출 대신 **Read, Grep, Glob 같은 도구를 사용할 수 있는 서브에이전트를 생성**하여 다중 턴 검증을 수행합니다. 최대 50턴까지 실행 가능하며, 실제 파일이나 테스트 출력의 검사가 필요한 경우에 적합합니다. 지원 이벤트와 응답 스키마는 프롬프트 기반 훅과 동일합니다.

```json
{
  "hooks": {
    "Stop": [{
      "hooks": [{
        "type": "agent",
        "prompt": "모든 단위 테스트가 통과하는지 검증하라. 테스트 스위트를 실행하고 결과를 확인하라. $ARGUMENTS",
        "timeout": 120
      }]
    }]
  }
}
```

> **쉽게 말하면**: `command`가 "정해진 매뉴얼대로 움직이는 로봇팔"이라면, `prompt`는 "한 번 슥 보고 OK/NO를 판단하는 검사관", `agent`는 "직접 파일을 뒤지고 테스트까지 돌려보고 판단하는 수사관"입니다. 뒤로 갈수록 더 똑똑하지만 더 느리고 비쌉니다.

### 비동기 훅 (p.217)

보통 훅은 클로드의 실행이 완료될 때까지 **차단(blocking)**합니다. 배포, 테스트 스위트, 외부 API 호출 같은 장시간 작업의 경우, `"async": true`를 설정하면 훅을 백그라운드에서 실행할 수 있습니다. 클로드는 훅의 완료를 기다리지 않고 즉시 다음 작업을 계속합니다.

비동기 훅은 `command` 타입에서만 지원되며, **차단이나 결정 제어가 불가능**합니다. 훅이 완료되면 `systemMessage`나 `additionalContext` 필드의 내용이 **다음 대화 턴**에서 클로드에게 전달됩니다. 각 실행은 별도의 백그라운드 프로세스로 생성되며, 동일한 비동기 훅의 여러 실행 간 중복 제거는 수행되지 않습니다.

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{
        "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/run-tests-async.sh",
        "async": true,
        "timeout": 300
      }]
    }]
  }
}
```

> **쉽게 말하면**: 보통 훅은 "그 자리에서 결과를 기다리는" 방식이라 오래 걸리는 작업을 걸면 클로드가 계속 멈춰 있습니다. `async: true`는 "일 시켜놓고 결과는 나중에 듣는" 방식이라, 배포처럼 오래 걸리는 작업에 적합합니다. 대신 그 훅으로 "안 돼, 하지 마"라고 막는 건 불가능합니다.

### 프론트매터 훅과 에이전트 범위 훅 (p.218~219)

훅은 설정 파일 외에 **스킬이나 에이전트의 YAML 프론트매터**에 직접 정의할 수도 있습니다. 프론트매터 훅은 해당 컴포넌트의 생애 주기에 한정되어 동작하며, 컴포넌트가 활성화되는 동안에만 실행되고 종료되면 자동으로 정리됩니다. 모든 훅 이벤트가 지원되며, 에이전트의 경우 `Stop` 훅은 자동으로 `SubagentStop`으로 변환됩니다.

```yaml
---
name: secure-operations
description: 보안 검증이 포함된 작업 수행
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/security-check.sh"
---
```

프론트매터 훅에서 특히 주목할 옵션은 `once: true` 설정입니다. 이 옵션이 활성화된 훅은 **세션당 한 번만** 실행됩니다. 초기화 작업이나 일회성 설정에 유용하며, 새로운 세션이 시작되면 카운터가 초기화되어 다시 한번 실행됩니다.

프론트매터 훅과 전역 훅(`settings.json`에 정의)은 **상호 배타적이지 않습니다.** 전역 훅은 항상 활성화되어 있고, 프론트매터 훅은 해당 컴포넌트의 컨텍스트에서만 추가로 활성화됩니다. 동일한 이벤트에 대해 둘 다 정의되어 있으면 **모두 실행됩니다.**

플러그인의 훅은 `hooks/hooks.json` 파일에 정의되며, 플러그인이 활성화되면 사용자 훅 및 프로젝트 훅과 병합됩니다. `${CLAUDE_PLUGIN_ROOT}` 환경 변수를 사용하여 플러그인에 번들된 스크립트를 참조할 수 있습니다.

### 실용적인 훅 예제 (p.219~221)

**위험한 셸 명령 차단** — `PreToolUse` 훅에서 stdin의 JSON 입력을 읽어 명령을 분석하고, `rm -rf`가 포함되면 도구 호출을 거부합니다.
```bash
#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')
if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "위험한 명령이 훅에 의해 차단됨"
    }
  }'
fi
exit 0
```

**코드 포매팅 자동화** — 타입스크립트 파일을 작성하거나 편집할 때마다 Prettier를 자동으로 실행합니다.
```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "FILE=$(cat | jq -r '.tool_input.file_path // .tool_response.filePath // empty'); if [[ \"$FILE\" == *.ts ]] || [[ \"$FILE\" == *.tsx ]]; then npx prettier --write \"$FILE\"; fi"
      }]
    }]
  }
}
```

**민감한 파일 보호** — `.env` 파일이나 `.git/` 디렉터리의 파일 편집을 차단합니다.
```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "FILE=$(cat | jq -r '.tool_input.file_path // empty'); if [[ \"$FILE\" == *.env* ]] || [[ \"$FILE\" == *.git/* ]]; then echo '보호된 파일' >&2; exit 2; fi"
      }]
    }]
  }
}
```

**세션 로깅** — 세션 시작과 종료 시 로그를 기록합니다.
```json
{
  "hooks": {
    "SessionStart": [{
      "matcher": "",
      "hooks": [{
        "type": "command",
        "command": "echo \"[$(date)] 세션 시작: $(pwd)\" >> ~/.claude/session.log"
      }]
    }],
    "SessionEnd": [{
      "matcher": "",
      "hooks": [{
        "type": "command",
        "command": "echo \"[$(date)] 세션 종료\" >> ~/.claude/session.log"
      }]
    }]
  }
}
```

**프롬프트 기반 Stop 훅** — 클로드가 모든 작업을 완료했는지 LLM이 평가한 후 종료를 허용합니다.
```json
{
  "hooks": {
    "Stop": [{
      "hooks": [{
        "type": "prompt",
        "prompt": "대화를 분석하여 다음을 판단하라: 1) 모든 요청 작업이 완료되었는가, 2) 오류가 남아있는가, 3) 후속 작업이 필요한가. $ARGUMENTS\n\nJSON 응답: {\"ok\": true} 또는 {\"ok\": false, \"reason\": \"설명\"}",
        "timeout": 30
      }]
    }]
  }
}
```

### 보안 유의 사항 (p.222~223, 그림 7-4)

훅은 **현재 환경의 시스템 사용자 권한으로, 에이전트 루프 중에 자동으로 실행**됩니다. 이는 강력한 자동화 능력을 제공하지만 동시에 보안 위험도 수반합니다. 악의적인 훅 코드는 사용자 계정이 접근할 수 있는 모든 파일을 수정·삭제·접근할 수 있으므로, 등록 전에 구현을 반드시 검토해야 합니다. 공식 문서가 제시하는 다섯 가지 보안 유의 사항은 다음과 같습니다.

1. 입력 데이터를 맹목적으로 신뢰하지 말고 검증 및 살균(sanitization) 과정을 거쳐야 한다
2. 셸 변수는 항상 따옴표로 감싸야 한다. `$VAR`이 아닌 `"$VAR"` 형태로 사용하여 공백이나 특수 문자가 포함된 값을 안전하게 처리한다
3. 파일 경로에서 `..`를 확인하여 경로 순회 공격을 차단해야 한다
4. 스크립트를 참조할 때는 절대 경로를 사용하거나 `$CLAUDE_PROJECT_DIR` 환경 변수를 활용해야 한다
5. `.env`, `.git/`, 키 파일 등 민감한 파일은 건너뛰어야 한다

(그림 7-4 "훅 보안 검증 흐름": 훅 입력 → 경로 순회 확인(위험하면 차단) → 민감 파일 확인(위험하면 차단) → 안전하면 실행 허용 → 변수 인용 → 절대 경로 사용 → 제한된 권한 → 타임아웃 설정 순으로 안전하게 실행)

> **쉽게 말하면**: 훅은 "내 컴퓨터 계정으로 자동 실행되는 매크로"라서, 잘못 짜면 랜섬웨어처럼 파일을 다 지울 수도 있습니다. 위 5가지는 "낯선 사람이 준 심부름 쪽지(입력값)를 그대로 믿지 말고, 따옴표로 안전하게 포장하고, 상위 폴더로 못 나가게 막고, 정확한 주소(절대경로)로만 심부름을 보내고, 금고(.env, .git)는 절대 건드리지 마라"는 안전수칙입니다.

### 훅 실행의 특성과 디버깅 (p.223)

훅 실행에는 몇 가지 특성이 있습니다. 첫째, 동일한 이벤트에 대해 여러 훅이 등록되어 있으면 **병렬로 실행**됩니다. 둘째, 완전히 동일한 훅 핸들러는 자동으로 중복 제거됩니다. 셋째, 기본 시간제한은 `command` 600초, `prompt` 30초, `agent` 60초이며, 개별 훅의 `timeout` 필드로 별도 설정이 가능합니다. 넷째, 훅은 현재 작업 디렉터리에서 클로드 코드의 환경으로 실행됩니다. 다섯째, 원격 웹 환경에서는 `$CLAUDE_CODE_REMOTE` 환경 변수가 `"true"`로 설정됩니다.

디버깅이 필요한 경우 `claude --debug` 플래그로 클로드 코드를 실행하면 훅 실행 세부 사항을 확인할 수 있습니다. 어떤 훅이 매칭되었는지, 종료 코드, 출력 내용 등이 로그에 표시됩니다. `Ctrl+O`로 상세 모드를 토글하여 훅 진행 상황을 트랜스크립트에서 확인할 수도 있습니다.

기본 문제 해결 단계: `/hooks` 명령으로 훅이 올바르게 등록되었는지 확인 → 설정 파일의 JSON 구문이 유효한지 검증 → 훅 명령을 터미널에서 직접 실행하여 동작을 테스트 → 스크립트 파일의 실행 권한(`chmod +x`)을 확인 → 셸 프로파일이 시작 시 텍스트를 출력하여 JSON 파싱을 방해하는지 확인.

### 체크포인팅 보완을 위한 훅 활용 (p.224~225)

6장에서 설명했듯이 클로드 코드의 체크포인팅 시스템은 Read, Write, Edit 같은 **직접 파일 조작 도구만 추적**합니다. Bash 도구를 통해 실행된 `rm`, `mv`, `cp` 같은 셸 명령은 체크포인팅으로 복구할 수 없습니다. 이는 bash 명령이 클로드 외부에서 실행되기 때문입니다. 이 제한을 해결하기 위해 `pre-bash`와 `post-bash` 훅을 결합한 **스마트 하이브리드 전략**을 제안합니다.

가장 간단한 방법은 bash 명령 실행 후 자동으로 깃 커밋을 생성하는 것입니다.
```bash
# .claude/hooks/post-bash.sh
#!/bin/bash
INPUT=$(cat)
git add -A
git commit -m "Auto-commit after bash command" --allow-empty
```

성능과 안정성을 모두 확보하는 향상된 접근 방식은, 위험한 명령어만 필터링해서 **사전 백업**하고, 실제 변경이 있을 때만 커밋하는 것입니다.
```bash
# .claude/hooks/pre-bash.sh
#!/bin/bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')
# 위험한 명령어만 필터링하여 사전 백업
if echo "$COMMAND" | grep -qE '^(rm|mv|cp|mkdir|touch)'; then
    git stash push -m "pre-bash-backup-$(date +%s)" --quiet
fi

# .claude/hooks/post-bash.sh
#!/bin/bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')
# 위험한 명령에 대해서만 결과 커밋
if echo "$COMMAND" | grep -qE '^(rm|mv|cp|mkdir|touch)'; then
    if ! git diff --quiet; then
        git add -A
        git commit -m "File operation: $COMMAND" --allow-empty
        git stash pop --quiet 2>/dev/null || true
    fi
fi
```

스마트 하이브리드 전략은 세 가지 핵심 장점을 제공합니다.

1. **최적의 성능과 안정성 균형**: 실제로 파일 변경이 발생했을 때만 깃 커밋을 생성하므로 불필요한 오버헤드를 방지하고, 동시에 `pre-bash` 훅에서 미리 상태를 저장해두기 때문에 명령 실행이 실패하거나 예상치 못한 결과가 발생했을 때 즉시 이전 상태로 복구할 수 있다
2. **스마트 감지 메커니즘**: `git diff --quiet` 명령을 활용하여 실제로 파일 시스템에 변경이 발생했는지를 정확하게 감지한다. 단순히 명령이 실행되었다는 사실이 아니라 실제로 의미 있는 변경이 있었는지를 기준으로 커밋 여부를 결정하므로 Git 히스토리가 깨끗하게 유지된다
3. **향상된 추적성**: 커밋 메시지에 실제로 실행된 bash 명령을 포함하므로 각 변경이 어떤 명령에 의해 발생했는지 명확하게 식별할 수 있다

> **쉽게 말하면**: 체크포인팅(6장)은 클로드가 파일 도구로 직접 고친 것만 "되돌리기" 버튼이 있습니다. 그런데 `rm`, `mv` 같은 터미널 명령으로 지운 건 되돌리기 버튼이 없어요. 그래서 "위험한 명령을 실행하기 직전에 몰래 스냅샷을 찍어두고(pre-bash), 실행 후 실제로 뭔가 바뀌었으면 그 스냅샷을 깃 커밋으로 남기는(post-bash)" 자동 안전망을 만드는 것입니다.

### HTTP 훅 (p.225~226)

기존의 `command` 타입 훅은 로컬 셸 명령을 실행하는 방식입니다. 클로드 코드는 이에 더해 `type: "http"` 훅을 지원합니다. HTTP 훅은 지정된 URL로 POST 요청을 전송하여 원격 서비스와 연동합니다. 팀 공유 감사 서비스, 중앙 로깅 시스템, 알림 서비스 등 외부 시스템과의 통합에 적합합니다.

```json
{
  "hooks": {
    "PostToolUse": [{
      "type": "http",
      "url": "https://audit.example.com/claude-events",
      "matcher": "Write"
    }]
  }
}
```

HTTP 훅은 이벤트 데이터를 JSON 형식으로 POST 요청의 본문에 포함하여 전송합니다. 로컬 셸 명령 실행이 불가능한 제한된 환경에서도 외부 서비스와의 연동을 구현할 수 있다는 점에서 `command` 타입 훅의 보완 역할을 합니다.

> **쉽게 말하면**: `command` 훅이 "내 컴퓨터 안에서 심부름"이라면, HTTP 훅은 "택배로 소식을 다른 회사(외부 서버)에 보내는 것"입니다. 셸 명령을 못 쓰는 환경에서도 "무슨 일이 있었는지"를 외부에 알릴 수 있습니다.

## 7-3 MCP 통합으로 외부 세계와의 연결 확장 (p.226~233)

### MCP란 무엇인가

MCP(Model Context Protocol)는 AI 에이전트가 **외부 시스템과 상호작용하기 위한 표준화된 프로토콜**입니다. 전통적인 API 통합은 서비스별로 고유한 방식과 인증 절차를 요구하지만, MCP는 단일화된 인터페이스를 통해 다양한 서비스에 접근할 수 있게 해줍니다. 개발자가 매번 새로운 통합 방식을 학습할 필요 없이, MCP 표준만 이해하면 어떤 서비스든 클로드 코드와 연결할 수 있습니다.

(그림 7-5 "클로드 코드와 MCP 서버 생태계": 클로드 코드는 내장 도구(Read/Write, Bash, Grep/Glob, WebSearch)와 MCP 서버들(GitHub→이슈 추적, Notion→문서 관리, Database→데이터 쿼리, Monitoring→오류 모니터링, Design Tools→디자인 통합, 기타)로 뻗어나가는 생태계를 이룸)

MCP의 핵심 가치는 **생태계 확장성**에 있습니다. 클로드 코드의 내장 도구가 로컬 파일 시스템과 터미널 작업을 처리한다면, MCP 서버는 클라우드 서비스, 데이터베이스, 모니터링 도구, 협업 도구 등 외부 리소스를 클로드 코드의 도구로 변환합니다. 덕분에 클로드 코드는 사용자의 모든 디지털 워크플로를 관리하는 통합 허브가 될 수 있습니다.

> **쉽게 말하면**: MCP는 "만능 어댑터"입니다. 노션, 깃허브, 슬랙, 데이터베이스 등 서비스마다 연결 방식이 다 다르면 매번 새로 배워야 하지만, MCP라는 표준 규격만 익히면 어떤 서비스든 클로드에 "USB처럼" 꽂아 쓸 수 있습니다.

### MCP 전송 방식

클로드 코드는 세 가지 전송 방식으로 MCP 서버와 통신할 수 있습니다. 선택 기준은 단순합니다: **로컬에서 실행되는 서버는 stdio, 원격 서버는 HTTP**를 사용합니다. SSE는 레거시 원격 서버가 HTTP 전송을 아직 지원하지 않는 경우에만 사용합니다.

**stdio 전송**은 로컬에서 실행되는 MCP 서버와 표준 입출력을 통해 통신하는 방식입니다. 프로세스 간 통신에 네트워크가 관여하지 않으므로 가장 빠르고 안정적입니다. npx로 실행하는 Node.js 기반 MCP 서버, 로컬 데이터베이스 연결, 파일시스템 기반 도구 등에 적합합니다.
```bash
# Airtable 서버 연결(환경 변수 사용)
$ claude mcp add --transport stdio airtable --env \
AIRTABLE_API_KEY=YOUR_KEY -- npx -y airtable-mcp-server

# PostgreSQL 데이터베이스 연결
$ claude mcp add --transport stdio db -- npx -y @bytebase/dbhub \
--dsn "postgresql://readonly:[email protected]:5432/analytics"
```

**HTTP 전송**은 원격 서버와 HTTP 프로토콜을 통해 통신하는 방식입니다. 클라우드에서 호스팅되는 MCP 서버에 접근할 때 사용됩니다. REST API 기반의 통신을 통해 안정적인 연결을 제공하며, 인증 헤더를 포함한 다양한 설정을 지원합니다. 노션, 깃허브, Stripe 등 주요 서비스에서 HTTP 전송 기반의 MCP 서버를 제공합니다.
```bash
# Notion 서버 연결
$ claude mcp add --transport http notion https://mcp.notion.com/mcp

# 인증이 필요한 API 서버 연결
$ claude mcp add --transport http secure-api \
https://api.example.com/mcp --header "Authorization: Bearer your-token"
```

**SSE(Server-Sent Events) 전송**은 공식 문서에서 더 이상 권장되지 않습니다(deprecated). 기존에 SSE를 사용하던 서버가 아직 HTTP 전송으로 마이그레이션하지 않은 경우에만 사용하며, 서버 측에서 HTTP 전송을 지원하게 되면 즉시 전환하는 것이 바람직합니다.

MCP 서버는 CLI 명령으로 관리할 수 있습니다. `claude mcp list`는 구성된 모든 서버를 나열하고, `claude mcp get <name>`은 특정 서버의 상세 정보를 표시하며, `claude mcp remove <name>`은 서버를 제거합니다. 클로드 코드 세션 내에서는 `/mcp` 명령으로 서버 상태를 확인하고 OAuth 인증을 관리할 수 있습니다.

### 주요 MCP 서버 활용 사례

- **GitHub 통합**: 깃허브 MCP 서버를 통해 클로드 코드는 리포지토리 코드를 분석하고 PR을 검토하며 이슈를 자동으로 해결하는 코드를 생성할 수 있음
  ```bash
  $ claude mcp add --transport http github https://api.githubcopilot.com/mcp/
  > PR #456을 검토하고 개선 사항을 제안하세요.
  > 이슈 #123의 설명을 기반으로 버그 수정 코드를 작성해 주세요.
  ```
- **데이터베이스 직접 쿼리**: PostgreSQL 데이터베이스에 직접 연결하여 데이터를 조회·분석. 로그 분석, 사용자 행동 패턴 확인, 비즈니스 인텔리전스 생성 등에 활용
  ```bash
  > 지난 7일간 가장 많이 구매한 사용자 상위 10명을 조회해 주세요.
  > 월별 매출 추세를 분석하고 성장률을 계산해 주세요.
  ```
- **모니터링 도구 연동**: Sentry, Statsig 같은 서비스와 연결하여 문제를 진단하고 해결
  ```bash
  $ claude mcp add --transport http sentry https://mcp.sentry.dev/mcp
  > 지난 24시간 동안 가장 일반적인 오류는 무엇입니까?
  ```
- **디자인 도구 통합**: 피그마, 스케치 같은 디자인 도구와 연결하여 디자인 시스템을 코드로 변환. 디자이너와 개발자 간 협업을 크게 향상시킴
  ```bash
  > 피그마의 새로운 버튼 디자인을 React 컴포넌트로 변환해 주세요.
  ```

### MCP 서버 설정과 구현 방법 (3가지 범위)

클로드 코드는 세 가지 범위의 서버 구성을 지원합니다.

- **로컬 범위** (`--scope local`): 현재 프로젝트의 사용자에게만 적용. `.claude/settings.local.json`에 저장. 민감한 데이터나 개인적인 API 키를 사용할 때 적합
- **프로젝트 범위** (`--scope project`): 프로젝트 루트의 `.mcp.json` 파일에 저장되어 프로젝트의 모든 팀원과 공유됨. 팀 전체가 사용하는 공통 서비스(공유 데이터베이스, 팀 노션 등)에 적합
- **사용자 범위** (`--scope user`): 모든 프로젝트에서 접근 가능하며 `~/.claude/mcp.json`에 저장. 개인적으로 자주 사용하는 서비스(깃허브, 개인 데이터베이스 등)에 적합

> **엔터프라이즈 환경에서의 MCP 서버 관리**: 엔터프라이즈 환경에서는 MCP 서버에 대한 중앙 집중식 제어가 가능합니다. 관리자는 `managed-mcp.json` 파일을 통해 조직 전체에서 허용되는 MCP 서버와 차단되는 MCP 서버를 정의할 수 있습니다. 이 파일의 위치는 운영체제에 따라 다릅니다 (macOS: `/Library/Application Support/ClaudeCode/managed-mcp.json`, 윈도우: `C:\ProgramData\ClaudeCode\managed-mcp.json`, 리눅스: `/etc/claude-code/managed-mcp.json`). `allowedMcpServers`에 서버 이름을 등록하면 해당 서버만 사용 가능하고, `deniedMcpServers`에 등록하면 해당 서버가 차단됩니다.

### .mcp.json 구성과 환경 변수 확장

`.mcp.json` 파일은 프로젝트 루트 디렉터리에 위치하며 프로젝트 범위의 MCP 서버를 정의합니다. 팀 전체가 동일한 MCP 서버 구성을 공유하려면 이 파일을 버전 관리 시스템에 체크인하면 됩니다.

환경 변수 확장 기능을 통해 API 키와 같은 민감한 정보를 코드에 직접 노출하지 않고 관리할 수 있습니다. `.mcp.json` 파일에서 `${VAR}` 구문을 사용하여 환경 변수를 참조할 수 있습니다.

```json
{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      }
    }
  }
}
```

`${VAR:-default}` 구문은 환경 변수가 설정되지 않은 경우 기본값을 사용합니다 (`:-`는 하나의 연산자로, 변수가 미설정이거나 빈 값이면 default를 사용한다는 의미). 이러한 패턴을 통해 민감한 값은 환경 변수에만 두고 `.mcp.json`은 안전하게 버전 관리 시스템에 체크인할 수 있습니다.

**인증**: 원격 MCP 서버의 인증은 두 가지 방식으로 처리됩니다. 첫째, **OAuth 2.0 인증**은 많은 클라우드 기반 MCP 서버가 채택하는 표준 인증 방식입니다. 인증이 필요한 서버를 추가한 후, 클로드 코드 내에서 `/mcp` 명령을 실행하면 브라우저가 열리고 OAuth 인증 플로우가 시작됩니다. 사용자가 브라우저에서 로그인을 완료하면 토큰이 자동으로 클로드 코드에 저장되어 이후 요청에 사용됩니다. 둘째, **헤더 기반 인증**은 API 키나 Bearer 토큰을 HTTP 헤더에 직접 포함하는 방식입니다. `--header` 플래그나 `.mcp.json`의 `headers` 필드를 통해 인증 헤더를 지정합니다.

> **MCP 리소스와 프롬프트 기능**: MCP 서버는 리소스를 노출할 수 있으며, 이 리소스는 `@` 멘션으로 클로드 코드에서 참조할 수 있습니다. 예를 들어 `@github:issue://123`으로 GitHub 이슈를 참조하거나, `@docs:file://api/authentication`으로 문서를 참조할 수 있습니다. MCP 서버가 프롬프트를 노출하면 이 프롬프트가 클로드 코드에서 슬래시 명령으로 사용 가능해집니다.

### 훅과 MCP의 연동 전략

MCP 서버는 훅 시스템과 결합하면 강력한 자동화 워크플로를 구축할 수 있습니다.

**PostToolUse 훅과 MCP 연동**으로 파일 변경 후 외부 시스템에 자동으로 알림을 보낼 수 있습니다.
```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{
        "type": "prompt",
        "prompt": "파일이 변경되었습니다. @github:create_pr로 PR을 생성할까요?"
      }]
    }]
  }
}
```

**PreToolUse 훅으로 MCP 도구를 제어**하여 특정 조건에서만 MCP 서버를 사용하도록 제한할 수 있습니다.
```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "mcp__github__.*",
      "hooks": [{
        "type": "command",
        "command": "if [[ $TOOL_INPUT != *'repo:allowed-project'* ]]; then echo '허용되지 않은 리포지토리입니다.'; exit 2; fi"
      }]
    }]
  }
}
```

### 실제 프로젝트 적용 예시

**풀스택 애플리케이션 개발**에서는 요구 사항 정의부터 배포, 모니터링까지 전 단계에 걸쳐 MCP 서버를 연결할 수 있습니다. Jira로 이슈를 생성하고, Figma에서 API 설계를 참조하며, 데이터베이스 스키마를 직접 조회하고, GitHub Actions로 테스트를 실행한 뒤, Vercel로 배포하고 Sentry로 이상 징후를 감지하는 흐름을 단일 세션에서 처리할 수 있습니다.

(그림 7-6 "풀스택 애플리케이션 개발 워크플로": 요구 사항 → Jira 이슈(`@jira:issue`) → API 설계(`@figma`) → 프런트엔드 개발 → 데이터베이스 스키마(`@db`) → 백엔드 개발 → 테스트 실행(`@github:actions`) → 배포(`@vercel`) → 모니터링(`@sentry`), 이렇게 순환하는 흐름)

**SaaS 애플리케이션 운영**에서는 고객 대응과 비즈니스 분석에 필요한 서비스를 MCP로 연결할 수 있습니다. Stripe로 결제 데이터를 분석하고 환불을 처리하며, SendGrid로 이메일 템플릿을 업데이트하고 발송 현황을 확인하며, Google Analytics로 사용자 행동을 분석하고, Zendesk로 고객 지원 티켓을 분석하여 자동 응답을 제안할 수 있습니다.

> **쉽게 말하면**: MCP를 여러 개 연결하면 클로드 코드가 "기획(Jira) → 설계(Figma) → 개발 → DB → 테스트(GitHub) → 배포(Vercel) → 모니터링(Sentry)"까지 이어지는 하나의 "만능 콘솔"이 됩니다. 개발자가 여러 탭을 왔다갔다 하지 않아도, 클로드 코드 안에서 전체 사이클을 다룰 수 있는 겁니다.

### 유의 사항

보안 측면에서 MCP 서버는 클로드 코드에 외부 시스템에 대한 접근 권한을 부여하므로 신중한 관리가 필요합니다. 각 MCP 서버에는 필요한 최소한의 권한만 부여하고, API 키는 환경 변수를 사용하여 코드와 분리하며, 더 이상 사용하지 않는 서버는 정기적으로 제거합니다. 엔터프라이즈 환경에서는 관리형 MCP 구성을 활용합니다.

성능 측면에서는 자주 사용하지 않는 서버는 필요할 때만 연결하고, 대량의 데이터를 처리할 때는 필터링 조건을 구체화합니다. 비용 모니터링으로 API 호출량을 제어하는 것도 중요합니다.

MCP 서버는 외부 서비스에 의존하므로 네트워크 문제나 서비스 중단 시 대응책을 마련해야 합니다.

## 7-4 플러그인 시스템 이해하기 (p.234~238, 이번 캡처 마지막 부분)

### 플러그인이란

플러그인은 클로드 코드의 핵심 기능을 손대지 않고도 새로운 기능을 추가할 수 있게 하는 **모듈화된 확장 단위**입니다. 사용자는 플러그인을 통해 자신만의 워크플로를 정의하고, 팀 전체가 동일한 도구 집합을 공유하며, 커뮤니티에서 검증된 확장 기능을 손쉽게 도입할 수 있습니다.

플러그인 시스템이 해결하는 문제는 명확합니다. 사용자마다 선호하는 작업 방식이 다르고, 프로젝트마다 필요한 자동화 수준이 다르며, 팀마다 고유한 코드 컨벤션이 있습니다. 클로드 코드 자체에 이 모든 요구 사항을 내장하는 것은 비현실적입니다. 대신 플러그인 시스템을 통해 개발자가 필요한 기능만 선택적으로 추가하고 자신의 환경에 맞게 클로드 코드를 맞춤 설정할 수 있습니다.

플러그인의 핵심 가치는 **재사용성**에 있습니다. 한 번 만든 플러그인을 여러 프로젝트에서 사용할 수 있고, 팀 전체에 배포할 수 있으며, 마켓플레이스를 통해 커뮤니티와 공유할 수 있습니다. 이는 개별 프로젝트에 흩어져 있던 `.claude/commands/`나 `.claude/agents/` 파일을 체계적으로 관리하고 배포하는 표준화된 방법을 제공합니다.

> **쉽게 말하면**: 지금까지 배운 비대화형 모드, 훅, MCP는 전부 "한 프로젝트 안에서 설정하는 기능들"이었습니다. 플러그인은 그렇게 만든 설정들(커스텀 명령어, 에이전트, 훅, MCP 연결)을 **하나로 포장해서 다른 프로젝트나 동료에게 그대로 전달**할 수 있게 하는 "설치 패키지"입니다.

### 플러그인 구조

모든 플러그인은 `.claude-plugin/` 디렉터리 내에 `plugin.json` 매니페스트 파일을 포함해야 합니다. 이 매니페스트는 플러그인의 메타데이터와 구성 요소를 정의하는 핵심 파일입니다. 클로드 코드는 플러그인을 로드할 때 이 파일을 읽어 플러그인의 이름, 버전, 제공 기능을 파악합니다.

기본 플러그인 디렉터리 구조:
```
my-plugin/
├── .claude-plugin/
│   └── plugin.json        # 플러그인 메타데이터(필수)
├── commands/
│   └── hello.md            # 커스텀 슬래시 명령(선택)
├── agents/
│   └── helper.md            # 커스텀 에이전트(선택)
├── skills/
│   └── my-skill/
│       └── SKILL.md          # 에이전트 스킬(선택)
├── hooks/
│   └── hooks.json             # 이벤트 핸들러(선택)
├── .mcp.json                   # MCP 서버 구성(선택)
└── README.md                    # 플러그인 문서
```

`plugin.json` 파일에서 유일하게 필수인 필드는 `name`입니다. 이 필드는 플러그인의 고유 식별자로, kebab-case 형식으로 작성해야 합니다. 나머지 필드는 선택적이지만 플러그인의 완성도를 높이기 위해 가능한 한 많은 메타데이터를 제공하는 것이 좋습니다. 완전한 `plugin.json` 스키마는 다음과 같은 구조를 가집니다.

```json
{
  "name": "plugin-name",
  "version": "1.2.0",
  "description": "플러그인 설명",
  "author": {
    "name": "작성자 이름",
    "email": "email@example.com",
    "url": "https://github.com/author"
  },
  "homepage": "https://docs.example.com/plugin",
  "repository": "https://github.com/author/plugin",
  "license": "MIT",
  "keywords": ["keyword1", "keyword2"],
  "skills": "./custom/skills/",
  "commands": ["./custom/commands/special.md"],
  "agents": "./custom/agents/",
  "hooks": "./config/hooks.json",
  "mcpServers": "./mcp-config.json",
  "lspServers": "./lsp-config.json",
  "outputStyles": "./styles/"
}
```

`lspServers` 필드를 사용하면 Language Server Protocol 서버를 플러그인에 포함할 수 있어 코드 완성이나 정의로 이동 같은 코드 인텔리전스 기능을 제공할 수 있습니다. `outputStyles` 필드는 플러그인이 제공하는 출력 스타일 디렉터리를 지정합니다.

### plugin.json 스키마 상세

메타데이터 필드는 플러그인의 검색 가능성과 신뢰도를 높입니다. `version` 필드는 의미 있는 버전 관리(semantic versioning)를 따르며 마켓플레이스에서 최신 버전을 식별하는 기준이 됩니다. `description` 필드는 사용자가 마켓플레이스에서 탐색할 때 표시되므로 간결하고 명확하게 기술해야 합니다. `author` 필드는 `name`, `email`, `url` 세 가지 하위 필드를 가집니다. `keywords` 필드는 마켓플레이스 검색에 사용되는 태그 목록입니다.

컴포넌트 경로 필드는 플러그인이 제공하는 기능의 위치를 지정합니다. 기본적으로 클로드 코드는 `commands/`, `agents/`, `skills/`, `hooks/` 디렉터리를 자동으로 인식하지만, 이 필드들을 사용하면 비표준 위치의 파일도 포함할 수 있습니다. `commands`와 `agents` 필드는 `string` 또는 `string` 배열 타입을 지원합니다. `hooks` 필드는 `string`으로 별도 JSON 파일 경로를 참조하거나 `object`로 인라인 정의할 수 있습니다. `mcpServers` 필드도 동일하게 `string` 또는 `object` 타입을 지원하며, MCP 서버 구성이나 훅 스크립트에서 플러그인 내부 리소스를 참조할 때는 `${CLAUDE_PLUGIN_ROOT}` 환경 변수를 사용합니다. 이 변수는 플러그인이 설치된 디렉터리의 절대 경로로 확장되며, 예를 들어 `${CLAUDE_PLUGIN_ROOT}/scripts/lint.sh`처럼 플러그인에 포함된 스크립트 경로를 지정할 수 있습니다. **절대 경로를 하드코딩하면 다른 환경에서 설치 시 경로가 일치하지 않아 실패하게 되므로 `${CLAUDE_PLUGIN_ROOT}`를 반드시 활용해야 합니다.**

스킬은 `plugin.json`에 별도의 경로 필드가 없습니다. 스킬은 항상 `skills/` 디렉터리의 하위 디렉터리에 있는 `SKILL.md` 파일을 통해 자동 발견됩니다.

클로드 코드는 플러그인을 로드할 때 먼저 `.claude-plugin/plugin.json`을 읽어 메타데이터를 파싱하고, 기본 디렉터리 구조(`commands/`, `agents/`, `skills/`, `hooks/`, `.mcp.json`)를 스캔하여 컴포넌트를 자동 등록한 뒤, `plugin.json`의 컴포넌트 경로 필드에 명시된 추가 경로를 처리합니다. 덕분에 간단한 플러그인은 `name` 필드만 정의하고 규약된 디렉터리 구조를 따르면 되고, 복잡한 플러그인은 경로 필드로 비표준 구조를 명시할 수 있습니다.

(그림 7-7 "plugin.json 스키마 구조": 메타데이터 필드(name/version/description/author,license/keywords) + 컴포넌트 경로 필드(commands/skills/agents/hooks/mcpServers) + 확장 필드(lspServers/outputStyles)로 구성)

> **쉽게 말하면**: `plugin.json`은 플러그인의 "제품 설명서 + 조립 설명서"입니다. `name`만 있으면 최소한 작동은 하고(대신 정해진 폴더 이름을 그대로 써야 함), 설명·버전·키워드를 채워 넣을수록 "상품 페이지"가 풍성해지고, 폴더 구조가 특이하면 경로 필드로 "여기 있어요"라고 직접 알려주는 방식입니다.

### 컴포넌트 유형 (5가지)

플러그인은 다섯 가지 유형(**명령어, 에이전트, 스킬, 훅, MCP 통합**)의 컴포넌트를 제공할 수 있습니다. 각 컴포넌트는 클로드 코드의 서로 다른 측면을 확장하며 조합하여 사용할 때 효과적입니다.

(그림 7-8 "플러그인 5대 컴포넌트 구조": plugin.json 매니페스트 → 명령어(슬래시 명령, 예: `/format` 명령으로 코드 포매팅) / 에이전트(특화 에이전트, 예: 보안 전문 에이전트 자동 호출) / 스킬(기능 확장, 예: React 패턴 자동 적용) / 훅(이벤트 핸들러, 예: 커밋 전 린트 자동 실행) / MCP 서버(외부 통합, 예: 외부 API 데이터 조회))

**명령어 컴포넌트**는 사용자가 직접 호출하는 진입점입니다. `commands/` 디렉터리에 마크다운 파일을 배치하여 커스텀 슬래시 명령을 추가합니다. 각 파일은 프론트매터에 `description` 필드를 포함하고, 본문에 클로드에 전달될 프롬프트를 담습니다. 플러그인 명령어는 **네임스페이싱 규칙**을 따릅니다. 파일명이 명령어 이름의 기반이 되지만, 플러그인에서 제공하는 명령어는 `/plugin-name:command-name` 형식으로 호출됩니다. 예를 들어 `my-first-plugin`이라는 플러그인의 `commands/hello.md` 파일은 `/my-first-plugin:hello` 명령으로 호출됩니다. 이러한 네임스페이싱은 서로 다른 플러그인이 같은 이름의 명령어를 제공해도 충돌하지 않게 보장합니다.

**에이전트 컴포넌트**는 복잡한 작업을 전담하는 전문가입니다. `agents/` 디렉터리에 에이전트 정의 파일을 배치하면 특정 작업에 특화된 서브에이전트를 추가할 수 있습니다. 에이전트 파일은 프론트매터에 `description`과 `capabilities` 배열을 포함하여 에이전트의 전문 영역을 명시합니다. 4장에서 다룬 서브에이전트 시스템과 동일한 구조를 따릅니다.

> **쉽게 말하면**: 명령어는 "내가 직접 부르는 단축키"(`/format`처럼), 에이전트는 "특정 분야를 전담하는 부하 직원"입니다.

**스킬 컴포넌트**는 클로드의 배경지식을 확장합니다. 3장에서 학습한 스킬 시스템을 플러그인 형태로 배포할 수 있습니다. `skills/` 디렉터리 아래에 스킬별 하위 디렉터리를 만들고 각 디렉터리에 `SKILL.md` 파일을 배치합니다. 플러그인이 설치되면 스킬이 자동으로 사용 가능해집니다.

**훅 컴포넌트**는 자동화된 워크플로를 구현합니다. `hooks/hooks.json` 파일이나 `plugin.json`에 인라인으로 정의할 수 있습니다. 훅이 응답할 수 있는 이벤트에는 `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `UserPromptSubmit`, `Notification`, `Stop`, `SubagentStart`, `SubagentStop`, `SessionStart`, `SessionEnd`, `PreCompact`, `TeammateIdle`, `TaskCompleted`, `InstructionsLoaded`, `ConfigChange`, `WorktreeCreate`, `WorktreeRemove`가 있습니다 (앞서 7-2절에서 다룬 것과 동일한 이벤트 목록). 훅의 action type에는 `command`, `prompt`, `agent` 세 가지가 있습니다. 예를 들어 `PostToolUse` 훅을 사용하면 파일 저장 후 자동으로 린트를 실행할 수 있습니다.

**MCP 서버 컴포넌트**는 외부 도구 및 서비스와의 통합을 담당합니다. `.mcp.json` 파일이나 `plugin.json`의 `mcpServers` 필드에 표준 MCP 서버 구성을 정의합니다. 이를 통해 데이터베이스, API, 파일 시스템 등 다양한 외부 리소스에 클로드 코드가 접근할 수 있습니다.

> **쉽게 말하면**: 5대 컴포넌트를 한 줄씩 정리하면 — 명령어(내가 부르는 단축키), 에이전트(전담 직원), 스킬(배경지식 확장팩), 훅(자동 반사신경), MCP(외부 서비스 어댑터)입니다. 플러그인은 이 다섯 가지를 원하는 만큼 골라 담는 "장바구니"입니다.

### 플러그인과 프로젝트 설정의 관계 (p.239)

프로젝트 수준의 `.claude/` 디렉터리에 있는 명령어, 에이전트, 스킬은 **해당 프로젝트에서만** 유효합니다. 반면 플러그인으로 설치된 컴포넌트는 **사용자의 모든 프로젝트**에서 사용 가능합니다.

이 구분은 코드 재사용 전략에 중요한 영향을 미칩니다. 특정 프로젝트에만 필요한 명령어나 에이전트는 프로젝트 디렉터리에 직접 배치하고, 여러 프로젝트에서 공통으로 사용할 기능은 플러그인으로 패키징하는 것이 효율적입니다. 팀 전체가 공유해야 하는 도구라면 팀 마켓플레이스를 통해 배포하고, 개인적으로 사용할 유틸리티는 로컬 플러그인으로 관리합니다.

플러그인의 설정은 `settings.json` 파일을 통해 관리됩니다. 이 파일에 마켓플레이스와 설치할 플러그인 목록을 명시하면 팀 멤버가 저장소를 신뢰할 때 플러그인이 자동으로 설치됩니다.

> **쉽게 말하면**: `.claude/` 폴더에 직접 넣은 명령어는 "이 프로젝트 전용 사내 규정"이고, 플러그인으로 설치한 건 "내 컴퓨터 전체에 깔린 공통 앱"입니다. 한 프로젝트에서만 쓸 거면 전자로, 여러 프로젝트에서 재사용할 거면 후자(플러그인)로 만드는 게 맞습니다.

### 플러그인 설치 범위 (p.240)

클로드 코드는 네 가지 설치 범위를 지원합니다. 각 범위는 플러그인의 적용 범위와 공유 방식을 결정합니다.

- **user 범위**: 기본값으로 `~/.claude/settings.json` 파일에 저장되며 사용자의 모든 프로젝트에 적용된다. 개인적으로 자주 사용하는 유틸리티 플러그인을 설치할 때 적합하다
- **project 범위**: `.claude/settings.json` 파일에 저장되며 해당 프로젝트 저장소에 포함된다. 버전 컨트롤에 커밋되므로 팀 전체가 동일한 플러그인을 공유하게 된다. 팀 표준 도구를 배포할 때 사용한다
- **local 범위**: `.claude/settings.local.json` 파일에 저장되며 `.gitignore`에 의해 버전 컨트롤에서 제외된다. 프로젝트별로 개인적인 설정을 유지하면서 팀과 공유하지 않을 때 사용한다
- **managed 범위**: `managed-settings.json` 파일에 저장되며 기업 IT 관리자가 중앙에서 관리한다. 이 범위의 설정은 읽기 전용이며 조직 전체의 보안 정책이나 필수 플러그인을 배포할 때 사용된다

### LSP 서버 지원 (p.240~241)

클로드 코드는 LSP(Language Server Protocol) 서버를 플러그인에 포함할 수 있습니다. LSP는 코드 편집기와 언어 서버 간의 표준 프로토콜로 코드 완성, 정의로 이동, 참조 찾기, 리팩터링 같은 코드 인텔리전스 기능을 제공합니다.

플러그인에 LSP 서버를 포함하려면 `.lsp.json` 파일을 생성하고 `plugin.json`의 `lspServers` 필드에서 참조합니다.
```json
{
  "servers": [
    {
      "name": "typescript-lsp",
      "command": "${CLAUDE_PLUGIN_ROOT}/node_modules/.bin/typescript-language-server",
      "args": ["--stdio"],
      "languages": ["typescript", "javascript"]
    }
  ]
}
```
LSP 서버 디버깅 시에는 `${CLAUDE_PLUGIN_LSP_LOG_FILE}` 환경 변수가 가리키는 로그 파일을 확인합니다 (`~/.claude/debug/` 디렉터리에 생성됨).

### 앤트로픽 공식 마켓플레이스 (p.241, 그림 7-9)

앤트로픽은 공식 플러그인 마켓플레이스(`claude-plugins-official`)를 운영합니다. 이 마켓플레이스는 클로드 코드 설치 시 자동으로 등록되어 별도의 추가 작업 없이 사용할 수 있습니다.

공식 마켓플레이스의 플러그인은 네 가지 카테고리로 구분됩니다. **Code Intelligence** 카테고리에는 `typescript-lsp`, `python-lsp` 같은 LSP 기반 플러그인이 포함됩니다. **External Integrations** 카테고리에는 `github`, `slack`, `figma` 같은 외부 서비스 연동 플러그인이 포함됩니다. **Development Workflows** 카테고리에는 개발 워크플로 자동화 플러그인이, **Output Styles** 카테고리에는 출력 형식 커스터마이징 플러그인이 포함됩니다.

(그림 7-9 "공식 플러그인 리스트": `/plugin` 메뉴의 Discover 탭에서 `context7`, `frontend-design`, `github`, `serena`, `feature-dev` 등 인기 플러그인을 설치 수와 함께 검색/탐색 가능)

> **Tip**: 공식 마켓플레이스 플러그인은 기본으로 자동 업데이트되며, 서드파티 마켓플레이스는 자동 업데이트를 하려면 설정해야 한다. 전체 자동 업데이트를 비활성화하려면 `DISABLE_AUTOUPDATER` 환경 변수를 설정한다.

### 마켓플레이스 개념과 관리 (p.242~244)

마켓플레이스는 사용 가능한 플러그인의 카탈로그입니다. 마켓플레이스는 단일 저장소일 수도 있고 여러 저장소를 조합한 집합일 수도 있습니다. 예를 들어 회사 내부 마켓플레이스에서 팀 전용 플러그인을, 커뮤니티 마켓플레이스에서 범용 도구를, 개인 마켓플레이스에서 실험적 플러그인을 각각 관리할 수 있습니다. 이러한 다중 소스 지원은 조직의 보안 요구 사항과 개발자의 유연성을 동시에 만족시킵니다.

(그림 7-10 "플러그인 마켓플레이스": `/plugin` 메뉴의 Marketplaces 탭에서 등록된 마켓플레이스 목록과 상태를 관리)

마켓플레이스를 추가하는 방법은 세 가지입니다.
1. **깃허브 저장소를 직접 지정**: `/plugin marketplace add owner/repo` (저장소 루트에 `.claude-plugin/marketplace.json` 파일이 있어야 유효한 마켓플레이스로 인식됨)
2. **깃허브가 아닌 깃 저장소도 지원**: GitLab, Bitbucket, 자체 호스팅 Git 서버 등 → `/plugin marketplace add https://gitlab.com/company/plugins.git`
3. **로컬 디렉터리를 마켓플레이스로 지정**: 플러그인 개발 중 테스트에 유용, 네트워크 연결 없이 로컬에서 빠르게 테스트하고 반복 개선 가능 → `/plugin marketplace add ./my-marketplace`

마켓플레이스의 구조는 `.claude-plugin/marketplace.json` 파일로 정의됩니다. 이 파일은 마켓플레이스의 이름, 소유자 정보, 포함된 플러그인 목록을 담습니다.
```json
{
  "name": "company-tools",
  "owner": {
    "name": "DevTools Team",
    "email": "devtools@company.com"
  },
  "plugins": [
    {
      "name": "code-formatter",
      "source": "./plugins/formatter",
      "description": "저장 시 자동 코드 포매팅",
      "version": "2.1.0"
    }
  ]
}
```
필수 필드는 세 가지로, `name`, `owner`, `plugins`입니다. `name`은 kebab-case 형식의 마켓플레이스 식별자이고, `owner`는 유지 관리자 정보를 담는 객체이며, `plugins`는 사용 가능한 플러그인 배열입니다. 선택적으로 `metadata` 객체를 추가하여 마켓플레이스 설명, 버전, 플러그인 기본 경로를 지정할 수 있습니다. **마켓플레이스 이름에는 제한 규칙이 있습니다.** `official`, `anthropic`, `claude`처럼 공식 앤트로픽/클로드 마켓플레이스를 사칭하는 이름은 사용할 수 없습니다.

플러그인 소스는 세 가지 형태로 지정할 수 있습니다.
- **상대 경로**: 마켓플레이스 저장소 내의 디렉터리를 가리킴 — `{"name": "my-plugin", "source": "./plugins/my-plugin"}`
- **깃허브 저장소 직접 참조** — `{"name": "github-plugin", "source": {"source": "github", "repo": "owner/plugin-repo"}}`
- **일반 깃 URL** — `{"name": "git-plugin", "source": {"source": "url", "url": "https://gitlab.com/team/plugin.git"}}`

마켓플레이스 관리 명령어는 추가, 나열, 업데이트, 제거의 네 가지 작업을 수행합니다. `/plugin marketplace list`는 등록된 모든 마켓플레이스를 보여 주고, `/plugin marketplace update marketplace-name`은 특정 마켓플레이스의 메타데이터를 갱신하며, `/plugin marketplace remove marketplace-name`은 마켓플레이스 등록을 해제합니다.

### 플러그인 설치, 활성화, 비활성화, 제거 (p.244~245)

마켓플레이스를 등록했다면 플러그인을 설치할 차례입니다. 클로드 코드는 **대화형 메뉴**와 **직접 명령**, 두 가지 설치 방식을 제공합니다.

대화형 메뉴는 플러그인을 탐색하고 설치하는 가장 직관적인 방법입니다. `/plugin` 명령을 입력하면 메뉴가 표시되고, '플러그인 찾아보기'를 선택하면 등록된 마켓플레이스의 모든 플러그인을 탐색할 수 있습니다. 이 방식은 어떤 플러그인이 있는지 모르는 상태에서 탐색할 때 유용합니다.

직접 명령은 설치할 플러그인을 이미 알고 있을 때 더 빠릅니다. `@marketplace-name` 부분은 같은 이름의 플러그인이 여러 마켓플레이스에 있을 때 명확히 구분하는 역할을 합니다.
```bash
> /plugin install formatter@your-org
```

플러그인의 **활성화와 비활성화**는 플러그인을 제거하지 않고 일시적으로 켜고 끄는 기능입니다. 비활성화된 플러그인은 설치된 상태로 유지되지만, 제공하는 명령어나 에이전트가 클로드 코드에서 동작하지 않습니다. 이 기능은 플러그인 간 충돌을 진단하거나 특정 작업에서만 플러그인을 사용하고 싶을 때 유용합니다.
```bash
> /plugin enable plugin-name@marketplace-name
> /plugin disable plugin-name@marketplace-name
```

플러그인을 완전히 **제거**하려면 `uninstall` 명령을 사용합니다. 제거된 플러그인은 다시 설치해야 사용할 수 있습니다.
```bash
> /plugin uninstall plugin-name@marketplace-name
```

설치 확인은 `/help` 실행 후 새로 추가된 명령어 확인, 기능 직접 테스트, `/plugin` 메뉴의 "플러그인 관리"에서 상태 확인, 이렇게 세 가지 방법으로 확인할 수 있습니다.

### 팀 플러그인 워크플로와 자동 설치 (p.245~246)

팀 프로젝트에서는 모든 팀원의 플러그인 환경이 동일해야 합니다. 클로드 코드는 이를 위해 **자동 설치 기능**을 제공합니다. 저장소의 `.claude/settings.json` 파일에 마켓플레이스와 플러그인 구성을 추가하면 팀 멤버가 저장소를 클론하고 신뢰를 선택할 때 자동으로 설치됩니다.

```json
{
  "plugins": {
    "marketplaces": [
      {
        "name": "team-marketplace",
        "source": "company-org/claude-plugins"
      }
    ],
    "installed": [
      "code-formatter@team-marketplace",
      "test-runner@team-marketplace",
      "security-scanner@team-marketplace"
    ]
  }
}
```
이 설정은 `team-marketplace`라는 마켓플레이스를 등록하고, 해당 마켓플레이스에서 3개의 플러그인을 자동 설치하도록 지정합니다. 새 팀원이 프로젝트에 합류하면 별도의 설정 없이 동일한 플러그인 환경을 갖게 됩니다.

팀 플러그인 워크플로의 권장 구조는 **계층적 마켓플레이스 구조**입니다. 조직 전체에서 사용하는 기본 플러그인은 회사 마켓플레이스에, 팀별 특화 플러그인은 팀 마켓플레이스에, 프로젝트별 플러그인은 프로젝트 저장소에 배치합니다. `.claude/settings.json`에서 이들을 조합하면 조직-팀-프로젝트의 세 계층에서 적절한 플러그인이 자동으로 구성됩니다.

보안 측면에서 자동 설치 기능은 **명시적인 신뢰 승인**을 요구합니다. 저장소를 처음 열 때 클로드 코드가 설정 파일의 플러그인을 설치할지 묻고, 사용자가 명시적으로 승인해야만 설치가 진행됩니다. 이는 악의적인 플러그인이 사용자 모르게 설치되는 것을 방지합니다.

> **쉽게 말하면**: 팀 저장소를 git clone 받으면, 클로드 코드가 "이 프로젝트가 요구하는 플러그인들을 설치해도 될까요?"라고 한 번 물어봅니다. "네"라고 하면 팀원 전체가 똑같은 도구 세트를 자동으로 갖추게 됩니다. 다만 "묻지도 않고 설치"는 절대 안 되고, 항상 사람의 승인을 거칩니다.

### 문제 해결 (p.247)

플러그인 사용 중에 발생할 수 있는 일반적인 문제와 해결책입니다.

- **마켓플레이스가 로드되지 않는 경우**: URL 접근 가능성을 먼저 확인. 비공개 저장소라면 적절한 접근 권한이 있는지 확인. `.claude-plugin/marketplace.json` 파일이 저장소 루트에 있는지 확인하고, JSON 구문이 유효한지 검증
- **플러그인 설치가 실패하는 경우**: 플러그인 소스 URL의 접근 가능성 확인. GitHub 소스의 경우 저장소가 공개되어 있거나 접근 권한이 있는지 확인. 플러그인 디렉터리에 `.claude-plugin/plugin.json` 파일이 포함되어 있는지 확인
- **`claude --debug` 명령**으로 클로드 코드를 실행하면 상세한 디버깅 정보를 얻을 수 있습니다. 이 모드에서는 로드되는 플러그인, 매니페스트 오류, 명령어와 에이전트 등록 과정, MCP 서버 초기화 상황이 모두 출력됩니다
- **일반적인 문제 유형과 해결책**: 플러그인이 로드되지 않으면 `plugin.json`의 JSON 구문을 검증. 명령어가 나타나지 않으면 `commands/` 디렉터리가 플러그인 루트에 있는지 확인. 훅이 실행되지 않으면 스크립트에 실행 권한이 있는지 확인하고 필요하면 `chmod +x script.sh`를 실행. MCP 서버가 실패하면 경로에 `${CLAUDE_PLUGIN_ROOT}` 변수를 사용했는지 확인. 경로 관련 오류가 발생하면 절대 경로 대신 `./`로 시작하는 상대 경로를 사용

### 실전 플러그인 예제: 코드 품질 도구 (p.247~250)

플러그인은 앞서 개별로 학습한 스킬, 서브에이전트, 명령어를 하나의 패키지로 통합합니다. 개별 요소가 프로젝트 디렉터리에 흩어져 있을 때는 관리와 배포가 어렵지만 플러그인으로 묶으면 버전 관리, 의존성 추적, 팀 배포가 체계화됩니다.

플러그인 개발의 첫 단계는 해결하려는 문제를 명확히 정의하는 것입니다. 팀에서 반복적으로 수행하는 작업이 있는가? 코드 리뷰 전에 항상 실행하는 검사가 있는가? 특정 도메인에 특화된 지식이 필요한 작업이 있는가? 이러한 질문에 대한 답이 플러그인의 컴포넌트 구성을 결정합니다.

실제 플러그인 예시로 "**코드 품질 도구**" 플러그인을 설계해 봅니다. 이 플러그인은 코드 작성 전에 팀 컨벤션을 적용하고(**스킬**), 린트와 테스트를 자동 실행하며(**훅**), 품질 검사를 명령어로 트리거하고(**명령어**), 복잡한 리팩터링을 전문 에이전트에게 위임합니다(**에이전트**).

플러그인 디렉터리 구조:
```
code-quality-plugin/
├── .claude-plugin/
│   └── plugin.json
├── commands/
│   ├── quality-check.md
│   └── refactor.md
├── agents/
│   └── refactor-specialist.md
├── skills/
│   └── team-conventions/
│       └── SKILL.md
└── hooks/
    └── hooks.json
```

`plugin.json`:
```json
{
  "name": "code-quality-plugin",
  "version": "1.0.0",
  "description": "컨벤션, 린팅, 리팩터링을 포함한 팀 코드 품질 도구",
  "author": { "name": "DevOps Team" },
  "keywords": ["quality", "lint", "refactor", "conventions"]
}
```
명시적인 경로 지정이 없으면 클로드 코드는 표준 디렉터리(`commands/`, `agents/`, `skills/`, `hooks/`)를 자동으로 인식합니다.

**명령어 파일** `quality-check.md`:
```markdown
---
description: 코드베이스에 대한 종합적인 품질 검사 실행
---

# Quality Check Command

현재 프로젝트에 대해 다음 품질 검사를 수행하세요:

1. 린터를 실행하고 모든 이슈를 보고
2. 단위 테스트를 실행하고 결과 요약
3. 보안 취약점 검사
4. 코드 커버리지가 팀 표준(최소 80%)을 충족하는지 확인

실행 가능한 권장 사항을 포함한 구조화된 형식으로 결과를 보고하세요.
```

**에이전트 파일** `refactor-specialist.md`는 서브에이전트 정의 형식을 따릅니다:
```markdown
---
description: 복잡한 코드 리팩터링 전문 에이전트
capabilities: ["extract-method", "rename-symbol", "move-code", "simplify-logic"]
---

# Refactor Specialist

당신은 코드 리팩터링 전문가입니다. 전문 분야는 다음과 같습니다.

- 코드 스멜과 안티 패턴 식별
- SOLID 원칙 적용
- 구조를 개선하면서 동작 보존
- 리팩터링 전 포괄적인 테스트 작성

항상 리팩터링 결정에 대해 설명하고 동작 보존을 검증하세요.
```

**스킬 파일** `SKILL.md`는 스킬 정의 형식을 따릅니다:
```markdown
# Team Code Conventions

## Naming Conventions
- 변수와 함수는 camelCase 사용
- 클래스와 컴포넌트는 PascalCase 사용
- 상수는 SCREAMING_SNAKE_CASE 사용

## File Structure
- 파일당 하나의 컴포넌트
- 테스트는 __tests__ 디렉터리에
- 유틸리티는 utils/ 디렉터리에

## Code Style
- 최대 함수 길이: 30줄
- 최대 파일 길이: 300줄
- 상속보다 조합을 선호
```

**훅 파일** `hooks.json`은 이벤트 핸들러를 정의합니다. 이 훅은 파일이 저장될 때마다 린트를 자동으로 실행합니다.
```json
{
  "hooks": [
    {
      "event": "PostToolUse",
      "matcher": { "tool": "Write" },
      "action": {
        "type": "command",
        "command": "npm run lint --fix ${file}"
      }
    }
  ]
}
```

> **쉽게 말하면**: 이 예제 하나로 플러그인 5대 컴포넌트가 실전에서 어떻게 조합되는지 보여줍니다. "코드 짜기 전엔 스킬(팀 규칙)을 참고하고, 저장할 때마다 훅이 자동으로 린트를 돌리고, `/quality-check` 명령어로 언제든 종합 점검을 하고, 복잡한 리팩터링은 전문 에이전트에게 넘긴다"는 하나의 완결된 워크플로입니다.

### 로컬 테스트 환경 설정과 개발 워크플로 (p.250~252)

플러그인 개발에서 빠른 반복이 핵심입니다. 변경 사항을 적용하고 테스트하는 주기가 짧을수록 개발 효율이 높아집니다. 클로드 코드는 로컬 테스트를 위한 **dev-marketplace 패턴**을 제공합니다.

```bash
$ mkdir dev-marketplace
$ cd dev-marketplace
$ mkdir my-plugin
```

마켓플레이스 매니페스트를 작성합니다 (`.claude-plugin/marketplace.json`):
```json
{
  "name": "dev-marketplace",
  "owner": { "name": "Developer" },
  "plugins": [
    {
      "name": "my-plugin",
      "source": "./my-plugin",
      "description": "개발 중인 플러그인"
    }
  ]
}
```

클로드 코드에서 마켓플레이스를 등록하고 플러그인을 설치합니다.
```bash
> /plugin marketplace add ./dev-marketplace
> /plugin install my-plugin@dev-marketplace
```

플러그인을 수정한 후에는 **재설치가 필요**합니다.
```bash
> /plugin uninstall my-plugin@dev-marketplace
> /plugin install my-plugin@dev-marketplace
```
이 과정이 번거롭게 느껴질 수 있지만 플러그인의 격리와 일관성을 보장하는 데 필요합니다. 플러그인 코드를 수정해도 설치된 버전에 즉시 반영되지 않으므로 의도하지 않은 변경이 실행 중인 세션에 영향을 주지 않습니다.

디버깅은 `claude --debug` 명령으로 시작합니다. 이 모드에서 클로드 코드는 다음 정보를 출력합니다: 로드되는 플러그인 목록(플러그인이 제대로 인식되는지 확인), 플러그인 매니페스트 오류(JSON 구문 오류나 필수 필드 누락을 즉시 파악), 명령어·에이전트·훅의 등록 과정(컴포넌트가 제대로 등록되는지 확인), MCP 서버 초기화 상황(외부 서비스 연결 문제를 진단).

개발 워크플로는 **점진적 개발**을 기준으로 삼습니다. 모든 컴포넌트를 한 번에 만들지 말고 가장 핵심적인 기능 하나부터 시작합니다. 예를 들어 명령어 하나만 있는 최소 플러그인을 먼저 만들고, 테스트가 통과하면 에이전트를 추가하고, 다시 테스트한 후 스킬을 추가하는 방식입니다.

### 플러그인 캐싱 (p.252)

클로드 코드는 플러그인을 설치할 때 원본을 캐시 디렉터리로 복사합니다. 이러한 설계는 몇 가지 중요한 특성을 가집니다.

1. **원본 플러그인 소스를 수정해도 설치된 버전에 즉시 반영되지 않습니다.** 변경 사항을 적용하려면 플러그인을 제거하고 다시 설치해야 합니다. 이는 개발 중에는 번거롭지만 실행 중인 세션이 예기치 않게 변경되는 것을 방지합니다
2. **심볼릭 링크는 허용됩니다.** 개발 환경에서 심볼릭 링크를 활용하면 원본과 설치된 버전을 동기화할 수 있습니다
3. **경로 순회는 차단됩니다.** `../shared-utils` 같은 상위 디렉터리 참조는 보안상의 이유로 허용되지 않습니다. 플러그인은 자체 디렉터리 내부의 리소스만 접근할 수 있습니다

> **쉽게 말하면**: 플러그인을 설치하면 원본 폴더가 아니라 "복사본"이 캐시에 저장됩니다. 그래서 원본을 고쳐도 바로 반영되지 않고(재설치해야 반영), 대신 심볼릭 링크를 걸어두면 개발 중엔 실시간 동기화도 가능합니다. 다만 플러그인이 자기 폴더 바깥(`../`)을 훔쳐보는 건 원천 차단됩니다.

### 플러그인 배포와 마켓플레이스 게시 (p.252~253)

**팀 내부 배포**의 경우, 회사 깃허브 조직에 마켓플레이스 저장소를 생성하고 프로젝트의 `.claude/settings.json`에 해당 마켓플레이스를 등록합니다. **커뮤니티 배포**의 경우, 공개 깃허브 저장소를 마켓플레이스로 사용하고 플러그인 문서와 사용 예시를 충실히 작성하며 의미 있는 버전 관리를 적용합니다. 이슈 트래커와 기여 가이드라인을 제공하면 커뮤니티 참여를 유도할 수 있습니다.

플러그인을 배포하기 전에 다음 항목을 확인합니다.

1. `plugin.json`의 메타데이터가 완전한지 확인한다. `name`, `version`, `description`, `author` 필드는 필수적으로 채운다
2. 모든 컴포넌트가 올바르게 동작하는지 테스트한다. 명령어, 에이전트, 스킬, 훅 각각을 실제 사용 시나리오에서 검증한다
3. README 파일에 설치 방법, 사용 예시, 설정 옵션을 문서화한다
4. 라이선스를 명시한다. 오픈 소스 배포라면 MIT, Apache 2.0 같은 표준 라이선스를 선택한다
5. CHANGELOG를 작성하여 버전별 변경 사항을 기록한다

마켓플레이스 게시 후에도 유지보수가 필요합니다. 사용자 피드백을 반영하고, 클로드 코드 업데이트에 맞춰 플러그인을 갱신하며, 보안 취약점을 신속히 수정합니다. 활발하게 유지되는 플러그인이 더 많은 신뢰와 사용자를 얻습니다.

### 유의 사항 (p.253)

플러그인을 개발할 때는 다음을 유의합니다.

- **단일 책임 원칙**을 플러그인에도 적용한다. 하나의 플러그인이 너무 많은 기능을 담으면 관리가 어려워지고, 사용자가 필요한 것만 선택하기 어렵다. "코드 포매팅", "테스트 자동화", "보안 검사"는 각각 별도의 플러그인으로 분리하는 것이 좋다
- **플러그인 간 의존성은 피한다.** 플러그인 A가 플러그인 B의 기능에 의존하면, 사용자는 두 플러그인을 모두 설치해야 한다. 이는 설치 복잡도를 높이고 버전 충돌 가능성을 만든다. 공통 기능이 필요하다면 해당 기능을 스킬로 분리하여 여러 플러그인에서 참조하는 방식을 고려한다
- **경로는 항상 상대 경로를 사용한다.** 절대 경로는 개발 환경과 배포 환경에서 다르게 동작할 수 있다. `./`로 시작하는 상대 경로를 사용하면 플러그인이 어디에 설치되든 일관되게 동작한다. MCP 서버 경로에는 `${CLAUDE_PLUGIN_ROOT}` 변수를 사용한다. 이 변수는 플러그인이 설치된 실제 경로로 대체되어 MCP 서버가 플러그인과 함께 배포된 리소스에 접근할 수 있게 한다
- **훅 스크립트에는 실행 권한을 부여한다.** 훅이 외부 스크립트를 실행하는 경우, 해당 스크립트에 실행 권한(`chmod +x`)이 있어야 한다. 권한 누락은 훅 실행 실패의 가장 흔한 원인이다
- **에러 처리를 명확히 한다.** 플러그인 컴포넌트가 실패할 때 사용자에게 유용한 에러 메시지를 제공한다. 무엇이 잘못되었는지, 어떻게 해결할 수 있는지 안내하면 사용자 경험이 크게 향상된다

> **쉽게 말하면**: 플러그인도 결국 "남이 쓸 소프트웨어"입니다. 그래서 좋은 소프트웨어 설계 원칙(단일 책임, 낮은 결합도)이 그대로 적용됩니다. 기능 하나만 딱 하게 만들고, 다른 플러그인에 기대지 말고, 어디에 설치되든 안 깨지게 상대 경로를 쓰고, 스크립트엔 실행 권한을 꼭 챙기고, 에러가 나면 "왜 안 되는지" 친절하게 알려주라는 것입니다. 이 다섯 가지를 지키면 이 문서에서 다룬 7장 "자동화"의 네 축(비대화형 모드·훅·MCP·플러그인)을 안전하고 재사용 가능하게 팀 전체에 녹여낼 수 있습니다.

*(캡처된 자료는 253쪽 "유의 사항"에서 끝납니다. 이후 페이지에 7장 요약이나 8장으로의 전환부가 있을 수 있으나, 현재까지 캡처된 범위에서는 여기가 7장 자동화의 마지막 부분으로 보입니다.)*

## 한 줄 요약

- **비대화형 모드(`-p`)**: 클로드 코드를 "대화 없이 명령 → 결과"만 받는 프로그램처럼 호출하는 방법. CI/CD, cron, 챗봇 등 어디든 끼워 넣을 수 있음.
- **훅(Hooks)**: 클로드의 특정 행동 시점마다 "AI 판단과 무관하게 100% 실행되는" 내 로직을 심는 방법. 17개 이상의 이벤트 각각이 서로 다른 타이밍·매처·차단 권한을 가지며, `command`/`prompt`/`agent`/`http` 네 가지 타입으로 구현 가능.
- **MCP(Model Context Protocol)**: 깃허브·노션·데이터베이스·Stripe 등 외부 서비스를 클로드 코드의 "도구"로 바꿔주는 표준 어댑터. stdio(로컬)·HTTP(원격) 두 가지 전송 방식과 로컬/프로젝트/사용자 3단계 범위로 관리.
- **플러그인**: 명령어·에이전트·스킬·훅·MCP 설정을 하나의 패키지로 묶어 마켓플레이스를 통해 여러 프로젝트·팀·커뮤니티에 재사용 가능하게 배포하는 단위. `plugin.json` 매니페스트로 정의하고, user/project/local/managed 4단계 범위로 설치를 관리하며, 단일 책임 원칙을 지켜 설계하는 것이 좋음.
- 네 기능을 합치면 **"클로드를 외부 세계 전체와 연결하고, 정해진 순간마다 안전장치·자동화 로직을 강제로 심고, 그 결과물을 패키징해서 팀·커뮤니티에 배포하는"** 완전한 자동화 생태계를 만들 수 있음.
