# 7. 자동화

## 7-1. 비대화형 모드와 스크립트 자동화
- -p 플래그를 심화하여, 셸 스크립트, CI/CD 파이프라인, cron 작업 등에서 클로드 코드의 기능을 자동화하는 방법을 다룬다
- 대화형 UI없이 명령줄에서 직접 프롬프트를 전달하고 결과를 표준 출력으로 받을수 있어서 셸 스크립트, cron 작업 등에서 클로드 코드의 기능을 활용할 수 있다. 

### 1) 주요 플래그 
- 비대화형 모드를 활성화 하려면 --print 플래그 (-p)를 사용
    ```text
    $ claude -p "이 코드 구조 설명해줘"
    ```
- 실제 자동화에서는 도구 제한과 권한 모드를 함께 지정하는것이 일반적이다.
    ```text
    $ claude -p "스테이징된 변경 사항을 커밋으로 나눠줘" \
    --allowedTools "Bash,Read" \        // 사용 가능한 도구를 해당 두 가지로 제한
    --permission-mode acceptEdits.     // 파일 편집 작업을 사용자 확인없이 허용
    ```

### 2) 입출력 형식
- 출력은 텍스트 JSON, 스트리밍 JSON 출력 형식을 지원한다

### 3) 다중 턴 대화
- 비대화형 모드에서도 대화 컨텍스트를 유지할수 있다. 
- --continue(-c) : 가장 최근 대화를 계속한다.
- --resume(-r) : 특정 세션을 재개한다.

### 4) 프로그래밍 활용
- SRE 인시던트 대응봇
  - 인시던트 발생 시 자동으로 분석을 수행하도 대응 방안을 제시한다. 
    ```shell
    #!/bin/bash
    
    investigate_incident() {
      local incident_description="$1"
      local severity="${2:-medium}"
    
      claude -p "인시던트: $incident_description(심각도: $serverity)" \
        --append-system-prompt "당신은 SRE 전문가입니다. 문제를 진단하고 영향을 평가하고 즉각적인 조치 사항을 제공하세요." \
            --output-format json \
            --allowedTools "Bash,Read,WebSearch,mcp__datadog" \
            --mcp-config monitoring-tools.json
    }
    ```
  - 인시던트 설명과 심각도를 받아서 클로드에 분석을 요청
  - SRE 전문가 역할을 지정하고, 모니털이 도구(Data dog MCP)에 접근할수 있도록 설정
  - JSON으로 출력해서 결과를 파싱하여 후속 처리에 활용한다. 

- 자동화된 보안 리뷰
  ```shell
  audit_pr() {
    local pr_number="$1"
  
    gh pr diff "$pr_number" | claude -p \
      --append-system-prompt "당신은 보안 엔지니어입니다. 이 PR 에 대해 취약점, 안전하지 않은 패턴, 규정 준수 문제를 검토하세요." \
      --output-format json \
      --allowedTools "Read,Grep,WebSearch"
  }
  
  audit_pr 123 > security-report.json
  ```
    - 깃허브 CLI의 hg pr diff 명령으로 PR의 diff를 가져와서 클로드에 보안 검토를 요청한다. 

### 5) 비대화형 모드 사용시 고려사항
- JSON 출력 사용 : 응답을 프로그래밍 방식으로 파싱해야할 때는 반드시 --output-format json을 사용
- 오류 처리 : 종료 코드와 stderr을 확인하여 오류를 우아하게 처리한다.
- 세션 활용 : 여러 턴에서 컨텍스트를 유지해야할 때는 세션 기능을 활용한다.
- 타임아웃 적용 : 장기 실행 작업에는 timeout 명령으로 시간제한을 설정한다. 
- 속도 제한 존중 : 여러 요청을 연속으로 보낼 때는 요청 사이에 적절한 지연을 추가한다. 

## 7-2. 훅 시스템
- 훅은 클로드 코드의 생애 주기 중 특정 시점에서 자동으로 실해오디는 커스텀 셸 명령어, LLM 프롬프트 또는 에이전트 작업이다. 
- 특정 작업이 반드시 실행되도록 보장한다는 점에서 훅은 예측가능하고 결정론적인 자동화를 구현하는 핵심 메커니즘이다. 
- 훅의 가치는 일관성에 있다. AI는 매번 다른 답변을 낼 수 있지만, 훅은 동일한 이벤트에 대해 항상 동일한 로직을 수행한다. 
- 훅 시스템은 세가지 타입의 핸들러를 지원한다.
  - command 타입 : bash 셸에서 명령을 직접 실행한다. 포맷터, 린터, 유효성 검사 스크립트 등 결정론적인 작업에 적합하다.
  - prompt 타입 : LLM 에서 프롬프트를 전달하여 단일 턴 평가를 수행한다.
  - agent 타입 : 서브에이전트를 생성하여 Read, Grep, Glob같은 도구를 사용한 다중 턴 검증을 수행한다. 

### 1) 훅 이벤트
- 생애 주기의 특정 시점에서 발생하며 사용자는 원하는 이벤트에 훅을 등록하여 자동화 로직을 구현한다. 
  - 1. SessionStart     
    - 클로드 코드가 새 세션을 시작하거나 기존 세션을 재개할 때 발생한다. 
    - 환경 초기화, 작업 디렉터리 검증, 필수 설정 확인, 개발 컨텍스트 로딩 등에 활용
  - 2. UserPromptSubmit
    - 사용자가 프롬프트를 제출할 때 클로드가 처리하기 전에 실행한다. 
    - 프롬프트 검증, 건텍스트 추가, 사용자 입력 로깅 등에 활용할 수 있다. 
  - 3. PreToolUse
    - 클로드가 도구의 매개변수를 생성한 후 실제로 도구를 호출하기 직전에 발생하는 이벤트다.
    - 이 이벤트는 도구 실행을 사전에 차단하거나 입력을 수정할 수 있는 핵심 제어 지점이다. 
  - 4. PermissionRequest
    - 사용자에게 권한 대화상자가 표시될 때 발생하는 이벤트다.
    - 권한 승인이 필요한 시점에만 발생
  - 5. PostToolUse
    - 도구가 성공적으로 실행을 완료한 직후에 발생한다. 
    - 파일 작성후 자동 포매팅, 코드 변경 후 린트검사, 특정 작업 완료 후 외부 시스템에 알림전송등의 후처리 작업에 활용한다. 
  - 6. PostToolUseFailure
    - 도구 실행이 실패했을 때 발생하는 이벤트
    - 오류를 발생 시키거나 실패결과를 반환하는 도구 호출에 대해 발생한다. 
    - 실패 로깅, 알림 전송, 클로드에 보정 피드백 제공 등에 활용된다. 
  - 7. Nofification
    - 클로드 코드가 알림을 보낼때 발생한다. 
    - 매처를 통해 알림 유형별로 다른 핸들러를 실행 할 수 있다. 
  - 8. SubagentStart
    - Agent 도구를 통해 서브에이전트가 생성될 때 발생하는 이벤트이다. 
  - 9. SubagentStop
    - 서브에이전트가 응답을 완료했을 때 발생한다. 
    - 매처는 SubagentStart와 동일한 에이전트 타입값을 사용
  - 10. Stop
    - 메인 클로드 코드 에이전트가 응답 생성을 완료 했을 때 발생하며 사용자 인터럽트에 의한 중단 시에는 발생하지 않는다.
    - 세션 요약생성, 작업 완료 보고서 작성, 사용량 통계 기록, 후처리 워크플로 트리거 등에 사용
  - 11. TeammateIdle
    - 에이전트 팀 환경에서 팀원 에이전트가 자신의 턴을 마치고 유휴 상태로 전환되려 할 때 발생한다. 
    - 팀원이 작업을 중단하기 전에 품질 게이트를 강제 하는데 활용된다. 
  - 12. TaskCompleted
    - 작업이 완료로 표시되려 할 때 발생한다.
    - 두가지 상황에서 발생하는데, 에이전트가 TaskUpdate 도구를 통해 작업을 완료로 표시할 때와 에이전트 팀 팀원이 진행중인 작업을 가진채로 턴을 마칠떄 
  - 13. PreCompact
    - 클로드 코드가 컴팩트 작업을 실행하려 할 떄 발생한다. 
  - 14. SessionEnd
    - 클로드 코드 세션이 종료될 때 발생한다. 
    - 세션 로그 저장, 임시파일 정리, 사용량 통계 전송, 작업 상태 백업 등 정리 작업에 활용된다. 
  - 15. ConfigChage
    - 이벤트는 클로드 코드의 설정 파일이 변경될 때 발생한다. 
  - 16. WokrtreeCreate와 WorktreeRemove
    - 이벤트는 깃 작업 트리가 생성되거나 제거될 때 발생한다.

### 2) 종료 코드와 결정 제어 체계
- 훅의 실행 결과는 종료 코드 또는 JSON 출력으로 클로드 코드에 전달된다. 
- 종료 코드 0
  - 성공을 의미
  - stdout에서 JSON 출력을 파싱한다. 
- 종료 코드 2
  - 차단 오류를 의미
  - stderr 텍스트를 클로드에 오류 메시지로 전달한다. 
- 기타 종료 코드 (1, 3등)
  - 차단되지 않는 오류로 stderr가 상세모드에서 표시되고 실행이 계속된다.

### 3) 훅 구성 파일과 우선순위
- 훅의 설정 파일은 여러 수준으로 존재한다.
- 사용자 설정 : ~/.claude/settings.json
- 프로젝트 설정 : .claude/settings.json
- 로컬 프로젝트 설정 : .claude/settings.local.json

### 4) 매처 패턴 이해하기 
- 매처는 훅이 어떤 조건에서 실행될지를 결정하는 정규식 문자열이다. 

### 5) 체크 포인팅 보완을 위한 훅 활용
- bash 명령이 클로드 외부에서 실행되기 때문에 이 제한을 해결하기 위해 pre-bash, post-bash hooks를 결합한 스마트 하이브리드 전략을 제안한다.
- 가장 간단한 방법은 bash 명령 실행 후 자동으로 깃 커밋을 생성하는것이다. 
- 하이브리드 전략의 세가지 장점
  - 최적의 성능과 안정성 균형 : 파일 변경이 발생 했을때만 깃 커밋을 생성하므로 불필요한 오버헤드를 방지한다. 
  - 스마트 감지 : git diff --quiet 명령을 활용하여 실제로 파일 시스템에 변경이 발생했는지를 정확하게 감지한다. 
  - 향상된 추적성 : 커밋 메시지에 실제로 실행된 bash 명령을 포함하므로 각 변경이 어떤 병령에 의해 발생했는지 명확하게 식별할 수 있다. 

### 6) HTTP 훅
- 기존 command 타입 훅 로컬 셸 명령을 실행하는 방식이다. 
- 팀 공유 감사서비스, 중앙 로깅 시스템, 알림 서비스 등 외부 시스템과의 통합에 적합하다. 

## 7-3. MCP 통합으로 외부세계와의 연결 확장
- MCP는 AI 에이전트가 외부 시스템과 상호작용을 하기 위한 표준화된 프로토콜이다. 
- 단일화된 인터페이스를 통해 다양한 서비스에 접근할 수 있게 해준다. 
- MCP의 핵심 가치는 생태계 확장성에 있다. 
- MCP 서버는 클라우드 서비스, 데이터베이스, 모니터링 도구, 협업 도구 등 외부 리소스를 클로드 코드의 도구로 변환한다. 

### 1) MCP 전송 방식
- 세 가지 전송방식으로 MCP서버와 통신할 수 있다. 
  1) stdio 전송
     - 로컬에서 실행되는 MCP 서버와 표준 입출력을 통해 통신하는 방식이다. 
     - 프로세스 간 통신에 네트워크가 관여하지 않으므로 가장 빠르고 안정적이다. 
     - Node.js 기반 MCP 서버, 로컬 데이터베이스 연결, 파일시스템 기반 도구 등에 적합
  2) HTTP 전송
     - 원격 서버와 HTTP 프로토콜을 통해 통신하는 방식이다. 
     - 클라우드에서 호스팅 되는 MCP 서버에 접근할 때 사용된다. 
     - 노션, 깃헙브, Stripe 등 주요 서비스에서 HTTP 전송 기반의 MCP 서버를 제공한다. 
  3) SSE 전송
     - 공식 문서에서 더 이상 권장되지 않음

### 2) 주요 MCP 서버 활용 사례
- GitHub 통합
  - 레포지토리 코드를 분석하고 PR을 검토하여 이슈를 자동으로 해결하는 코드를 생성
- 데이터베이스 직접 쿼리
  - PostgreSQL 데이터베이스에 직접 연결하여 데이터를 조회하고 분석할 수 있다.
- 모니터링 도우 연동
  - Sentry, Statsig 같은 서비스와 연결하여 운영 상태를 분석 할 수 있다. 
- 디자인 도구 통합
  - 피그마, 스케치 같은 디자인 도구와 연결하여 디자인 시스템을 코드로 변환할 수 있다. 

### 3) MCP 서버 설정과 구현 방법
- 세 가지 범위의 서버 구성을 지원
  1) 로컬 범위
     - 현재 프로젝트의 사용자에게만 적용 .claude/settings/local.json
  2) 프로젝트 범위
     - 프로젝트 루트의 .mcp.json 파일에 저장되어 프로젝트의 모든 팀원에게 공유
  3) 사용자 범위 
     - 모든 프로젝트에서 접근 가능하며 ~/.claude/mcp.json에 저장

- .mcp.json 구성과 환경 변수 확장
  - .mcp.json 파일은 프로젝트 루트 디렉토리에 위치하며 프로젝트 범위의 MCP 서버를 정의한다. 
  - 팀 전체가 동일한 MCP 서버 구성을 공유하려면 이 파일을 버전 관리 시스템에 체크인하면 된다. 

- 인증
  - 서버인증은 두 가지 방식으로 처리
    1) OAuth 2.0 인증은 많은 클라우드 기반 MCP서버가 채택하는 표준 인증 방식
    2) 헤더 기반 인증은 API키나 Bearer 토큰을 HTTP 헤더에 직접 포함하는 방식

### 4) 유의 사항
- 보안 측면에서 MCP 서버는 클로드 코드에 외부 시스템에 대한 접근 권한을 부여하므로 신중한 관리 필요
- 각 MCP 서버에는 필요한 최소한의 권한만 부여하고, API 키는 환경 변수를 사용하여 코드와 분리하며 더 이상 사용하지 않는 서버는 정기적으로 제거 
- 성능 측면에서는 자주 사용하지 않는 서버는 필요할 때만 연결하고 대량의 데이터를 처리할 때는 필터링 조건을 구체화한다. 

## 7-4 플러그인 시스템 이해하기
- 플러그인은 클로드 코드의 핵심 기능을 손대지 않고도 새로운 기능을 추가할 수 있게 하는 모듈화된 확장 단위이다. 
- 사용자는 플러그인을 통해 자신만의 워크플로를 정의하고 팀 전체가 동일한 도구 집합을 공유하며 커뮤니티에서 검증된 확장 기능을 손쉽게 도입할 수 있다. 
- 사용자마다 선호하는 작업방식이 다르고 프로젝트마다 필요한 수준이 다르며 팀마다 고유한 코드 컨벤션이 있다. <br> 플러그인 시스템을 통해 개발자가 필요한 기능만 선택적으로 추가하고 자신의 환경에 맞게 클로드 코드를 맞춤 설정할 수 있다.
- 핵심 가치는 재사용성
  - 한번 만든 플러그인은 여러 프로젝트에서 사용할 수 있고 팀 전체에 배포할 수 있으며 마켓플레이스를 통해 커뮤니티와 공유할 수 있다. 

### 1) 플러그인 구조
- 모든 플러그인은 .claude-plugin/ 디렉토리 내에 plugin.json 매니페스트 파일을 포함해야 한다. 
- 이 매니페스트는 플러그인의 메타데이터와 구성 요소를 정의하는 핵심 파일이다. 
- 클로드 코드는 플러그인을 로드할 때 이 파일을 읽어 플러그인의 이름, 버전, 제공 기능을 파악한다.
``` json
// plugin.json 예시
{
    "name": "plugin-name",
    "version": "1.2.0",
    "description": "플러그인 설명",
    "author": {
        "name": "작성자 이름",
        "email": "email@google.com",
        "url": "http://github.com/autor"
    },
    "hompage": "http://github.com",
    "repositoy": "http://github.com",
    "license": "MIT",
    "keywords": [
        "keyword1",
        "keyword2"
    ],
    "skills": "./custom/skill/",
    "commands": [
        "./custom/commands/special.md"
    ],
    "agents": "./custom/agents/",
    "hooks": "./config/hooks.json",
    "mcpServers": "./mcp-config.json",
    "lspServers": "./lsp-config.json",
    "outputStyles": "./styles/"
}
```
- lspServers 필드를 사용하면 Language Server Protocol 서버를 플러그인에 포함할 수 있어 코드 완성이나 정의로 이동 같은 코드 인텔리전스 기능을 제공할 수 있다. 
- outputStyles 필드는 플러그인이 제공하는 출력 스타일 디렉토리를 지정

- plugin.json 스키마 상세
  - 메타데이터 필드는 플러그인의 검색 가능성과 신뢰도를 높인다. 
  - description : 마켓플레이스에서 탐색할때 표시되므로 간결하고 명확하게 기술
  - author : name, email, url 세가지 하위 필드를 가진다. 
  - keywords : 마켓플레이스 검색에 사용되는 태그 목록
  - 클로드 코드는 플러그인을 로드할 때 먼저 .claude-plugin/plugin.json을 읽어 메타데이터를 파싱하고 기본 디렉토리 구조를 스캔하여 컴포넌트를 자동 등록한 뒤, plugin.json의 컴포넌트 경로 필드에 명시된 추가경로를 처리한다. 

### 2) 컴포넌트 유형
- 총 다섯가지 유형의 컴포넌트를 제공할 수 있다. 
- 명령어 컴포넌트
  - 사용자가 직접 호출하는 진입점이며 commands/ 디렉토리에 마크다운 파일을 배치하여 커스텀 슬래시 명령을 추가한다. 
  - /plugin-name:command-name 형식으로 호출된다. 
- 에이전트 컴포넌트
  - 복잡한 작업을 전담하는 전문가이며 agents/ 디렉토리에 에이전트 정의 파일을 배치하면 특정작업에 특화된 에이전트를 추가할 수 있다. 
- 스킬 컴포넌트
  - 스킬 시스템을 플러그인 형태로 배포할 수 있다. 
- 훅 컴포넌트
  - 자동화된 워크플로를 구현한다. hooks/hooks.json 파일이나 plugin.json 인라인으로 정의할 수 있다. 
- MCP 서버 컴포넌트
  - 외부 도구 및 서비스와의 통합을 담당한다. 

### 3) 플러그인과 프로젝트 설계의 관계
- 플러그인으로 설치된 컴포넌트는 모든 프로젝트에서 사용가능하다. 
- 특정 프로젝트에만 필요한 명령어나 에이전트는 프로젝트 디렉토리에 직접 배치하고, 공통으로 사용할 기능은 플러그인으로 패키징 하는것이 효율적이다.
- 플러그인 설정은 settings.json 파일을 통해 관리된다. 

### 4) LSP 서버 지원
- LSP는 코드 편집기와 언어 서버 간의 표주 ㄴ프로토콜로 코드 완성, 정의로 이동, 참조 찾기, 리팩터링 같은 코드 인텔리전스 기능을 제공한다. 
- 플러그인에 LSP 서버를 포함하려면 .lsp.json 파일을 생성하고 plugin.json의 lspServers 필드에 참조한다. 

### 5) 팀 플러그인 워크플로와 자동 설치
- 팀 프로젝트에서는 모든 팀원의 플러그인 환경이 동일해야한다. 
- 이를 위해 클로드 코드는 자동 설치 기능을 제공한다. 

### 6) 플러그인 캐싱
- 클로드 코든느 플러그인을 설치할 때 원본을 캐시 디렉토리로 복사한다. 
  1) 원본 플러그인 소스를 수정해도 설치된 버전에 즉시 반영되지않는다. 
     - 변경 사항을 적용하려면 플러그인을 제거하고 다시 설치해야 한다. 
  2) 심볼릭 링크는 허용된다.
     - 개발 환경에서 심볼릭 링크를 활용하면 원본과 설치된 버전을 동기화 할 수 있다. 
  3) 경로 순회는 차단된다. 
     - 자체 디렉토리 내부의 리소스만 접근할 수 있다.
